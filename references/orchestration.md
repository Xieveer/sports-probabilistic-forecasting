# Оркестрация бизнес-инициатив

Product Owner владеет исходной целью, состоянием инициативы и выбором следующей роли.
Каждая специализированная роль запускается отдельно с ссылкой на канонический артефакт
и только нужным для её задачи контекстом. Роли не вызывают друг друга.

## Выбор маршрута

- Очевидный bug fix: `Product Owner → Developer → Reviewer → PR/CI → merge`.
  Создаются TASK и отдельный `done`; BA и ADR не нужны.
- Новая функция или изменение поведения: Product Owner подтверждает критерии, при
  неоднозначности вызывает Business Analyst, при значимом решении — Architect.
  Далее небольшие TASK через Developer и Reviewer.
- Research: при отсутствии данных `Data Researcher → Engineering TASK на сбор и
  пополнение → ожидание пользовательского сбора`. При готовых данных Data Researcher
  пропускается. Research Scientist проверяет baseline, гипотезы и финансовые метрики;
  Reviewer один раз проверяет итоговое исследование перед отчётом пользователю.
  GO не создаёт production-релиз без нового решения пользователя.
- Серверная задача без правки приложения: Product Owner вызывает внешнего Operations
  Agent; его проверки достаточно. Если требуется код, Operations передаёт техническую
  постановку Product Owner и начинается Engineering.

## Память и параллельная работа

Каноническая память — управляющий блок EPIC, либо TASK для одношаговой инициативы.
В ней лежат цель, критерии, текущий этап, ветка, выполненное, решения, ссылки,
предыдущая и следующая роль, блокеры и release intent. Для Research добавляются
пороги, baseline, номер цикла и последний результат. Обновление происходит после
значимого gate. Полные логи и raw data туда не переносятся.

Ветка `initiative/<id>-<slug>` принадлежит инициативе, а не внутренней TASK.
При реальной одновременной работе используются отдельные worktree. Конфликт простого
текста разрешает Product Owner, конфликт логики приложения — Developer, изменение
архитектурной границы — Architect. После разрешения повторяются затронутые тесты
и независимое review. Перед возобновлением Product Owner сверяет ID, ветку и
последний commit с памятью; опубликованная ветка позволяет продолжить на другой машине.

## CI и выпуск

После PR Product Owner ждёт terminal CI, например командой
`gh pr checks --watch --interval 300`, проверяя статус примерно раз в пять минут.
Красный результат запускает диагностику причины, исправление и новый Review; зелёный
не заменяет проверки Reviewer. При блокере, недостающем доступе или необходимости
изменить бизнес-требования Product Owner обращается к пользователю. Технический выбор
Architect в рамках подтверждённых требований отдельного одобрения не требует.

Без запроса на релиз зелёный PR сливается в `main` без тега, версии и новых образов.
Явный исходный запрос на production-версию разрешает конкретный выпуск. Operations
Agent готовит необходимые артефакты, Reviewer повторно проверяет весь release diff,
PR проходит CI и сливается. Reviewer ставит тег на проверенный commit в `main`;
Product Owner ждёт tag pipeline, затем Operations Agent развёртывает immutable images
и подтверждает health/smoke. Изменение содержимого после финального review требует
нового review и CI; тег не передвигают.

## Ограничения

Не запускай роли для церемонии, не создавай отдельные REQ/ADR для локального бага,
не дублируй отчёт `done` в памяти. Параллелить можно независимые изменения с разными
областями владения; одну mutable state одновременно не редактируют.
