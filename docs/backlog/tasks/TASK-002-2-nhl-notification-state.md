## Результат и границы

Создать внутренний контракт и персистентное состояние для сравнения live
коэффициентов, создания одного агрегированного события на logical cycle и учёта
доставки каждому Telegram chat ID. Турнир, рынок, окно и provider приходят из
notification-профиля. Не добавлять новый публичный API, DAG или изменять расчёт
model probability/edge.

## Критерии приёмки

- [x] Новая линия, изменение линии и отсутствие изменения различаются
  детерминированно по снимкам одного набора матчей.
- [x] Матч после начала не участвует в сравнении и не удерживает poll активным.
- [x] Повтор одного logical cycle не создаёт вторую запись успешной доставки тому
  же chat ID; неотправленный chat ID можно повторить.
- [x] Начальный digest способен записать baseline без повторной рассылки
  неизменившихся коэффициентов в первом poll.
- [x] Схема создаётся в чистой SQLite/PostgreSQL-совместимой БД и не изменяет
  таблицу `predictions`.

## Follow-up security fixes

- [x] Успех или неуспех каждой Telegram-доставки фиксируется до перехода к
  следующему получателю, поэтому retry после частичного сбоя не дублирует
  уже подтверждённую доставку.
- [x] Initial CLI получает batch-котировки для записи baseline.
- [x] Пустой список администраторов завершает сценарий ошибкой; сбой одного
  администратора не отменяет попытки для остальных; chat ID не пишется в лог
  открытым текстом.
- [x] В notification state принимаются только конечные decimal-коэффициенты
  строго больше единицы.
- [x] `use_cache=False` не создаёт каталог или файл кэша; имя кэш-файла не
  содержит исходный ключ, включая секрет.

## План реализации

1. Написать падающие contract-тесты delta и delivery ledger, включая retry,
   частичную ошибку получателя и границу начала матча.

3. Сохранить baseline и delta как предметные данные, отделив сбор текста и
   HTTP Telegram transport.
4. Выполнить unit и DB integration tests.
