# ADR-027 — Локальный реестр сущностей и публикация снимков

> **Статус:** accepted
> **Дата:** 2026-10-04
> **Связанное требование:** [REQ-026](../../product/requirements/REQ-026-entity-registry.md) (`confirmed`)
> **Инициатива:** [EPIC-026](../../backlog/EPIC-026-entity-registry.md)
> **Первый срез:** [TASK-026-1](../../backlog/tasks/TASK-026-1-source-neutral-entity-registry.md)

Независимое review 2026-10-04 закрыло замечания о версиях event mappings,
повторной активации ранее установленного snapshot при rollback, локальном
адаптере `sqlite3`, транзакционных границах, интервальных конфликтах и
идентичности event-проекции, полном `ir1` snapshot и provenance цепочки
данных/обучения и сохранении оснований принятых решений в полном снимке.
Contract probe Object Storage остаётся gate задачи публикации.

## Контекст и критерии выбора

Владелец подтвердил локальное принятие решений, собственные ID и имена,
веб-очередь с пакетными действиями и распространение проверенных полных снимков
через Object Storage. Сервер не принимает решения, обучение работает локально.
Механизм должен обслуживать разные турниры и предусматривать будущих игроков.

Сейчас `TeamNameRegistry` нормализует строки и при неизвестном имени возвращает
нормализованную строку. Источники после загрузки YAML теряют отдельные пространства
имён. Live odds matcher выбирает ближайшую котировку внутри окна 360 минут,
а отсутствие времени не всегда исключает сопоставление. Это нельзя использовать
как подтверждение новой связи в новом контракте.

`canonical_events.id` — локальный autoincrement integer, публичный `event_id`
по [ADR-026](ADR-026-calendar-and-data-cycle-control.md). Уникальность спортивной
записи задаёт `(tournament, source, source_event_id)`; revisions и odds уже
ссылаются на этот PK. Один числовой ID нельзя считать переносимой идентичностью
между независимо заполненными локальной и серверной БД.

Локальный DB engine по умолчанию использует SQLite; production использует PostgreSQL.
[ADR-012](ADR-012-nhl-source-state-archive.md) уже задаёт manifest, SHA-256 и
отдельный Object Storage sync, но source-state archive имеет другой смысл и retention.
Нужны отдельные prefix, права и жизненный цикл реестра.

ADR необходим: меняются долговечная идентичность, направление владения данными,
границы записи и публикации. Критерии — отсутствие зависимости обучения от сервера,
сохранение старых API/данных, простой запуск одним владельцем, отсутствие молчаливых
слияний, проверяемая установка и обратимость. «Сотни турниров» проверяются общей
схемой и индексами; замеров нагрузки пока нет.

## Рассмотренные варианты

| Вариант | Простота и тестируемость | Безопасность и эксплуатация | Стоимость, переносимость и обратимость |
|---|---|---|---|
| Status quo: YAML + source keys | Минимум нового кода, существующие тесты | Нет очереди, аудита, полной локальной идентичности и контролируемой публикации | Дёшев сейчас, не выполняет REQ; старый путь сохраняется для совместимости |
| Локальный SQLite + веб-страница + полные снимки в Object Storage; серверная проекция PostgreSQL | Один локальный файл, общие domain contracts, две DB-реализации проверяются отдельно | Один владелец; короткие сериализованные записи; отдельные publisher/sync права | Нет нового локального сервиса, переносимый JSONL; выбран |
| Локальный PostgreSQL + тот же протокол снимков | Меньше различий SQL с сервером; удобнее конкурентные записи | Дополнительный локальный daemon/container, credentials, backup и запуск | Жизнеспособен, но дополнительная эксплуатация пока не оправдана одним владельцем; возможен позже через тот же snapshot |
| Серверный master registry + локальный cache | Одна центральная БД, проще несколько редакторов | Требует серверной административной авторизации и доступности для решений | Не соответствует подтверждённому локальному владению; сложнее offline write |
| Object Storage как изменяемый master-файл, прямое чтение runtime | Меньше DB-проекции, простой первоначальный экспорт | Нужно заново решать аудит, конкуренцию, cache, целостность и offline режим | Подходит доставке immutable данных; прямой online read не выполняет требование устойчивого runtime |

SQLite выбран для локального приложения одного владельца. Он допускает только
одного одновременного writer; short transactions и ограниченные повторы должны
проверяться вместе с локальным ingest. Файл хранится на локальном диске, не на
сетевом filesystem. Поддержка внешних ключей включается на каждом соединении.
[Ограничения SQLite](https://www.sqlite.org/whentouse.html),
[внешние ключи](https://www.sqlite.org/foreignkeys.html).

Для локального адаптера рассмотрены SQLAlchemy и стандартный `sqlite3`.
SQLAlchemy уже является зависимостью проекта и сохраняет единый стек запросов,
но локальный master и серверная проекция имеют разные схемы и роли.
Выбран `sqlite3` за repository-контрактом: переносимость обеспечивает JSONL
snapshot, общие SQL-запросы между локальной и серверной БД не требуются.
Цена выбора — явное управление соединениями, транзакциями и миграциями с
отдельными проверками конкурентных записей. SQLAlchemy остаётся серверным
адаптером PostgreSQL; смена локального драйвера не меняет domain-контракты.

## Решение

### Границы и локальное владение

Общий модуль registry содержит типизированные операции идентичности, разрешения,
решений, экспорта и валидации. Его правила не импортируют NHL, FastAPI или Object
Storage SDK. Адаптеры источников передают нормализованные факты и исходные
обозначения; локальный repository на `sqlite3`, локальная веб-страница и sync
используют одни domain DTO и контракты операций. SQL, соединения и миграции
изолированы в адаптерах; PostgreSQL/SQLAlchemy installed projection получает
данные через snapshot и не переиспользует локальные SQL-запросы. Hydra задаёт
расположение локального файла, источники, scopes
и политики сопоставления. DVC/Airflow не становятся владельцами решений.

Редактируемый реестр хранится в отдельном локальном SQLite-файле. Отдельность
защищает его от пересоздания локальной predictions DB. Миграции версионируются;
неявного создания таблиц при чтении runtime нет. Ingest и UI используют короткие
транзакции и проверку ожидаемой revision. Локальный write unit-of-work выполняет
`BEGIN IMMEDIATE` до первого проверочного SELECT, затем все проверки, изменения
и аудит в одной транзакции; успех завершает commit, ошибка — rollback.
Соединение всегда явно закрывается в `finally` или эквивалентном контекстном
менеджере, включая read-операции и ошибки проверки схемы. Сам контекстный
менеджер SQLite connection не закрывает соединение.
[Контекстный менеджер sqlite3](https://docs.python.org/3/library/sqlite3.html#how-to-use-the-connection-context-manager).

Команды изменения сущности или решения принимают `expected_revision`, сверяют
её под write-транзакцией и атомарно увеличивают revision с записью аудита.
Несовпадение возвращает конфликт без частичных изменений. Это отдельная защита
от устаревшей формы владельца, даже когда записи сериализованы SQLite.
Одиночная команда и пакет используют общий unit-of-work; вызванные внутри
пакета операции не открывают независимые соединения и не выполняют свой commit.
Параллельный повторный импорт опирается на сериализованные проверки и уникальные
ограничения, а не на проверку существования вне транзакции.

Read-only resolver работает по закреплённой версии. Локальный ingest может
добавлять кандидатов; подтверждённые изменения попадают в новый immutable export.
Перед обучением экспортируется/выбирается полный локальный снимок, версия
закрепляется на весь run и сохраняется в provenance данных и модели.
Публиковать его в сеть для запуска обучения не требуется. Изменения через UI
во время обучения не меняют уже закреплённую версию.

### Сущности, внешние обозначения и решения

Проектный ID — случайный UUID, выдаваемый локально один раз, без зависимости
от имени, slug, команды игрока или выбранного поставщика. Экспорт хранит UUID
в канонической текстовой форме. Минимальные логические записи:

| Запись | Контракт |
|---|---|
| Entity | `id, kind, sport, project_name, revision, state`; типы `tournament/team/event/player` |
| External designation | `source, kind, scope, value_kind, raw_value, normalized_value, valid_from, valid_until, entity_id, state` |
| Decision | Неизменяемые `decision_id, actor, action, reason, prior_revision, decided_at`, ссылка на исходную запись/предыдущее решение |
| Event identity | Турнир UUID, участники UUID с ролями, source references; время и статус наблюдаются отдельно и не входят в ID |
| Membership | `player_id, team_id, relation_kind, valid_from, valid_until`; полуинтервал времени UTC, открытый конец допустим |
| Candidate | Исходный ключ, минимальные факты, кандидаты/основания, origin, observed_at, revision, состояние очереди |

Область применимости обязательна и явно отличает `sport/tournament/season`
от глобального пространства ID конкретного provider. Scope — каноническая
структура со стабильным ключом; отсутствие scope не означает wildcard.
Внешний source ID сравнивается по контракту provider. Нормализация имён
версионируется, сохраняет исходный Unicode и не превращает результат в ID.
Коллизия нормализации даёт конфликт. Совпадение названий из разных источников
само по себе ничего не подтверждает.

Один внешний ключ в одной области и пересекающемся периоде не может иметь
два действующих подтверждения. Идентичные операции идемпотентны.
Проверка временного пересечения выполняется в сериализованной write-транзакции.
Историческое разрешение получает дату события; если дата нужна для выбора
между историческими привязками и отсутствует, результат неоднозначен.
Переименование меняет project name с аудитом, сохраняя UUID и старое обозначение.
Неправильное решение исправляется новым решением; историю не перезаписывают.
Автоматическое слияние двух уже созданных UUID не входит в этот ADR.

**Интервальные конфликты.** Решение действует только на явно заданный
полуинтервал `[valid_from, valid_until)` внешнего ключа. За его пределами
подтверждения и UUID не меняются. Например, при A→X на `[2020,2030)` и
противоречии B→Y на `[2025,2026)` выбор Y даёт X/Y/X; отклонение B до выбора
восстанавливает X на всём исходном интервале, если других противоречий нет.

Базовые designation сохраняют provenance; отдельные interval overlays хранят
участников конфликта, границы, revision и `decision_id`. Их состояния:
`open` блокирует подтверждённое разрешение внутри своего интервала;
`resolved` содержит выбранный `selected_entity_id`; `dismissed` означает снятое
противоречие и не задаёт победителя. `conflict` является состоянием разрешения
спорного интервала, а не основанием переписать всю базовую привязку.

| Действие | Переход внутри указанного интервала |
|---|---|
| `pending` | Новый кандидат не подтверждён; при противоречии открыть overlay только на пересечении |
| `confirm` | Подтвердить при отсутствии открытого конфликта и другой подтверждённой сущности; иначе потребовать разрешение конфликта |
| `defer` | Отложить кандидата, сохранив открытые противоречия |
| `reject` | Исключить отвергнутую гипотезу и закрыть вызванные ею overlays как `dismissed`; пересчитать разрешение по оставшимся привязкам |
| `resolve_conflict` | Записать выбор UUID для явного интервала и набора противоречий, закрыть охваченные overlays как `resolved`; не менять base UUID вне интервала |

При частичном закрытии overlay разбивается на закрытый участок и открытые
остатки; пустые интервалы не создаются. Частичное изменение состояния самой
designation также требует непересекающихся сегментов с общей исходной ссылкой:
исходная запись сохраняется как `superseded`. Исправление прежнего интервального
решения явно заменяет его действие на нужном участке, сохраняя историю.

При нескольких кандидатах проверяются все пересечения ключа. Неохваченный
открытый конфликт продолжает блокировать разрешение; отклонение B не подтверждает
оставшегося pending C. Resolver с датой сначала учитывает открытые overlays,
затем действующий интервальный выбор, затем подтверждённые базовые сегменты.
`dismissed` и заменённые исторические решения не перекрывают базовые привязки.
Несогласованные действующие решения дают конфликт, а не выбор по порядку строк.

Закрытие, разбиение, изменения состояний и аудит выполняются в одном write
unit-of-work с `BEGIN IMMEDIATE`. Команда проверяет ожидаемые revisions всех
затронутых designation/overlays и полный набор пересечений; новый неучтённый
участник или устаревшая revision отклоняет всю операцию. Аудит сохраняет точный
интервал, прежний/новый target, автора, причину и связь с заменённым решением.
Граничные даты, частичное решение, reject/defer и три кандидата проверяются
контрактными тестами вместе с сохранением привязок вне спорного интервала.

`player` поддерживается типовым контрактом. Принадлежность игрока команде
не является частью его ID или уникальности имени. Схема не предполагает
единственную команду для всех типов отношений: сборная и клуб могут сосуществовать.
Тест перехода между командами проверяет исторические интервалы; загрузка
составов и player predictions остаются за пределами эпика.

YAML NHL импортируется как явно доверенный seed с provenance файла/версии,
пространством источника и idempotency key. Повтор не восстанавливает отменённое
владельцем решение и не заменяет его новым seed. Импорт не удаляет YAML.
NHL-разбор и source-specific секции находятся в отдельном seed importer,
который вызывает общие операции registry; repository/domain не содержат
NHL-констант, YAML-схемы источника или импортов provider-модулей. Другой турнир
использует тот же repository-контракт со своим адаптером входных данных.

### Локальная веб-очередь

Отдельный локальный entry point на существующем FastAPI, минимальный HTML
с серверной обработкой форм; отдельный frontend framework не требуется.
Есть поиск, фильтры по источнику/турниру/состоянию, пагинация, сравнение вариантов
и оснований, выбор проектной сущности или её создание, подтверждение, отклонение
и откладывание. Отложенный/отклонённый кандидат не открывается повторно от
идентичного импорта; новые факты могут создать новую revision с видимой причиной.

Пакетное действие показывает выбранные строки и целевые сущности, передаёт
ожидаемые revisions и выполняется одной ограниченной транзакцией. Конфликт
любой строки отклоняет пакет целиком и возвращает конкретные строки для
повторного просмотра. Поиск не означает массовое подтверждение всех невидимых
результатов; лимит пакета конфигурируется.

Слушать только loopback. Локальный секрет открывает сессию владельца;
секрет не передаётся в query string. Для mutations обязательны CSRF token,
проверка Origin/Host и session cookie с HttpOnly/SameSite. GET ничего не меняет,
внешние имена HTML-экранируются. Автор берётся из серверной конфигурации сессии,
а не из поля формы. Это защищает от запросов посторонней вкладки браузера;
компрометация учётной записи ОС вне границы локальной аутентификации.
В production образе/entry point роуты редактирования не подключаются.
Прежнее предложение SSH-туннеля отменено локальным процессом.

### Разрешение событий и совместимость

Resolver возвращает `resolved/unresolved/ambiguous/conflict` вместе с причиной,
версией и основаниями. Существующая подтверждённая привязка source event ID
имеет приоритет над эвристикой времени; существенное противоречие участников
или турнира блокирует автоматическое использование и попадает на проверку.
Перенос времени того же source ID не создаёт новый UUID.

Для новой букмекерской связи допускается автоматическое локальное решение
только при подтверждённых tournament/home/away UUID, известных UTC timestamps,
отсутствии конфликтов и взаимно единственном совпадении событий в заданном
окне. Ближайший из нескольких не считается однозначным; перестановка
home/away и похожие строки не исправляются молча. Версия политики и основания
сохраняются как machine decision. Локально созданное решение действует на
сервере только после публикации.

Начальная консервативная политика — точное равенство времени (`tolerance=0`).
Существующее окно 360 минут применяется только для предложений владельцу.
Расширение окна автоматического решения требует fixture с повторными матчами
и переносами и явной настройки турнира/источников, не Python-ветвления.
Missing timestamp и неполные участники допускают кандидата, но не автоматическую
связь. Явные ручные overrides импортируются с provenance, а не применяются
скрытым обходом resolver.

Существующие `canonical_events.id`, source key, forecast/source `match_id`,
FK и archive payload сохраняются. Добавляется таблица
`registry_canonical_event_mappings` с первичным ключом
`(snapshot_id, canonical_event_id)`, nullable `project_event_id`, состоянием
разрешения и ссылкой на решение. Ссылка на проектное событие проверяется внутри
того же snapshot. Для разных снимков одновременно сохраняются независимые
отображения одной canonical записи; единственного перезаписываемого UUID-поля
на `canonical_events` недостаточно. Записанное отображение внутри версии
неизменно, в том числе результат `unresolved`.
Числовой PK обозначает прежнюю локальную canonical запись; UUID обозначает
переносимую проектную сущность. Публичный `event_id` остаётся прежним integer;
проектный UUID при необходимости добавляется отдельным необязательным полем.
UUID не вычисляется из локального autoincrement ID.

Backfill сопоставляет полные source keys и проверенные entities. Совпадения
по одному имени, времени или числу `match_id` запрещены. Несколько historical
canonical rows могут ссылаться на один project event; старые rows не удаляют.
Выдача спортивного календаря сохраняет действующий primary sports source,
а новые bookmaker mappings не создают отдельные календарные события.
Backfill строит отображения только для устанавливаемого snapshot в staging,
не обновляя строки прежних версий. Для canonical записей, появившихся позднее,
отображение вычисляется по полному source key и закреплённому snapshot, затем
идемпотентно добавляется для этой пары ключей. Отсутствие строки требует такого
разрешения в той же версии, а не чтения active/latest mapping. Запросы и runs
всегда читают bridge с закреплённым `snapshot_id`; смена активной версии не
смешивает новый alias с предыдущим event mapping.

Если сервер первым видит спортивное событие, он продолжает сохранять его
canonical source запись и допускает календарь/прогноз по прежнему контракту.
Bridge данной версии фиксирует `unresolved` и пустой `project_event_id`,
кандидат передаётся локально. Неизвестная команда
также не должна удалять календарную запись; пригодность модельных признаков
по-прежнему проверяют существующие quality gates. Сервер не выдаёт новый
project UUID и не утверждает bookmaker связь. Это сохраняет доступность
календаря при offline-владельце, но новые odds могут ожидать публикации.

Переход управляется явной конфигурацией reader mode. При включённом registry
режиме `unresolved` не вызывает fallback в прежний нормализатор/ближайший
matcher. До перехода старый режим остаётся для совместимости; переключение
production отдельно разрешается пользователем после gates.

### Идентичность event-проекции до полного экспорта

Один `snapshot_id` навсегда обозначает одно проверенное содержимое resolver.
Фабрика `EventIdentitySnapshot.from_registry(registry)` не принимает ID от
вызывающего кода: в одной SQLite read-транзакции она копирует resolver-relevant
данные и вычисляет SHA-256 канонического UTF-8 JSON. Сортируются события,
обозначения, source keys, scopes и interval overlays; timestamps приводятся
к UTC. Digest включает участников/турнир события, исходные ключи, состояния,
временные границы designation, overlays с их интервалами и действующими
решениями, а также версии схемы проекции, нормализации и политики разрешения.
Порядок INSERT не влияет на ID; изменение влияющих на разрешение фактов меняет
digest. Отдельная revision изменяемого registry не заменяет эту проверку.

В TASK-026-3 ID имеет вид `ev1:<sha256>` и вид `event_projection`. Это локальная
event-проекция, не полный registry manifest. В TASK-026-4 фабрика
`from_verified_registry_snapshot(...)` получает ID полного проверенного manifest
по контракту следующего раздела и вид `registry_manifest`; digest event-проекции
сохраняется отдельно. Эти пространства идентичности не смешиваются: старые
`ev1:*` и их mappings не переименовываются и не считаются полным экспортом.
Серверная публикация полного registry использует только `registry_manifest`.

В той же service DB, где хранится bridge, вводится immutable заголовок
`registry_identity_snapshots`: `snapshot_id` PK, `snapshot_kind`,
`projection_schema_version`, `normalization_version`, `projection_sha256`, `policy_version` и
`projection_json` с каноническим содержимым. Для `registry_manifest` регистрация
дополнительно требует проверенный полный manifest и вывод проекции именно из
него; произвольная пара manifest ID/проекция недопустима. Bridge имеет FK
`snapshot_id` на этот заголовок. Сохранённая проекция позволяет после рестарта
добавить отсутствующий mapping без обращения к mutable registry.

`register_event_snapshot(session, snapshot)` пересчитывает digest и проверяет
связь ID, вида и содержимого на границе записи, даже если dataclass был создан
в обход фабрики. Повтор идентичного заголовка идемпотентен; тот же ID с другим
содержимым отклоняется. `put_event_mapping` принимает проверенный snapshot или
descriptor, привязанный к сохранённому заголовку, вместо произвольного ID.
Одного FK недостаточно: нужно проверить, что resolver использовал именно
закреплённое содержимое. Для `resolved` project event должен присутствовать в
этой проекции, а policy соответствовать её закреплённой версии.

Регистрация и запись bridge выполняются атомарно в SQLAlchemy-транзакции.
PK заголовка защищает конкурентную регистрацию: после конфликта проверяется
совпадение сохранённого содержимого, без перезаписи. Загрузка сохранённой
проекции проверяет digest/schema/kind и воспроизводит прежний resolver; текущая
локальная БД не используется для дополнения старого снимка. Immutable заголовки
и их содержимое сохраняются вместе с mappings и закреплёнными runs.

Контрактные проверки: одинаковые факты при разном порядке загрузки дают один ID;
изменение времени/overlay/policy даёт другой; поддельный прежний ID не допускает
добавления даже нового canonical mapping; после рестарта mapping дополняется
из сохранённой проекции; конкурентная регистрация не закрепляет разное
содержимое за одним ID. Это не заменяет полный export/manifest gate TASK-026-4.

### Формат снимка и Object Storage

Полный снимок содержит сущности, внешние обозначения с состояниями и периодами,
принятые решения/историю, event relations и memberships. Внешние обозначения
экспортируются в объёме, необходимом resolver и истории принятых решений;
необработанные наблюдения и техническое состояние очереди передаются отдельным
каналом и не являются содержимым полного снимка.
Снимок не содержит локальных DB credentials, browser sessions, полных ответов
источников или локальных путей. Actor — проектный идентификатор владельца.

История принятого решения включает ограниченные по схеме и размеру ревизии
evidence, на основании которых владелец принял решение: исходный ключ/значение,
источник, значимый временной контекст, рассмотренные кандидаты и основания,
ссылку на decision и конкретную evidence revision. Эти данные фиксируются
при принятии решения, сохраняются в `decisions.jsonl` либо отдельном immutable
сегменте с hash/bytes/counts в manifest и доступны после offline-загрузки пакета.
Ссылка на изменяемую локальную очередь без сохранённого evidence недостаточна.
Связи с предыдущими решениями и их основаниями сохраняются; валидатор проверяет
целостность ссылок и лимиты. Полные provider payload не включаются в evidence.

Позднейшее дополнение оснований оформляется новой связанной evidence revision
с аудитом; основания уже принятого решения не заменяются текущим состоянием
кандидата. Новая сохранённая revision evidence принятого решения меняет `ir1`,
даже если результат resolver прежний: это изменение опубликованной истории.
Новые pending observations, их last_seen/count и служебные revisions очереди
не меняют `ir1`, пока не меняют resolver state и не закреплены в evidence
принятого решения. Если наблюдение открывает действующий конфликт, изменение
resolver state входит в snapshot и меняет ID независимо от статуса очереди.

Предлагаемый независимый prefix в существующем storage:

```text
entity-registry/v1/snapshots/<sha256>/
  manifest.json
  entities.jsonl
  designations.jsonl
  decisions.jsonl
  events.jsonl
  memberships.jsonl
entity-registry/v1/publications/<publication-id>.json
entity-registry/v1/current.json
entity-registry/v1/candidates/<installation-id>/<batch-id>.jsonl
entity-registry/v1/candidate-acks/<installation-id>/<batch-id>.json
```

JSONL в UTF-8 — переносимые данные, не SQL dump и не исполняемый pickle.
Каждый файл сортируется по стабильному ключу; сериализация и timestamps UTC
канонизированы. Manifest задаёт schema version, file SHA-256/bytes/counts,
policy versions и только стабильные версии/идентичности происхождения данных
(например, schema источника и digest доверенного seed). Полный snapshot ID имеет вид
`ir1:<sha256(canonical manifest)>`, где собственный ID исключён из хешируемого
manifest. Хеш охватывает стабильное состояние и версии schema/policy/source
provenance; время текущего экспорта, export run ID, hostname, локальные пути
и другие метаданные конкретной попытки не входят ни в хешируемый manifest,
ни в перечисленные им state-файлы. Такие сведения при необходимости сохраняются
отдельным журналом экспорта вне content-addressed пакета либо не сохраняются.
Сохранённые даты и авторы исходных решений и связанные с ними evidence revisions
являются частью состояния/аудита и не заменяются временем или автором текущего
экспорта. «Полное состояние» здесь означает экспортируемое состояние resolver
и принятых решений с их основаниями; техническая pending queue в него не входит.
Одинаковое полное
состояние при одинаковых версиях контрактов и стабильном source provenance
даёт одинаковые bytes manifest и `ir1` при повторном экспорте, на другой машине
и в другом каталоге; это проверяется тестом с разными часами/run ID/путями.
Дополнительные проверки подтверждают offline-доступ к evidence старого решения,
смену `ir1` при добавлении его evidence revision и неизменность ID при новом
pending наблюдении, не изменяющем resolver state или принятую историю.
Этот content-derived manifest ID служит единственной глобальной
версией экспортированного состояния registry. Отдельного монотонного счётчика
master registry нет; максимум или иная агрегация row revisions не заменяет
версию состояния. Row revisions служат проверке конкурирующих изменений записей,
а publication sequence — порядку публикаций, включая откат.
Вид снимка — `registry_manifest`; `ir1` отличается от `ev1` проекции.
В Object Storage компонент `<sha256>` пути содержит только hex digest,
а manifest/descriptors и provenance используют полный `ir1:<digest>`.
В manifest разрешены только
известные относительные имена файлов; абсолютные пути и `..` запрещены.
Ограничения размера/числа строк проверяются до установки.

### Полный локальный пакет и provenance обучения

До публикации полный снимок хранится локально как immutable пакет manifest и
перечисленных файлов, адресуемый digest. Повтор идентичного экспорта допускает
переиспользование пакета; другое содержимое по тому же ID запрещено. Проверка
пакета выполняется offline и охватывает ID manifest, schema, все file hashes
и структурные ограничения. Неизменяемый пакет не зависит от доступности
Object Storage, сервера или редактируемого master registry.

Выбор версии для pipeline представлен manifest-файлом по стабильному
конфигурируемому пути. Его содержимое соответствует выбранному immutable
пакету; смена выбора меняет этот файл, а не содержимое существующего пакета.
DVC объявляет selected manifest явной зависимостью затронутых стадий.
Стадия в начале проверяет выбор и закрепляет `ir1` на всё исполнение; она не
перечитывает изменившийся выбор посередине. Package files проверяются по
manifest до использования, даже если выбранный manifest не изменился.

Для выходного Parquet стадий `raw → interim → processed` сохраняется sidecar:
версия контракта, `registry_snapshot_id`, manifest digest, стадия и SHA-256
точных bytes выходного Parquet. Производная стадия проверяет входной sidecar
и hash входного Parquet, сохраняет ту же закреплённую версию и связывает
свой sidecar с проверенным входом. Sidecars объявляются outputs/dependencies
DVC вместе с соответствующими данными. Новая версия registry требует
перестроить затронутую цепочку; переписать только sidecar нельзя.

При включённом registry режиме отсутствие пакета/manifest/sidecar, несовпадение
выбранного `ir1`, schema или checksum завершает стадию ошибкой. Старый файл
данных с новым sidecar и новый Parquet со старым sidecar не считаются готовым
результатом. Совместный выпуск Parquet и sidecar не должен оставлять принимаемую
читателем неполную пару: staging, проверка и атомарная фиксация либо проверяемый
маркер готовности обеспечивают этот контракт. Legacy режим остаётся явно
выключенным registry режимом, без автоматического fallback при ошибке проверки.

Trainer проверяет sidecar именно выбранного processed Parquet, его checksum
и соответствие закреплённому manifest до начала обучения. Полный локальный
snapshot используется для разрешения без server API/Object Storage. В provenance
модели и параметрах/артефактах MLflow сохраняются `ir1`, manifest digest,
processed data hash и проверенный sidecar; исходная версия восстанавливается
по этим данным. Проверка provenance выполняется локально и не требует
сетевого поиска registry; проверочный сценарий использует локальный MLflow.

Контрактные проверки включают offline export/read/train, порчу package file,
смену selected manifest с перестроением DVC, пропущенный sidecar, подмену
Parquet, несовпадение registry версии между стадиями и изменение master/выбора
во время уже закреплённого run. Эти проверки относятся к TASK-026-4.

### Публикация полного снимка

Exporter читает полное локальное состояние в одной SQLite read-транзакции,
вычисляет content-derived версию снимка, проверяет FK, UUID,
уникальность/scopes/временные конфликты и создаёт полный snapshot. Publisher:

1. Загружает immutable objects по content address с запретом overwrite.
2. Читает удалённые bytes и сверяет SHA-256 и manifest.
3. Создаёт immutable publication record: монотонный sequence, snapshot ID,
   предыдущая publication, время и автор.
4. Меняет `current.json` последним, условной записью по предыдущему ETag;
   первоначальное создание использует условие отсутствия объекта.

Указатель содержит publication sequence/ID и snapshot ID/hash, а не набор
изменяемых файлов. Reader читает pointer один раз и скачивает указанную версию;
последующая смена pointer не изменяет этот download. Ошибка до шага 4 оставляет
старую опубликованную версию. Повтор после неизвестного результата PUT сначала
читает pointer и проверяет publication ID. Конфликт CAS требует перечитать
состояние, не затирает чужую публикацию. Один локальный publisher дополнительно
сериализуется lock; нельзя молча обходить unsupported conditional writes.

Yandex Object Storage документирует `If-None-Match` и `If-Match` для `PutObject`;
поддержка и настройки конкретного bucket/endpoint ещё требуют contract probe.
ETag используется как concurrency token, отдельный SHA-256 — как checksum.
Это не WORM и не защита от злоумышленника с publisher credentials.
[Условные записи Yandex Object Storage](https://yandex.cloud/en/docs/storage/operations/objects/upload).

### Серверная установка, offline и обратная очередь

Отдельная sync-команда читает Object Storage и пишет только registry installation
tables. Worker/API не получают storage credentials. Начальная техническая
cadence — раз в пять минут с jitter, ограниченным timeout/retry и запретом
параллельной установки; это настройка, не обещание SLA. Для локальной проверки
предусмотрен явный sync. Runtime запросы не ожидают сеть.

Installer проверяет весь снимок и staging-таблицы до активации. Таблицы
проекции адресуются `(snapshot_id, entity/key)`; установленные версии immutable.
Активная пара `(publication_sequence, snapshot_id)` переключается одной
PostgreSQL-транзакцией после всех проверок, включая versioned event mappings.
Каждый resolver request и batch run сначала закрепляет snapshot ID, включая
event bridge. Старые поколения и их mapping rows остаются доступны выполняющимся
runs и не перезаписываются при backfill или активации следующего поколения.
Одна смена pointer в БД без закрепления версии недостаточна: при Read Committed
разные SELECT могут увидеть разные commits.
[Изоляция PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html).

Ошибка сети, checksum, schema, constraint или транзакции не меняет активную пару.
Для уже проверенного установленного snapshot повторный импорт его immutable
данных — no-op. Активация publication является отдельной обязательной операцией:
больший sequence обновляет активную пару даже при уже установленном snapshot.
Если sync пропустил несколько публикаций, он проверяет цепочку
`previous_publication_id` и устанавливает недостающие records по порядку;
installer принимает только следующую sequence и предыдущий активный
publication ID. Это не позволяет произвольному пропуску скрыть подмену истории.
Повтор идентичной publication — no-op; тот же sequence с другим publication ID
или содержимым — конфликт. До первой установки registry
mode возвращает unavailable; не подменяет пустой registry legacy-сопоставлением.
Метрики/health показывают installed/published version, last successful sync,
возраст снимка, candidate backlog и last error code; старый снимок помечается
устаревшим, но не перестаёт существовать.

Для отката publisher создаёт новую publication с большим sequence, указывающую
на прежний проверенный snapshot. Это отделяет намеренный rollback от
проигрывания старого pointer. Installer отвергает меньший sequence и принимает
повтор идентичного. При rollback импорт уже установленного snapshot можно
пропустить, но новый publication sequence и прежний snapshot активируются
атомарно вместе. Его сохранённые mappings вновь используются новыми запросами;
runs, закреплённые за другой версией, дочитывают её собственные mappings.
Локальная история решений от отката сервера не изменяется.

Сервер пишет неизвестные обозначения в отдельный durable outbox, разрешённый
acquisition-процессу. Transport экспортирует bounded immutable batches в
`candidates/`; локальный importer проверяет схему и идемпотентно переносит их
в очередь по origin/idempotency key. Только после local commit публикуется ack.
Потерянный ack вызывает безопасный повтор; cursor не продвигается до commit.
Повторные наблюдения обновляют last_seen/count, не плодят одинаковые задания.
Из batch передаются только необходимые исходные ключи и evidence.
Отказ storage оставляет outbox для retry. Ack означает доставку, не подтверждение:
сервер продолжает ждать решения в новом snapshot.

Права разделены: local publisher — Get/Put snapshots/publications/current;
server sync — Get этих ключей; server feedback exporter — Put/Get verification
только своего candidates prefix; local importer — List/Get candidates и Put ack;
server exporter — Get своего ack. List ограничен prefix. Runtime не пишет
published registry. Ни одной application account не нужен DeleteObject.
Current/snapshots не доступны server feedback writer.
Operations проверяет, что старые wildcard archive grants не захватывают новый prefix.

Историю snapshots/publications по умолчанию не удаляют автоматическим lifecycle;
старое правило source-state 90 дней сюда не переносится. Использованные обучением
версии закрепляются в provenance и сохраняются. Минимум active и previous
поколения вместе с их mapping rows остаются установленными; GC дополнительно
учитывает закреплённые runs и не удаляет их snapshot или mappings.
Чистка не входит в автоматическую миграцию. Backup локального master хранит
также очередь и unpublished audit; опубликованный snapshot не заменяет этот backup.

## Последствия

- Локальные данные и решения доступны без сервера; immutable версии делают
  обучение и серверное разрешение воспроизводимыми.
- Совместимость требует двух ID и явного bridge. Это дополнительная модель,
  но не требует переписывать старые predictions, revisions и архивы.
- SQLite упрощает запуск; нужны tests writer contention, а PostgreSQL installer
  требует реального integration test атомарности и DB grants.
- Полные snapshots проще incremental replication, но растут с событиями и
  историей решений. Объём, длительность export/install и storage cost измеряются
  на реальных данных; обещания throughput для сотен турниров пока нет.
- Локальный компьютер — единственный writer: пока он выключен, новые
  неоднозначные связи ожидают. Candidate outbox и установленная копия сохраняют
  работу с известными сущностями.
- Ошибочное массовое подтверждение исправляется audited decision и новой
  публикацией. Checksum защищает целостность доставки, но не качество решения.
- Необходимы Operations grants/cadence/retention/backup runbook перед выпуском;
  этот proposed ADR не является production deployment authorization.

## Проверка и пересмотр

Предлагаемые последовательные вертикальные TASK:

1. **Локальная идентичность:** SQLite schema/domain + source-scoped resolver +
   идемпотентный YAML seed; NHL и синтетический второй турнир, переименование,
   конфликты, player membership. Проверяются параллельное добавление одного
   обозначения, два решения по одной revision, rollback изменения вместе с
   аудитом, закрытие соединений и повтор явной миграции.
   Основа [TASK-026-1](../../backlog/tasks/TASK-026-1-source-neutral-entity-registry.md).
2. **Удобное решение:** локальная веб-очередь, поиск, bounded batches, аудит,
   reject/defer, optimistic conflict, session/CSRF и ingest → UI → resolver.
3. **События и совместимость:** event entities/bridge, строгий matcher, additive
   backfill/dry-run, сохранение календаря и forecast API при unresolved,
   fixtures переносов/повторных матчей и архива.
4. **Воспроизводимый локальный run:** полный validated snapshot, pinned offline
   reader, provenance ingest/training, изменение master во время обучения.
5. **Публикация и серверное чтение:** Object Storage fake fault injection,
   CAS/current, PostgreSQL staging/activation/pinned requests, retry/rollback.
   Обязательный сценарий: run закрепляет A, B меняет mapping того же события,
   run продолжает видеть A; новая publication откатывает active на уже
   установленный A с большим sequence, новые запросы видят A, а run на B — B.
   Отдельный provider contract probe выполняется перед реальным включением.
6. **Обратная очередь и итоговый процесс:** server outbox → Object Storage →
   local queue → decision → publication → installed resolution, lost ack/retry,
   NHL и второй турнир через конфигурацию; runbook, migration/rollback evidence,
   независимый review и terminal CI.

Пересмотреть SQLite при измеренных очередях writers/lock timeouts, потребности
в нескольких редакторах или удалённом доступе. Переход на локальный PostgreSQL
сохраняет UUID, repository contract и snapshots. Пересмотреть полные снимки
при измеренном превышении времени/дискового бюджета; incremental формат
потребует отдельного ADR с сохранением возможности полного восстановления.
Публичный переход с integer event_id на UUID тоже отдельное API-решение.

Откат к прежнему reader mode возможен только явно и с фиксацией семантики
старого matcher; unresolved не запускает такой откат автоматически.
Аддитивные таблицы и история сохраняются, destructive downgrade не нужен.

## Источники и неизвестное

Проверенный локальный контекст: `sports_forecast/service/db/models.py`,
`sports_forecast/service/db/engine.py`,
`sports_forecast/data/providers/odds/team_name_registry.py`,
`sports_forecast/data/providers/odds/live_nhl_pinnacle.py`,
`sports_forecast/deploy/canonical_bootstrap.py`,
`sports_forecast/deploy/archive_sync.py`,
[production topology](../../operations/production-runtime-topology.md),
[ADR-026 календаря](ADR-026-calendar-and-data-cycle-control.md),
[ADR-012 архива](ADR-012-nhl-source-state-archive.md).
Официальные источники SQLite, PostgreSQL и S3 выше проверены 2026-10-04.

Неизвестные не блокируют локальный domain/UI срез, но являются gates соответствующих
TASK: фактическая поддержка conditional writes существующим Object Storage endpoint,
права/prefix/lifecycle, объём полного registry, длительность установки, backlog при
offline-владельце и backup recovery. При отсутствии CAS поддержку нельзя предполагать:
до publication TASK требуется скорректированный проверяемый протокол в ADR.
Численные resource limits и окна вне точного совпадения задаются конфигурацией
после fixture/нагрузочной проверки; provider schema здесь не выдумывается.
