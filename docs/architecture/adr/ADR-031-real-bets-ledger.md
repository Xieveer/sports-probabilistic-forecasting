# ADR-031 — Журнал фактических ставок и контекст Telegram-карточки

> **Статус:** accepted
> **Дата:** 2026-10-11
> **Связанное требование:** [REQ-031](../../product/requirements/REQ-031-real-bets-ledger.md)
> **Инициатива:** [EPIC-031](../../backlog/EPIC-031-real-bets-ledger.md)

## Контекст и критерии выбора

Владелец записывает через Telegram одиночные ставки Winline в RUB, включая
отдельные доборы и фрибеты. Финансовый журнал должен переживать рестарт бота,
повторную доставку callback, исправление суммы или расчёта и новую публикацию
прогноза. Для каждой ставки нужна проверяемая история изменений.

В сервисной БД уже есть неизменяемые `prediction_revisions`, изменяемая витрина
`predictions.current_revision_id` и отдельное control-соединение с авторизацией
по service credential и Telegram principal. Это отдельная роль подключения к
существующей БД, а не необходимость разворачивать ещё одну БД.

Публичный `/predict` предназначен для чтения. Его live Pinnacle enrichment
возвращает цену без устойчивого observation ID. Сервисная последняя линия и
локальный исторический архив EPIC-027 не являются взаимозаменяемыми источниками
идентичности котировки. Поиск актуальной revision после нажатия кнопки может
привязать ставку к другой версии, чем видел владелец.

ADR необходим: выбираются долговечный финансовый контракт, граница записи и
авторизации, механизм неизменяемой связи и поведение конкурентных исправлений.
Они затрагивают API, БД и Telegram и дороже локального изменения форматтера.

## Рассмотренные варианты

| Вариант | Достоинства | Риски и стоимость |
| --- | --- | --- |
| Состояние диалога в памяти бота, запись текущих значений без audit | Минимум таблиц | Теряются контекст и защита от повторов после рестарта; невозможно проверить исправления. REQ не выполняется. |
| Текущая запись + audit + сохранённый контекст карточки в существующей БД | Одна транзакционная граница, повторное использование control API, прямой месячный запрос | Нужны миграция, права таблиц и проверка согласованности audit с текущей строкой. Выбрано. |
| Подписанный контекст в Telegram или отдельное event-sourcing хранилище | Подпись позволяет проверять содержимое; полный event sourcing восстанавливает любое состояние | Подписанный payload не помещается в callback и всё равно требует хранения; ключи/ротация или проекции событий усложняют эксплуатацию одного владельца. Оснований для отдельного сервиса нет. |

## Решение

### Хранение и границы

Использовать существующую SQLAlchemy/Alembic БД через control-соединение.
Три сущности: неизменяемый контекст карточки, текущая фактическая ставка,
добавляемая история операций. Отдельные сервисы, scheduler и очередь не нужны.
Исследовательские simulated bets не записываются в эти таблицы.

Контекст содержит непрозрачный ID, владельца, время создания UTC, идентичность
события (`tournament`, `source_namespace`, `source_event_id`), рынок и его
правила, данные отображённой карточки,
nullable `prediction_revision_id`, snapshot показанной котировки и nullable
внешнюю ссылку observation. Идентификатор source event нельзя использовать без
namespace и турнира. Первый срез хранит идентичность источника без отдельного
`canonical_event_id`; этого достаточно для привязки карточки к её исходному
событию. Для старой записи без namespace сохраняется явное отсутствие значения,
которое нельзя считать подтверждённой межисточниковой идентичностью. Nullable
связи сопровождаются явным статусом отсутствия.

Ставка содержит собственный ID, владельца, `context_id` при наличии карточки,
идентичность события/рынка/исхода, `bookmaker=winline`, `currency=RUB`, тип средств,
номинал, фактический decimal coefficient, `placed_at`, состояние open/settled/
cancelled, settlement win/loss/void, nullable `settled_at`, фактическую выплату,
номер revision и служебные timestamps. Исправления фактических условий
не перезаписывают исходный контекст. Каждый добор — новая ставка.

Для денег использовать целые копейки или точный `Numeric` с двумя десятичными
знаками; для odds — точный decimal, без финансовой арифметики на `float`.
Входные NaN/Infinity, отрицательные выплаты, неположительный номинал, odds ≤ 1,
неизвестные типы средств/исходы и неполный settlement отклоняются. Расчётная
выплата округляется один раз до копеек по `ROUND_HALF_UP`; фактическая выплата
хранится отдельно. Разница показывается и не исправляется автоматически.

Audit хранит actor, request ID, время UTC, действие, причину отмены,
прежнее и новое состояние, revision и результат операции. Создание тоже
попадает в audit. Изменение текущей строки и добавление audit атомарны.
API не предоставляет физическое удаление: ошибочная запись отменяется с
причиной и исключается из финансовой сводки; история сохраняется.

### Привязка к карточке

Публичный `/predict` добавляет nullable `current_revision_id` из той же
прочитанной строки, что вероятности и идентичность прогноза. Это дополнительное
поле ответа без изменения read-only границы. Бот получает обычный батч прогнозов
с live extras, затем **до показа** отправляет точный payload выбранной карточки
в защищённый `POST /admin/bet-contexts`. Сервер проверяет и сохраняет snapshot
через `get_control_session()`, возвращает сохранённый payload и context ID.
Бот показывает возвращённый payload; кнопка содержит только context ID.

Этот вариант требует одного первоначального batch enrichment. POST контекста
не запрашивает Odds API, latest prediction или новую цену. Альтернатива —
полностью формировать батч карточек внутри закрытого endpoint — также может
использовать один live fetch, но дублирует путь выборки периодов. Повторная
генерация каждой карточки после уже выполненного публичного запроса вызывает
лишние fetch и может сохранить другую линию. Выбран обмен готовым payload при
явном доверии авторизованному боту.

Действующие grants позволяют `sf_api_reader` читать `predictions`; control-роль
не читает эту витрину и не нуждается в новом доступе к ней. Для проверки ссылки
control-роли добавить SELECT необходимых полей `prediction_revisions`:
ID, событие, рынок, исходы и вероятности. Endpoint проверяет соответствие
идентичности события/рынка и модельных исходов/вероятностей указанной revision,
включая допустимую точность числовой сериализации. Несовместимый payload
отклоняется, а не переписывается под latest. Отсутствующий в БД непустой ID
также отклоняется. При `null` запись разрешена с явной пометкой; автоматическое
достраивание ссылки позже запрещено.

Поля snapshot проходят ограниченную схему: допустимые ключи, размеры строк,
конечные числовые значения и диапазоны вероятностей/цен. При наличии внешнего
observation ID нужна проверяемая ссылка на поддерживаемое хранилище; произвольный
ID клиента нельзя принимать как подтверждение происхождения. В первом срезе
live payload без такой ссылки сохраняется с `observation_id=null`.

Котировка хранится как snapshot показанных цен с источником и `captured_at`
сервера. Это время фиксации карточки, а не заявленное время наблюдения провайдера.
Если enrichment не дал observation ID, он остаётся `null`; интерфейс сообщает
об отсутствии исторической ссылки. ID контекста не выдаётся за observation ID
EPIC-027. Недоступная линия остаётся отсутствующей и не блокирует ввод Winline.
Выбор другого исхода разрешён; рекомендованность не является условием записи.

Для ручной записи из матча без прогноза использовать тот же контракт ставки
с отсутствующими ссылками и явными исходными данными события. Нельзя разрешать
клиенту подменять snapshot существующего контекста. Для будущих рынков исходы
и правила задаются явно, без автоматического распространения NHL OT на футбол.

### Идемпотентность и исправления

При начале каждого подтверждаемого изменения ставки бот создаёт устойчивый request ID,
сохраняет его до отправки и повторяет при retry. Ключ уникален в области
владельца и операции; нормализованное тело имеет digest. Та же операция с тем
же ключом и телом возвращает сохранённый результат, даже если ставка уже
исправлена. Другое тело с тем же ключом возвращает conflict. Новый добор
обязательно получает новый ключ; сумма/матч/odds не являются ключом дедупликации.

Защита действует в БД, а не только в памяти Telegram FSM: unique constraint
и единая транзакция предотвращают два create при одновременных запросах.
Создание контекста карточки не идемпотентно: повторный POST может вернуть новый
context ID с тем же содержимым. Контекст не создаёт ставку, не является фактом
отправки сообщения и не участвует в финансовых суммах. Поэтому лишний контекст
после retry допустим в первом срезе. Идемпотентность обязательна для денежного
`POST /admin/bets` и последующих изменений ставки. При повторе денежного запроса
бот сохраняет исходные request ID и context ID: подмена контекста означает
изменение тела и должна привести к conflict.

Каждое исправление, settlement или отмена передаёт `expected_revision`.
Условное обновление текущей строки выполняется только при совпадении версии;
проигравший конкурентный запрос получает conflict и перечитывает запись.
Идемпотентный replay проверяется до проверки устаревшей expected revision.
История и response payload операции фиксируются в той же транзакции.

### Доступ и финансовый отчёт

Все пути чтения/записи журнала и контекста используют `require_bets_owner`,
который сначала выполняет `require_control_admin`, затем проверяет совпадение
principal с единственным явно настроенным владельцем `SF_BETS_OWNER_ID`.
Production-параметр `BET_OWNER_USER_ID` передаётся сервису как `SF_BETS_OWNER_ID`,
а боту как `BOT_BETS_OWNER_ID`. Пустая или некорректная настройка запрещает
доступ; другие control admins права на журнал не получают.
Principal берётся из проверенного заголовка, а не из JSON клиента. Каждый
запрос ограничен `owner_user_id=principal`, включая получение по ID, исправление,
audit и отчёт. Доступ к чужому ID не раскрывает существование записи.

Telegram проверяет allowlist и явного владельца на каждом шаге, выдаёт журнал только в личном
чате владельца, чтобы авторизованный пользователь не опубликовал финансы в
группе. Service credential остаётся только в secret file. Callback ID —
указатель, а не полномочие. Финансовые payload и audit не пишутся в обычный лог.

Миграция выдаёт необходимые права только control-роли: SELECT/INSERT контекстов
и audit, SELECT/INSERT/UPDATE текущих ставок. Public reader не получает SELECT
новых таблиц; runtime-роли не получают DELETE или изменение audit/контекстов.
Grants обновляются в `sports_forecast/deploy/database_roles.py`: существующий
bootstrap выполняет их migration identity после Alembic. При integer PK
новых таблиц выдать control-роли USAGE/SELECT только соответствующих sequences;
UUID PK этого не требуют. Добавление таблиц в Alembic без обновления bootstrap
недостаточно для работающего production API.
Проверить существующие default privileges: отсутствие явного GRANT само по себе
не доказывает запрет. Владение миграцией/DBA сохраняет возможность обслуживания.

Месяц — календарный месяц в `Europe/Moscow`, переводимый в полуоткрытые UTC
границы для `settled_at`. Граница букмекерских суток 08:00 применяется к выбору
матчей, а не к финансовому месяцу. Сводка строится по актуальным неотменённым
рассчитанным ставкам; исправление расчёта пересчитывает затронутые месяцы.
Формулы own money/freebet, ROI и hit rate берутся из REQ-031. Открытые записи
показываются отдельно; materialized финансовая проекция первому срезу не нужна.

## Последствия

- Старая карточка остаётся проверяемой после materialization и рестарта бота.
  Пользователь может внести добор без связи с новой рекомендацией.
- Растёт число сохранённых контекстов; объём для одного владельца мал.
  Retry создания карточки может оставить дополнительный неиспользуемый контекст.
  Автоматическое удаление контекстов и финансового audit в этот срез не входит.
- Потеря незавершённого FSM диалога допустима с повторным вводом, но подтверждённая
  запись и её ключ не должны теряться. После неопределённого ответа create
  нужно проверить сохранённый результат, прежде чем предлагать новую запись.
- Trusted bot передаёт Telegram principal через существующий control credential.
  Компрометация этого credential позволяет имитировать настроенного владельца;
  это существующая граница доверия control API, а не пользовательская подпись.
- Quote snapshot передаёт авторизованный бот. API проверяет форму данных и
  immutable prediction, но не аттестует Pinnacle цену независимо. Этот риск
  принят для одного доверенного бота; отдельная подпись публичного ответа или
  серверная генерация контекстов нужна при появлении недоверенных клиентов.
- Snapshot без observation ID доказывает сохранённое содержание карточки,
  но не происхождение полной исторической линии. В отчёте нельзя заявлять
  исторический CLV/качество рекомендации без необходимых наблюдений.

## Проверка и пересмотр

Разработка идёт небольшими TASK через red → green → refactor:

1. Миграция и create/read ставки с точными суммами: два добора сохраняются
   отдельно; replay, конкурентный create, чужой principal, другой control admin
   и отсутствие явной настройки владельца проверяются тестом.
2. Контекст и Telegram: карточка revision A сохраняется, витрина меняется на B,
   ставка из старой кнопки остаётся на A с прежней ценой; отсутствие revision/
   observation не создаёт фиктивной связи. Проверить рестарт и private chat,
   отклонение подменённой identity/probability и отсутствие live fetch в POST.
3. Settlement, исправление и отмена: win/loss/void для обоих типов средств,
   фактическая выплата с расхождением, конфликт revision и восстановимый audit.
4. Месячная сводка: пограничные timestamps МСК, открытые/отменённые записи,
   переход ставки между месяцами после исправления; сумма строк и разрезов
   совпадает с итогом. Провести сценарий от карточки до отчёта на fixture данных.

Проверить запреты ролей на PostgreSQL, а не выводить их из SQLite unit tests.
Перед выпуском требуется независимое review и обычные release gates проекта.
Новая функциональность добавляется отдельными таблицами и закрытыми путями;
существующие публичные consumers не должны требовать журнал.

Rollback приложения отключает команды/закрытые маршруты и оставляет данные.
После первых реальных ставок downgrade с удалением таблиц без отдельного
решения владельца запрещён. Новый ADR нужен при автоматическом settlement,
частичном cash-out, экспрессах, переносе архива котировок или нескольких
независимых владельцах с другим контуром аутентификации.

## Источники и неизвестное

- [REQ-031](../../product/requirements/REQ-031-real-bets-ledger.md): подтверждённые
  правила Winline/freebet и границы первого среза; внешний API Winline не нужен.
- `sports_forecast/service/db/models.py`: `Prediction`, `PredictionRevision`.
- `sports_forecast/service/db/engine.py`: отдельное control-соединение.
- `sports_forecast/service/control_auth.py`: проверка credential и principal.
- `sports_forecast/deploy/database_roles.py`: подтверждённые текущие runtime
  grants; control не читает predictions, reader не читает prediction_revisions.
- `sports_forecast/service/routers/predictions.py` и
  `sports_forecast/service/live_odds_enrichment.py`: публичный read path и live линия.
- [ADR-031 исторической линии](ADR-031-historical-odds.md): отдельный контракт
  исторических наблюдений. Номер ADR уже используется; ссылки на эти два
  решения должны содержать полное имя файла.
- Точные имена таблиц и схемы payload определяет Developer в TASK с сохранением
  перечисленных инвариантов. Авторизация и пользовательские финансовые правила
  не требуют дополнительных подтверждений в пределах принятого REQ.
