# ADR-035 — Словари registry и вычисляемое сопоставление матчей

> **Статус:** proposed
> **Дата:** 2026-10-11
> **Связанное требование:** [REQ-026](../../product/requirements/REQ-026-entity-registry.md)
> **Инициатива:** [EPIC-026](../../backlog/EPIC-026-entity-registry.md)
> **Заменяет после принятия:** части [ADR-029](ADR-029-local-entity-registry-and-snapshots.md), требующие проектных событий в owner registry и event mappings для использования котировок; доставка снимков и локальное владение сохраняются.

## Контекст и критерии выбора

Владелец уточнил назначение registry: редактируемые через веб-интерфейс словари
турниров, команд, рынков и исходов с обозначениями по источникам; в будущем —
игроков с учётом принадлежности командам во времени. Обычный матч сопоставляется
автоматически по подтверждённым командам и допустимому расхождению времени.
Отдельное постоянное подтверждение пары ID каждого матча не требуется.
Для NHL владелец подтвердил автоматический допуск до 15 минут включительно.

Сейчас `EntityKind` содержит `tournament/team/event/player`; рынки описаны в
конфигурации букмекера. `RegistryEventResolver` сначала ищет подтверждённый
event ID, затем проектное событие по точному UTC. Оба потребителя котировок
используют project event projection. Поэтому одной настройки допуска
недостаточно: отсутствие project event всё ещё блокирует котировку.

ADR необходим, поскольку меняются ответственность реестра, состав снимка,
основания присоединения котировок и требования к воспроизводимости. Критерии:
новые матчи известных команд не требуют публикации registry; ошибка не
присоединяет чужие коэффициенты; история прогнозов и ставок сохраняется;
переход обратим без удаления существующих данных и новых сервисов.

## Рассмотренные варианты

| Вариант | Простота и проверка | Риски, эксплуатация и стоимость | Обратимость |
|---|---|---|---|
| Status quo: event registry и явные связи либо импорт событий | Текущие контракты уже реализованы; хорошие проверки ссылок | Публикация каждого нового календаря, дублирование источника расписания, ручные решения при расхождении часов; не выполняет уточнённое назначение | Сохраняется как прежняя реализация для отката |
| Словари плюс вычисляемое сопоставление при загрузке котировок | Один общий matcher, проверяемые входы и причины отказа; выбран | Нужно учитывать переносы, дубликаты и полноту выборки; воспроизводимость требует версий входов | Добавочное изменение схемы, старые данные и снимки сохраняются |
| Словари плюс автоматически пополняемый постоянный cache пар event ID | Ускоряет повторное соединение и переносы при стабильном ID | Второй источник истины, правила устаревания и конфликтов, риск применения прежней пары после исправления источника | Возможен позже как пересоздаваемый cache, сейчас не нужен |

Все варианты используют существующие локальное хранилище, PostgreSQL и sync.
Новый сервис не требуется. Для выбранного варианта безопасность определяется
подтверждёнными обозначениями и отказом при неоднозначности, а стоимость
сопровождения переносится с ежедневного ведения матчей на общий алгоритм.
Замеров производительности нового matcher ещё нет.

## Решение

### Словари и спортивный календарь

Registry владеет ID, именами, обозначениями источников, интервалами действия,
решениями и конфликтами для `tournament/team/market/outcome`, в будущем `player`.
Рынок описывает период, включение овертайма/буллитов, допустимые исходы и параметры
линии. Внешнее `h2h` разрешается с учётом спорта, турнира и букмекера; одно имя
без этого контекста не доказывает одинаковую семантику. Исход разрешается внутри
рынка; обозначение команды в исходе сначала проходит словарь команд.
Число линии тотала является параметром котировки, отдельная сущность registry
для каждого числа не нужна.

Игрок имеет стабильный ID, независимый от текущей команды. Интервальная связь
`player_id/team_id/valid_from/valid_until` позволяет разрешать одинаковые имена
и переходы. Вводить составы и workflow игроков в первый NHL срез не требуется.

Операционный календарь остаётся владельцем конкретных матчей. Существующие
`canonical_events.id`, ключ спортивного источника, ссылки прогнозов, ставок и
котировок сохраняются. Отказ от event registry не означает удаление матчей из
БД или отказ от связи уже сохранённой котировки с календарной записью.

### Вычисляемая связь

Оба потребителя котировок используют один контракт сопоставления:

1. Закрепить версию словарей, политики и наблюдаемую версию календаря на запуск.
   Разрешить турнир и обе команды по подтверждённым обозначениям источников.
2. Требовать совпадение турнира и ролей home/away, известные timestamps UTC;
   отсутствующее время и перестановка сторон не исправляются молча.
3. Для NHL отобрать календарные события с абсолютной разницей стартов
   не более 15 минут. Другие турниры получают явную политику; широкое legacy
   окно 360 минут не наследуется автоматически.
4. Разрешить пару только при взаимной уникальности: один подходящий матч для
   события провайдера и один distinct event провайдера для матча в данном
   источнике и срезе времени. Повторные snapshots одного source ID не являются
   отдельными матчами; несколько букмекеров также не создают такой конфликт.
   Ближайший из нескольких кандидатов не выбирается.
5. Проверить соответствие рынка, исходов и участников до присоединения цены.
   Неизвестность или конфликт дают явную причину отказа и кандидата на проверку.

Календарная выборка должна охватывать всё окно допуска, включая соседнюю дату.
Нельзя доказывать уникальность только внутри текущей страницы API или списка
прогнозов, если другие календарные кандидаты были отфильтрованы раньше.
Неоднозначные случаи попадают владельцу на диагностику и исправление словаря
либо исходных данных; ручное решение не создаёт постоянный обход matcher по
event ID. Если исправление невозможно, котировка остаётся неприсоединённой.

### Происхождение и повторяемость

Source event ID сохраняется в наблюдениях котировок вместе с источником,
provider time, observed time, выбранным canonical ID, версией словарей,
политикой сопоставления и основанием результата. Это след выполненного расчёта,
а не owner-справочник постоянных разрешений. Нужные для воспроизведения значения
участников и времени календаря закрепляются revision либо минимальным снимком
входов; ссылаться только на изменяемое текущее расписание недостаточно.

Удалять source IDs нельзя: иначе теряются дедупликация, поиск исходной котировки
и объяснение исторического решения. При переносе матча новое наблюдение проходит
matcher заново; прошлая привязка не даёт ему автоматический пропуск. Историческая
котировка и принятое по ней решение не переписываются после нового расписания.

### Минимальная миграция и выпуск

1. Расширить domain/snapshot/UI словарями рынков и исходов. Перенести применяемые
   NHL/Pinnacle правила из конфигурации с явным происхождением и сверкой смысла.
   Новая семантика снимка получает версию, которую старый reader явно отклоняет;
   недопустимо молча трактовать новый пакет по старым правилам.
2. Добавить общий matcher и заменить зависимость NHL runtime от project event
   projection на словари и календарь. Проверить оба пути: live inference и
   materialization будущих котировок. Неизвестные словарные обозначения идут
   через существующую очередь; её PostgreSQL grants исправляются отдельно.
3. Обновить gates установки и readiness: полнота event registry больше не
   является условием. Вместо неё проверить словари и реальное присоединение
   котировок на календаре. Старые event relations/mappings оставить читаемыми
   для прежних снимков и истории, исключив из обязательного нового runtime.
4. На сохранённом реальном batch проверить шесть случаев расхождения +10 минут
   без ручных event links; на свежих данных — полный цикл до API и бота.
   Проверить очередь неизвестного обозначения и публикацию решения владельца.
   Затем review, CI, production handoff, backup/restore и release gates.
5. Выпустить новую версию и переключить reader после gates. До этого production
   остаётся v1.3.1. Откат возвращает прежний выпуск и совместимый snapshot;
   автоматический fallback на YAML в новом строгом режиме не допускается.
   Удаление старых таблиц, событий и legacy-кода — отдельная последующая задача.

## Последствия

- Новые матчи известных участников обрабатываются без локального создания
  event UUID и ежедневной публикации связей событий.
- При переносе за пределы 15 минут линия временно останется missing, пока
  источники не согласуют расписание. Это ожидаемая цена ограниченного допуска.
- Повторные матчи, дубликаты и неполная календарная выборка создают риск ложной
  уникальности; обязательны полная выборка окна и отказ при нескольких кандидатах.
- Потеря устойчивой межисточниковой event identity осложнит будущие объединения
  большого числа расписаний. Для текущего одного primary calendar такая сущность
  не нужна; её повторное введение потребует отдельной бизнес-потребности.
- История event registry сохраняется при переходе. Старые потребители, snapshot
  validator, импорт обучения и исторический backtest требуют явной проверки
  совместимости; переключать формат до поддержки нового reader нельзя.

## Проверка и пересмотр

Проверить границы 0/10/15/больше 15 минут, разные турниры, обратные стороны,
повторные матчи, несколько provider IDs, повторные наблюдения одного ID,
отсутствующее время, смену даты UTC, перенос календаря, неизвестные и конфликтные
обозначения, рынки с ничьей и без неё, неверный период/OT и неверный исход.
Проверить повторяемость исторического решения после изменения расписания и
алиасов, а также откат без удаления данных. Тесты и серверные gates в рамках
этого ADR не выполнялись: документ задаёт план.

Пересмотр нужен при регулярно пропускаемых корректных матчах за пределами окна,
нескольких primary calendars, необходимости устойчивой межисточниковой истории
события или измеренной стоимости повторного matching. Эти сигналы не разрешают
самостоятельно расширять допуск либо использовать event cache как подтверждение.

## Источники и неизвестное

- Подтверждение владельца 2026-10-11: словари вместо постоянных event links,
  будущие игроки, автоматический NHL допуск 15 минут; отражено в REQ-026.
- Локальные первичные источники текущего контракта:
  `sports_forecast/identity/registry.py`, `identity/events.py`,
  `identity/installation.py`, `data/providers/odds/live_nhl_pinnacle.py`,
  `orchestration/future_odds.py`, `conf/bookmaker/the_odds_api.yaml`.
- Конкретный новый формат snapshot и перечень исторических потребителей нужно
  определить в TASK перед реализацией. Новые свойства библиотек или внешних API
  для выбора этого решения не предполагаются.
