# ADR-040 — Две стратегии для одного футбольного рынка 1X2

> **Статус:** proposed
> **Дата:** 2026-10-12
> **Связанное требование:** [REQ-040](../../product/requirements/REQ-040-club-football-platform-e2e.md)
> **Инициатива:** [EPIC-040](../../backlog/EPIC-040-club-football-platform-e2e.md)

## Контекст и критерии выбора

Исходный клубный пул содержит девять соревнований. Пользователь запросил два
кандидата одного рынка `winner` 1X2: независимые П1/П2 на long-строках с
проверкой остатка `1 − П1 − П2` для ничьей и прямое 1X2 на wide-строках.
Нынешний `winner` считает бинарный таргет в long-формате,
`Trainer` берёт только `predict_proba[:, 1]`, а `materialize` нормализует две
вероятности до единицы. Такая нормировка скрывает возможность ничьей.

Требуется локальный E2E без изменения работающего NHL-контракта, с проверкой
утечки, разделения во времени, всех исходов и тестовой выдачи. Состав пула
должен оставаться одним конфигурационным профилем, а не девятью независимыми
модельными пайплайнами.

## Рассмотренные варианты

1. **Status quo — один бинарный `winner`.** Минимум кода, но ничья становится
   отрицательным классом одновременно для обеих сторон, а materialize нормализует
   П1 и П2. Не выполняет сравнение двух подходов и искажает смысл первой модели.
2. **Один 1X2 market-spec и две стратегии модели (предлагается).** Long-кандидат
   сохраняет два независимых шанса победы и проверяет остаток для ничьей;
   wide-кандидат выдаёт три класса `home_win/draw/away_win` напрямую. Обе модели
   имеют отдельные identity и метрики, но
   используют один источник и одну конфигурацию состава соревнований. Потребуются
   изменения Trainer, materialize и карточки бота; NHL сохраняет прежний контракт.
3. **Три независимые бинарные модели для 1X2.** Можно переиспользовать текущую
   бинарную оценку, но три числа не образуют распределение без дополнительной
   нормализации и калибровки. Три артефакта повышают стоимость сопровождения.

## Решение

Для этой инициативы предлагается вариант 2. Один `market_spec` объявляет правила
1X2. Long-стратегия сохраняет два `P(win)` без нормировки до единицы и выводит
`P(draw)` остатком. Если остаток отрицателен или нечисловой, конкретный прогноз
не проходит gate публикации; доля таких случаев фиксируется в отчёте. Wide-
стратегия использует трёхклассовый target по итоговому счёту.
Классы wide-модели сопоставляются с исходами по сохранённому списку `classes_`, а не
по позиции, предполагаемой из training sample. NHL `winner_withOT` сохраняет
двухисходную нормировку. В двух отчётах сохраняются resolved Hydra-конфигурация,
snapshot fingerprint, временные границы, состав фичей и вероятностные метрики.
Для 1X2 конфигурация рынка явно отключает действующие бинарные калибровку и
BettingSimulator; трёхклассовые logloss, accuracy и Brier считаются по полному
распределению. TSCV останавливается, если ранний fold ещё не содержит все три
исхода. Отсутствующие AUC/ECE не записываются нулями как успешные метрики.

Локальный E2E использует один каталог состава пула. Реальные upcoming-события
запрашиваются у Smart Tables и закрепляются отдельным timestamped snapshot;
исходы завершённых матчей не входят в этот вход. Прогнозы пишутся в отдельную
локальную БД; API и бот читают её в тестовом окружении. Production pointer,
расписание и получатели остаются вне инициативы.

Для UCL/UEL входной счёт трактуется как результат основного времени только при
совпадении `home_score_ft`/`away_score_ft` с `*_goals_all` и суммой `*_goals_1h`
и `*_goals_2h`. Незавершённые, технические, неполные и противоречивые записи
исключаются при ingest. Этот контракт проверяется при каждом обновлении CSV;
официальные матчи с дополнительным временем и пенальти служат выборочной
проверкой семантики источника. Незаполненные `stage`/`round` не позволяют
надёжно выделить плей-офф только по этим полям.

## Последствия

- Положительные: два подхода сравнимы на одном пуле; 1X2 представляет ничью
  честно; NHL-контракт сохраняется.
- Отрицательные и стоимость: потребуется поддерживать два типа классификации,
  отдельные model identity при одном рынке и явно тестировать отрицательный
  остаток, class order, метрики, калибровку и сериализацию прогноза.
- Безопасность и эксплуатация: replay работает в изолированном локальном
  окружении; отсутствие предматчевого snapshot или неполная тройка вероятностей
  блокируют публикацию. Ручное promotion в production данным ADR не разрешено.

## Проверка и пересмотр

Тесты должны показать три исхода обеих стратегий, отрицательный остаток как
отказ публикации, сумму валидных вероятностей, временной holdout,
отсутствие текущих post-event полей в признаках, сохранение и повторное чтение
одного прогноза через API и карточку бота. Отдельно проверяется сохранение
бинарного NHL-контракта. Решение пересматривается при доказанной несовместимости
общего пула по турнирам или необходимости независимых моделей для частей пула.
