# ADR-014 — Версионируемый контракт каталога исследованных API

> **Статус:** accepted
> **Дата:** 2026-08-25
> **Связанное требование:** [REQ-014](../../product/requirements/REQ-014-research-api-catalog.md)

## Контекст и критерии выбора

REQ-014 требует результата Data Researcher, с которым можно работать без чата и без
догадок о внешней схеме. Текущий `DataSourceRecord` содержит лишь строки endpoint'ов и
полей. Он не позволяет проверить тип, JSON path, ключ, nullable, доказательство или момент
появления значения; следовательно, не может предотвращать leakage и не является контрактом
для engineering.

Критерии: машиночитаемость, строгая validation, provenance каждого наблюдения, понятный
scientist data dictionary, отсутствие raw payload/credentials и обратимость при изменении
неофициального API.

## Рассмотренные варианты

1. **Status quo: строки в `DataSourceRecord` и prose в `docs/`.** Дешёв, но не связывает
   поле с методом и временем доступности; машинная проверка и безопасный handoff невозможны.
2. **Свободный JSON каждого провайдера.** Позволяет быстро записать наблюдение, но не даёт
   единой validation, поиска и тестов; scientist снова вынужден трактовать произвольную
   структуру.
3. **Версионируемые typed records `endpoint → parameter → field` в Data Source Catalog и
   генерируемый/поддерживаемый data dictionary.** Даёт строгий минимум общих метаданных,
   сохранение source-specific semantics и локальное хранение безопасного summaries.

## Решение

Выбран вариант 3. `DataSourceRecord` получает обязательный структурированный каталог для
исследований уровня `complete`: endpoint record с HTTP-методом, путём, параметрами,
ответом/пагинацией/access и evidence; field record с entity, JSON path, типом, nullable,
семантикой, ключами, temporal availability, leakage risk и доказательством. Карточка имеет
версию схемы, `last_verified` и уровень полноты (`partial` / `complete`).

Легаси-карточки сохраняют прежние сводные строковые поля и помечаются `partial`; новый
`complete`-каталог валидируется строго. Человекочитаемый Markdown dictionary в `docs/research/`
ссылается на идентификаторы записей, но не заменяет JSON-контракт. Неподтверждённые поля и
недоступные методы записываются с уровнем evidence/ограничением, без схемы, выведенной из
догадки. Полные HTTP-ответы, cookies, HAR и секреты не сохраняются.

## Последствия

- Положительные: scientist и engineer получают проверяемый field-level contract; тесты могут
  отвергать неполные complete-карточки; temporal risk становится явным.
- Отрицательные и стоимость: исследование двух API требует значительного документирования и
  повторной проверки при изменении внешней схемы; часть старых карточек останется partial.
- Безопасность и эксплуатация: каталог не содержит credentials/raw payload и не разрешает
  запросы или массовый ingestion; доступ к источникам остаётся отдельной инженерной задачей.

## Проверка и пересмотр

Выбор подтверждают negative tests incomplete complete-карточки и две заполненные карточки
NHL/Smart Tables, где любое поле можно проследить до endpoint и evidence. Пересмотр нужен,
если появится официальный versioned OpenAPI либо один source потребует структуры, которую
невозможно выразить через entity/path/type/temporal metadata. Миграция обратима: JSON-card
версионируется и старые `partial` записи остаются читаемыми.

## Источники и неизвестное

- Локальная зафиксированная разведка: [NHL Web API](../../cursor/source_data/nhl_web_api.md)
  и [Smart Tables](../../cursor/source_data/smart_tables.md); это наблюдения, а не
  официальный стабильный контракт.
- Официального versioned API contract для обоих источников на момент решения не зафиксировано;
  конкретные методы и поля повторно верифицируются отдельными задачами.
