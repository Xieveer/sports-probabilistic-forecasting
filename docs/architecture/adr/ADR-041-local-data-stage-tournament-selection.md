# ADR-041 — Состав локального data stage и расписание legacy DAG

> **Статус:** proposed
> **Дата:** 2026-10-12
> **Связанное требование:** [REQ-040](../../product/requirements/REQ-040-club-football-platform-e2e.md)
> **Инициатива:** [EPIC-040](../../backlog/EPIC-040-club-football-platform-e2e.md)

## Контекст и критерии выбора

`dvc.yaml` перечислял девять турниров в команде features и пропускал новый
`football_top_leagues`, хотя ingest и clean уже создают его interim-данные.
Отдельный legacy Airflow `data_refresh` имел четырёхчасовое расписание со своим
списком, параллельно с `portfolio_refresh`, который строит задачи из каталога.
В production действует systemd и Worker, без Airflow и DVC. Нужен локальный
воспроизводимый граф без второго списка и без двух плановых Airflow data refresh.

## Рассмотренные варианты

1. **Сохранить статические списки.** Нет миграции, но добавление турнира требует
   правки нескольких мест, а клубный пул не обрабатывается `dvc repro`.
2. **Строить features для всех фактически подготовленных interim-турниров;
   legacy DAG оставить только для ручного запуска.** Один локальный DVC stage
   продолжает использовать тот же Hydra и feature pipeline. Новый турнир с
   валидным interim и конфигом автоматически попадает в features. Airflow
   `portfolio_refresh` остаётся единственным плановым общим DAG.
3. **Удалить DVC и legacy Airflow полностью.** Меньше инструментов, но ломает
   локальный граф и ручной диагностический путь без доказательства отсутствия
   потребителей. Для текущей задачи цена миграции выше пользы.

## Решение

Выбран вариант 2. DVC features stage вызывает небольшой CLI, который находит
`matches_interim.parquet` и требует для каждого каталога конфиг
`conf/tournament/<name>.yaml`. Он строит Hydra-конфигурацию и вызывает
существующий feature builder; неизвестный турнир и пустой набор останавливают
stage. `data/interim/` и каталог конфигов входят в зависимости DVC.
Legacy `data_refresh` сохраняет ручной запуск с явным списком, но его
`schedule=None`. Новое плановое включение делается через deployment profile
и проверку production gates, а не через этот DAG.

## Последствия

- Положительные: клубный пул и последующие подготовленные турниры не требуют
  правки списка в DVC; одинаковые interim-данные приводят к одинаковому составу
  features; два общих Airflow расписания не конкурируют.
- Отрицательные и стоимость: локальный features stage обрабатывает все готовые
  interim-каталоги, поэтому его время зависит от их числа. Для выборочного
  запуска остаётся исходный CLI одного турнира.
- Безопасность и эксплуатация: production граф не меняется; ручной legacy DAG
  больше не стартует по расписанию. Неподготовленный каталог не включается сам.

## Проверка и пересмотр

Тесты проверяют автообнаружение, отсутствие конфига и отсутствие расписания
legacy DAG. Hydra-конфигурация составляется для всех реально присутствующих
interim-турниров; `dvc dag` должен сохранять цепь ingest → clean → features →
validate. Если появится требование планово обрабатывать турниры без локального
interim, нужен явный каталог источников и отдельное решение о запуске.
