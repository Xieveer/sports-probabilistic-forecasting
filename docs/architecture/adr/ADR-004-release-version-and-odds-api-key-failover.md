# ADR-004 — Версия поставки и отказоустойчивый выбор ключа The Odds API

> **Статус:** accepted
> **Дата:** 2026-08-08
> **Связанное требование:** [REQ-004](../../product/requirements/REQ-004-nhl-readiness-and-release-versioning.md)

## Контекст и критерии выбора

[REQ-004](../../product/requirements/REQ-004-nhl-readiness-and-release-versioning.md)
требует подготовить NHL-контур к production и выпустить первую поставку как
`1.0.0` в приложении/API, Git-теге и Docker-образах. Сейчас номер пакета в
`pyproject.toml` — `0.1.0`, а FastAPI объявляет независимый `2.0.0`. Клиент
The Odds API принимает ровно один `ODDS_API_KEY`; cache и логирование уже не
включают ключ в имя файла или query-логи.

Нужно ввести три ключа с приоритетом free → 20k → 100k, но не расходовать
платный ключ при сетевой ошибке, ошибке схемы либо другой ошибке, не доказывающей
исчерпание квоты. У The Odds API quota-headers содержат остаток и расход, а
`429` определён как rate limiting; исторические odds являются отдельным endpoint
и зависят от тарифа. Критерии: одна версия поставки, проверяемое переключение,
отсутствие секретов в логах, обратимость и минимальное изменение существующих
Airflow/API/batch границ.

## Рассмотренные варианты

1. **Status quo: независимые литеральные версии и один `ODDS_API_KEY`.**

   Не требует миграции, но даёт противоречивую версию поставки и не выполняет
   согласованную политику расходования трёх квот.

2. **Три ключа выбираются shell/CI до старта каждого процесса.**

   Код проще, но shell не видит response headers и не может безопасно отличить
   исчерпанную квоту от временной ошибки. Логика разъедется между локальным
   запуском, worker и Airflow.

3. **Единый источник версии в package metadata и узкий key-ring в существующем
   клиенте The Odds API.**

   Версия читается из установленного metadata пакета приложением; CI принимает
   релизный Git-тег только при совпадении с `pyproject.toml` и публикует образы
   с тем же immutable SemVer-тегом. Key-ring получает три именованные переменные
   окружения, пробует ключи по порядку и переключается только по явному
   quota/rate-limit сигналу. Он сохраняет существующий одноключевой
   `ODDS_API_KEY` как временный fallback для обратной совместимости. Выбран.

## Решение

1. `pyproject.toml` — единственный исходник release version. Application/API
   читает её через `importlib.metadata`; литерал версии FastAPI удаляется.
   Первый подготовленный production-релиз получает `1.0.0`.
2. Release workflow принимает annotated Git-тег `v<version>` только если он
   совпадает с package metadata, и публикует каждый сервисный Docker-образ как
   минимум с тегом `<version>` и traceable SHA-тегом. Создание Git-тега и
   публикация образа остаются отдельной явно авторизуемой release-операцией.
3. Вводятся `ODDS_API_KEY_FREE`, `ODDS_API_KEY_20K` и `ODDS_API_KEY_100K`.
   Key-ring исключает пустые и повторяющиеся значения, выбирает первый
   работоспособный ключ в заданном порядке и передаёт в HTTP-клиент только
   активный ключ.
4. Переход к следующему ключу разрешён, когда ответ явно обозначает истощение
   quota/rate-limit: `429` либо ответ с zero remaining quota. Ошибки сети,
   таймаут, `5xx`, некорректный JSON, `4xx` авторизации/параметров и отсутствие
   заголовка не вызывают перехода. В таком случае операция завершается ошибкой
   текущего ключа, не тратя следующий.
5. При первом запуске с новыми переменными legacy `ODDS_API_KEY` используется
   лишь если все три новые пусты; одновременная конфигурация предпочитает
   key-ring и остаётся наблюдаемой по имени tier, но никогда по значению ключа.
6. NHL readiness оформляется отдельной воспроизводимой операционной командой:
   refresh/quality gate, historical odds backfill и проверка будущего расписания
   дают структурированное краткое доказательство. Отсутствующее расписание —
   штатный `no_upcoming_schedule`; отсутствие исторических данных или прав
   тарифа отражается отдельно, без фиктивных данных.

## Последствия

- Положительные: одна наблюдаемая версия; образы можно однозначно связать с
  тегом и исходным кодом; бесплатная квота используется прежде платной;
  ошибочные переключения и утечка секрета покрываются тестами.
- Отрицательные и стоимость: обновляются все runtime-потребители env, Docker
  CI и документация; поведение `429` меняется с текущего blind retry на
  контролируемое решение key-ring. Требуется тестировать response headers
  на fixtures, а не реальными ключами.
- Безопасность и эксплуатация: ключи допускаются только в secret store/`.env`
  вне Git. Логи содержат tier, HTTP status и quota counters, но не URL query,
  тело ответа или секрет. Аварийный откат — оставить только legacy ключ либо
  очистить новые переменные: клиент вернётся к совместимому пути.
- Ограничение: API не предоставляет надёжного сигнала, что paid key имеет
  требуемый конкретный тариф; порядок определяется конфигурацией владельца.
  Если у ключа нет доступа к историческому endpoint (`401/403`), он не должен
  автоматически сжигать следующий ключ без явной будущей политики.

## Проверка и пересмотр

- Unit-тесты key-ring: порядок, пустые/дублированные ключи, `429`, нулевой
  quota-header, network/`5xx`/`401` без failover, отсутствие всех ключей и
  отсутствие секрета в exception/log records.
- Contract-тесты: FastAPI и metadata возвращают `1.0.0`; release workflow
  отвергает несовпадающий Git-тег и формирует version/SHA Docker-теги.
- NHL smoke: в отдельном запуске с предоставленными владельцем secret variables
  зафиксированы source refresh/gate, число найденных historical odds и статус
  будущего расписания. В тестах внешняя сеть не используется.
- Пересмотреть решение при появлении гарантированного quota-management API,
  общего пула ключей между несколькими hosts или необходимости продолжать
  backfill после `401/403`: тогда нужен персистентный budget store и явно
  согласованная политика тарифных ошибок.

## Источники и неизвестное

- [The Odds API v4: response headers и quota](https://the-odds-api.com/liveapi/guides/v4/#response-headers)
  — документирует `x-requests-remaining`, `x-requests-used` и стоимость вызова.
- [The Odds API v4: historical odds](https://the-odds-api.com/liveapi/guides/v4/#get-historical-odds)
  — отдельный исторический endpoint и его параметры.
- [The Odds API v4: rate limiting](https://the-odds-api.com/liveapi/guides/v4/#rate-limiting-status-code-429)
  — код `429` для rate limit.
- [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) — формат
  `MAJOR.MINOR.PATCH`.
- Не подтверждены владельцем фактические права каждого ключа и доступность
  historical odds за нужный период; это проверяется только безопасным NHL smoke
  после передачи секретов в окружение выполнения.
