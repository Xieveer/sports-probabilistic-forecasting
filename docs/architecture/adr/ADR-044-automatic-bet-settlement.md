# ADR-044 — Расчёт фактических ставок после canonical import

> **Статус:** accepted
> **Дата:** 2026-10-31
> **Требование:** [REQ-044](../../product/requirements/REQ-044-automatic-bet-settlement-and-season-report.md)
> **Инициатива:** [EPIC-044](../../backlog/EPIC-044-bets-cycle-report.md)

## Контекст

Журнал фактических ставок хранит ручной расчёт и audit. Canonical import уже
сохраняет завершённость матча и исходный счёт. Data Cycle запускается одним
host timer. Требуется рассчитать только однозначные открытые ставки и отдельно
сообщить владельцу о результате конкретного цикла.

## Решение

После canonical import тот же одноразовый Worker запускает расчёт открытых
ставок. Правило исхода задаётся явно для пары вид спорта/рынок. Первая
поддержанная пара — NHL `winner_withOT`: полный счёт включает ОТ и буллиты.
Рынки с неизвестным правилом, отсутствие результата, равный счёт и отменённый
матч оставляют ставку открытой с причиной. Void не выводится из спортивного
результата. Обновление ставки, audit и запись сводки доставки выполняются в
одной транзакции. Доступ Worker к журналу ограничен SELECT, нужными UPDATE
полями и INSERT audit/outbox.

Существующий notification outbox получает тип сообщения и короткий JSON
сводки; доставка по прежнему lease/retry протоколу. Сообщение получают только
личные адреса владельца. Отправка в Telegram имеет семантику at least once:
сбой после фактической отправки и до подтверждения lease может повторить
сообщение. Разделение terminal и bet-summary сообщений не позволяет потерять
второе из-за подтверждения первого.

Начало отчётного сезона хранится в конфигурации турнира. API считает итог по
фактическим `settled_at` в МСК и отдаёт точки накопленного общего денежного
PnL; бот строит PNG. Месячный отчёт и ручное исправление сохраняются.

## Альтернативы

- Расчёт в Telegram polling привязал бы изменение журнала к доступности бота
  и создал бы гонку между доставкой и записью результата.
- Отдельный scheduler или сервис добавил бы второй путь запуска и наблюдения
  без потребности в масштабировании.
- Один outbox item на два сообщения терял бы идемпотентность подтверждения.

## Проверка

Проверить повторный цикл, частичный/неоднозначный canonical результат,
ручное исправление, audit и отдельную доставку после ошибки. До выпуска
выполнить миграцию, backup, review и production smoke.
