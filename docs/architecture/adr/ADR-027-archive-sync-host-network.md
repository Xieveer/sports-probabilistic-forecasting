# ADR-027 — Сеть хоста для production archive-sync

> **Статус:** accepted
> **Дата:** 2026-09-30
> **Связанное требование:** [REQ-025](../../product/requirements/REQ-025-bot-schedule-readiness.md)
> **Инициатива:** [EPIC-025](../../backlog/EPIC-025-bot-schedule-readiness.md)
> **Реализация и проверка:** [TASK-025-32](../../backlog/tasks/TASK-025-32-archive-sync-host-network.md)

## Контекст и критерии выбора

Production v1.2.11 публикует прогнозы, но стадия `archive_sync` не завершает
TLS handshake с Object Storage. Согласно операционной диагностике от
2026-09-30, повторные запуски штатного контейнера через Docker bridge
получают timeout даже при отправке manifest размером 686 байт. TCP connect
проходит, ClientHello выходит через интерфейс хоста, но TLS response до
таймаута не приходит. Снижение MSS до 1200 и 1000 не помогло.

Тот же образ с сетью хоста завершил TLS handshake за 0,12 с. Host S3 client
записал manifest и файл матчей размером 49 717 759 байт; скачивание последнего
и SHA-256 подтвердили совпадение. Эти наблюдения подтверждают рабочий путь
через сеть хоста, но ещё не подтверждают полный штатный sync обоих архивов
и не доказывают конкретную причину сбоя bridge.

Критерии выбора: завершение штатного Data Cycle, минимальная область
воздействия, сохранение формата архива и durable state, проверяемость на
существующих artifacts, ограничение дополнительных сетевых полномочий,
простой откат без изменения данных. Production работает на Linux Docker
Engine. `archive-sync` — одноразовый S3-клиент без входящего сервера,
Compose DNS зависимостей и DB credentials.

ADR необходим: меняется граница сетевой изоляции production-компонента.
Малый размер Compose diff не делает это обычным локальным исправлением.

## Рассмотренные варианты

| Вариант | Простота, проверка и эксплуатация | Безопасность, стоимость, переносимость и откат |
| --- | --- | --- |
| Status quo: bridge и повтор запуска | Не требует изменений; повтор уже воспроизводит TLS timeout. Не выполняет критерий завершения цикла. Увеличение timeout не обосновано наблюдениями. | Сохраняет изоляцию и переносимость; стоимость повторных неуспешных циклов, архивы остаются локально. Откат не нужен. |
| Исправить forwarding/NAT/firewall или MTU bridge | Потенциально устраняет первопричину и сохраняет топологию. Нужны дополнительная диагностика и доказательство конкретного исправления; MSS эксперименты результата не дали. | Сохраняет сетевую изоляцию, но системное изменение может затронуть другие контейнеры. Срок и стоимость исследования неизвестны; откат зависит от найденного изменения. Переносимость приложения сохраняется. |
| Только archive-sync перевести на host network | Малый Compose diff, тот же образ и команда. Работоспособность TLS подтверждена; полный sync проверяется отдельно. Не добавляет сервис или новый способ отправки архива. | Ослабляет сетевую изоляцию только одноразового клиента. Требует Linux host networking, теряет Compose DNS для этого сервиса. Откат — возврат Compose; стоимость сопровождения — документированное исключение. |

## Решение

Выбрать `network_mode: host` только для `archive-sync` в production Compose
как ограниченный обход подтверждённого сбоя сетевого пути. Не объявлять
первопричину bridge исправленной. Остальные сервисы сохраняют свои сети.

Контракт сервиса:

- Нет `ports`, `networks`, `privileged`, host PID/IPC или Docker socket.
- Сохраняются immutable image, штатная команда и профиль, UID/GID `10001`,
  read-only rootfs, архив read-only, отдельный writable sync-state, tmpfs,
  CPU/memory limits и только существующие Object Storage secrets.
- `cap_drop: [ALL]` и `security_opt: [no-new-privileges:true]` ограничивают
  полномочия клиента в общей сетевой среде; их совместимость подтверждается
  штатным sync. Сетевые capabilities для обычного HTTPS-клиента не нужны.
- Endpoint остаётся HTTPS; проверка TLS не отключается. DB grants,
  credentials и Object Storage permissions не расширяются.
- Durable state переводит в `verified` только штатный процесс после
  проверки remote content. Ручная диагностическая запись не заменяет sync.

Минимальный план реализации: зафиксировать регрессионный контракт Compose,
изменить только конфигурацию сервиса, обновить runbook/handoff и пройти
независимое review и применимые release gates. Operations Agent применяет
конфигурацию и принимает результат по runtime evidence.

## Последствия

- Положительные: проверенный сетевой путь без нового daemon, proxy,
  зависимости или альтернативного S3 uploader; приложение продолжает
  использовать существующие архивы, ownership/fencing и проверки содержимого.
- Отрицательные и стоимость: причина bridge остаётся неизвестной; решение
  привязано к поддержке host networking. При будущей зависимости от Compose
  DNS или входящих портов контракт потребуется пересмотреть.
- Безопасность: контейнер получает доступ к loopback-службам хоста и общий
  namespace портов; возможный listener станет listener хоста. Отсутствие
  `ports` само по себе не является защитой в host mode. Bridge firewall
  ограничения могут больше не применяться. Non-root, отсутствие capabilities
  и запрет повышения привилегий уменьшают последствия компрометации, но
  не восстанавливают сетевую изоляцию. Перед запуском необходимо проверить
  доступные локальные службы и применимые host firewall правила; listener
  или доверие локального API только по loopback требуют отдельной оценки.
- Эксплуатация: запускается только штатный одноразовый клиент, без перезапуска
  API, бота, БД, Docker daemon или изменения общей bridge сети.

## Проверка и пересмотр

1. Адресный тест проверяет host mode только у `archive-sync`, отсутствие
   несовместимых сетевых полей, сохранение mounts/secrets/resource limits и
   ограничений полномочий. `docker compose config` проверяет итоговую
   конфигурацию с безопасными fixture inputs. Тесты не требуют production keys.
2. До применения Operations Agent сверяет exact image, конфигурацию и локальные
   сетевые риски. Сохраняет предыдущий Compose для отката, выполняет обязательные
   review/CI/handoff gates. Ежедневные timers остаются выключенными до приёмки.
3. Из штатного контейнера выполнить sync двух сохранённых artifacts с обратной
   проверкой содержимого. Подтвердить exit code, remote manifests/content,
   durable `verified`, отсутствие TLS timeout и непредусмотренных listeners.
   Успешного TLS handshake или одного PutObject недостаточно.
4. Штатно обработать зависший run с доказательством отсутствия живого владельца;
   его статус должен отражать реальный результат recovery, а не задним числом
   присвоенный успех. Проверить итоговое уведомление. Выполнить разрешённый новый
   ручной Data Cycle, проверить стадии, прогнозы/odds и уведомление. При сбое
   остановиться на соответствующем gate; не включать ежедневный timer.
5. Откат: после завершения либо контролируемой остановки одноразового sync
   вернуть предыдущую production Compose-конфигурацию для следующих запусков.
   Сохранять локальные/remote artifacts и durable state; не удалять данные,
   не подменять `verified`, не обновлять run прямым SQL. Откат возвращает
   прежнюю изоляцию, но может вернуть исходный timeout, поэтому timer остаётся
   выключенным до подтверждения рабочего цикла.

Пересмотр обязателен, если host sync также не проходит, появляются другие
клиенты со сбоем bridge, сетевые зависимости или listener у archive-sync,
либо риск доступа к локальным службам оказывается неприемлемым. После
доказанного исправления bridge проверить полный sync через bridge и вернуть
изоляцию отдельным проверенным изменением.

## Источники и неизвестное

- [Docker host network driver](https://docs.docker.com/engine/network/drivers/host/):
  общий network namespace, отсутствие отдельного IP, поддержка Linux и отсутствие
  port mapping. Проверено 2026-09-30.
- [Compose network_mode](https://docs.docker.com/reference/compose-file/services/#network_mode):
  контракт host mode и несовместимость с `networks`. Проверено 2026-09-30.
