# REQ-040 — Сквозная проверка платформы на клубном футбольном пуле

> **Статус:** confirmed
> **Владелец продукта:** пользователь
> **Дата:** 2026-10-12
> **Инициатива:** [EPIC-040](../../backlog/EPIC-040-club-football-platform-e2e.md)

## Результат

Один локальный сквозной сценарий использует весь уже собранный пул клубного футбола:
`ENG1`, `SPA1`, `GER1`, `ITA1`, `FRA1`, `RUS1`, `RUS2`, `UCL`, `UEL`. Он проходит
проверку данных, подготовку признаков, обучение и сравнение двух кандидатов,
создание тестовых прогнозов, чтение через API и тестовую выдачу в боте. Первый
кандидат оценивает П1 и П2 на развёрнутых строках как два независимых шанса
победы и проверяет остаток `1 − П1 − П2` как оценку ничьей. Второй даёт полное
распределение 1X2 на одной строке матча. Обе модели оценивают один рынок. Пул не
дробится на девять отдельных модельных инициатив. Production-публикация не
входит в результат.

## Подтверждено пользователем

- Проверяется весь перечисленный клубный пул, а не один турнир.
- Обязательный результат — локальный E2E и тестовая выдача; production не включается.
- В той же инициативе исправляются выявленные при архитектурном разборе
  расхождения конфигурации, путей запуска и документации.
- Обе модели оценивают один `winner` 1X2: первая использует развёрнутый
  датасет и получает два независимых шанса победы без нормировки; остаток
  `1 − П1 − П2` проверяется как шанс ничьей. Вторая использует wide-датасет
  и напрямую оценивает П1/Х/П2.
- Тестовый календарь должен содержать реальные upcoming-события Smart Tables.
- UCL/UEL обучаются только на счёте основного времени; источник подтверждается
  выборочной сверкой с UEFA, а каждая строка проходит автоматическую проверку
  счёта карточки, общей статистики и суммы двух таймов. Несогласованные и
  технические результаты исключаются с указанием `match_id` и причины.

## Предлагаемые критерии приёмки

1. Один каталог задаёт состав девяти соревнований, источник, один 1X2 market-spec
   и общий пул данных. Две стратегии кандидата различаются model identity,
   форматом данных и отчётом, а не правилами рынка. Локальный пул сам по себе
   не создаёт плановый Airflow/production refresh.
   Типовое добавление совместимого соревнования не требует второго списка в DVC,
   Airflow, CLI или Python-коде.
2. На закреплённом снимке всего пула повторяемый сценарий создаёт валидные
   raw/interim/processed данные, отчёт о покрытии по каждому коду соревнования и
   два обученных кандидата с разными model identity. Текущие признаки матча не используют итог или статистику,
   появившуюся после начала игры.
   Для UCL/UEL четыре записи без статистики таймов (`207721`–`207724`) не
   допускаются к обучению; новый сомнительный результат также исключается.
3. Бинарный кандидат вычисляет два независимых числа `P(П1)` и `P(П2)` без
   нормировки и проверяет `P(Х) = 1 − P(П1) − P(П2)`. Доля матчей с отрицательным
   или нечисловым остатком явно измеряется; они не публикуются как валидный 1X2.
   Прямой 1X2-кандидат публикует П1/Х/П2. Опубликованные значения конечны,
   лежат в `[0, 1]` и суммируются в единицу.
   Временное разделение не переносит события из тестового периода в обучение.
4. Локальная тестовая материализация обеих моделей сохраняет прогнозы с идентификаторами
   данных, модели, рынка и запуска. API и бот выдают те же исходы и вероятности.
   Повторный запуск не создаёт противоречивых записей или дублированных сообщений.
5. Отсутствие будущих событий, неполные данные, неизвестная модель или несовместимый
   рынок дают проверяемую причину остановки без ложной публикации.
6. NHL продолжает проходить затронутые контрактные проверки. Документы описывают
   фактические роли DVC, Airflow, MLflow, Hydra, Pandera и метрик в локальном и
   серверном контурах; неподтверждённые потребители метрик не объявлены работающими.

## Границы и зависимости

- Для обучения используется существующий локальный
  `data/source/football_top_leagues/source.csv`; на 2026-10-12 он содержит только
  завершённые матчи. Для тестовой выдачи upcoming-события читаются отдельно из
  Smart Tables, с моментом получения и проверкой отсутствия завершённого исхода.
- Исторические `odd_home`/`odd_draw`/`odd_away` не доказывают, что цена была
  доступна до начала матча. Историческую доходность нельзя выдавать за production
  edge без отдельного as-of контракта.
- Действующий [REQ-021](REQ-021-top-football-winner-baseline.md) задаёт исследование
  1X2 и финансовые критерии. Эта инициатива проверяет платформенный E2E, не
  подменяет исследовательское решение GO/ITERATE/STOP.
- Сервер, production pointer, расписание и реальные Telegram-получатели не меняются.

## Подтверждение

2026-10-12 пользователь выбрал весь клубный пул, локальный E2E и тестовую выдачу,
две модели одного рынка `winner` и реальный upcoming Smart Tables. Отдельно
подтверждены независимые шансы победы для бинарной модели без нормировки и
проверка остатка `1 − П1 − П2` как оценки ничьей.
Позже подтверждён выборочный внешний аудит UCL/UEL и автоматическая сверка
каждого результата основного времени.
