# REQ-025 — Расписание, готовность прогнозов и управление Data Cycle

> **Статус:** confirmed
> **Владелец продукта:** пользователь проекта
> **Создано:** 2026-09-26
> **Источник:** [полная постановка владельца](https://docs.google.com/document/d/14kneTT8iL9SqBEjk-4N7JOmuZv4mC-OrEQp_tMEYZFk/edit)

## Цель

К старту NHL Telegram-бот становится основной точкой просмотра календаря и
готовности событий. Администратор через бот управляет расписанием единого
Data Cycle, запускает его вручную и видит фактический результат без обычного
доступа к серверу. Итог инициативы — production-выпуск `1.2.0`. Базовый
контракт допускает последующее подключение футбольных турниров.

## Календарь

- Событие существует независимо от прогноза. Все доступные из источника
  события сохраняются со стабильным `event_id`, турниром, участниками,
  временем начала, статусом и временем последнего обновления календаря.
- Перенос времени обновляет то же событие; исчезновение из очередного ответа
  источника само по себе не удаляет запись. Календарь регулярно обновляется.
- Поддерживаются как минимум `scheduled`, `postponed`, `cancelled`,
  `started`, `finished`.
- Букмекерские сутки едины для backend, API, Telegram и тестов: `08:00
  Europe/Moscow` → `08:00` следующего дня. В 03:00 МСК «Сегодня» означает
  остаток суток, начавшихся вчера в 08:00 МСК (уточнение владельца).
- Пользователь выбирает «Сегодня», «Завтра» или `3`, `7`, `14`, `30`
  дней. Период `N` содержит текущие букмекерские сутки и следующие `N−1`.
- Выдача содержит все известные будущие события периода, даже без прогноза
  или коэффициентов. Для каждого показаны время, участники и готовность
  прогноза и коэффициентов. Пустой подтверждённый календарь отличается от
  неполного/необновлённого или временно недоступного.

## Готовность события

- Независимые состояния календаря: актуален, изменён, перенесён, отменён,
  отсутствует/требует проверки; прогноза: `pending`, `ready`, `partial`,
  `failed`, `unavailable`; коэффициентов: `missing`, `partial`,
  `ready`, `stale`, `failed`.
- Для календаря, прогнозов и коэффициентов хранятся моменты последнего
  успешного обновления. Старые данные не означают `ready`: для каждого вида
  нужны отдельные конфигурируемые freshness/SLA правила.
- Telegram агрегирует состояния как «Готово», «Частично готово», «Ожидает»,
  «Ошибка». «Ожидает» действует до срока подготовки, «Ошибка» — после
  несостоявшегося ожидаемого выполнения.

## Data Cycle и управление

- Единый цикл: `calendar → data/odds → quality checks → predictions →
  publication`. Выбор systemd, Airflow или cron не влияет на Telegram-контракт.
- Каждый запуск получает новый `run_id`, pipeline/турнир, причину
  (`scheduled`, `manual`, в будущем `retry`), время старта/окончания,
  текущий этап, результаты стадий, ошибки и итоговый статус `waiting`,
  `running`, `success`, `partial_success` либо `failed`.
- Администратор для каждого pipeline видит: автоматический цикл включён или
  выключен, время и частоту, часовой пояс, последний и следующий запуск,
  текущий `run_id` и этап, результат предыдущего цикла. Настройки
  персистентны и переживают рестарт сервисов.
- Только администратор меняет время основного запуска, частоту дальнейших
  запусков, включённость автоматического цикла и запускает его вручную.
  Частота означает интервал от основного времени, например 10:00 МСК и затем
  каждые 6 часов (уточнение владельца). Некорректное и конфликтующее
  расписание отвергается; время показано с зоной.
- Кнопка «Запустить сейчас» инициирует новый цикл. При уже активном запуске
  второго нет: бот показывает его `run_id`, старт и этап. После ошибки ручной
  повтор получает новый `run_id`, сохраняя историю старого. Службы не
  перезапускаются.
- Итоговый summary содержит числа найденных, новых, изменённых событий,
  событий, требующих прогноза, готовых прогнозов, событий с коэффициентами,
  полностью и частично готовых событий, ошибок и длительность. Покрытие
  представлено абсолютным числом и долей.
- Результат каждой стадии сохраняется отдельно. Ошибки отдельных событий
  допускают `partial_success`, если основная задача выполнена; `failed`
  означает срыв основной задачи. Не запущенные стадии обозначаются явно.
- После планового запуска администратор получает компактный итог, с явным
  предупреждением для `partial_success` и `failed`. При ручном запуске —
  принятие с `run_id` и отдельный итог, без лишних сообщений.
- История последних циклов показывает время, `run_id`, причину, итоговый
  статус, число событий и покрытие прогнозами и коэффициентами.
- Успех job не доказывает свежесть данных; календарь, прогнозы и коэффициенты
  оцениваются по своим freshness/SLA правилам.

## API, футбол и тестирование

- В API первично событие календаря; прогнозы и коэффициенты — связанные
  данные. Границы: `Tournament → Calendar → Event → Readiness` и
  `Pipeline → Data Cycle → Run → Stage results`.
- Футбол не включается в меню `1.2.0`, но минимум один контрольный случай
  проверяет иные рынки, источник, горизонт, freshness и отдельный pipeline
  без изменения базовых контрактов.
- Автоматический сценарий `Telegram request → handler → API → calendar →
  prediction/odds readiness` запускается локально и в CI без браузера,
  production token и production-запросов.
- Тесты отдельно проверяют границы 08:00, все периоды, перенос времени,
  отсутствие прогноза и коэффициентов, stale данные, `partial_success`,
  повторный manual run и блокировку параллельного запуска.

## Критерии приёмки 1.2.0

1. Пользователь получает актуальное расписание NHL на выбранный горизонт
   независимо от наличия прогноза и понимает готовность каждого события.
2. Администратор только через Telegram видит расписание, состояние, историю
   и покрытие циклов; меняет параметры и запускает цикл вручную без дублей.
3. Общие модели Calendar/Event/Readiness/Data Cycle работают для NHL и
   контрольного футбольного случая; перенос события сохраняет идентичность.
4. Кодовый сценарий Telegram/API и граничные тесты проходят без production.
5. Независимый review, локальные проверки, terminal CI, release gates,
   фактическая проверка scheduler и production health/smoke подтверждают
   выпуск `1.2.0` с rollback-планом.

## Зависимости и ограничения

- Изменение моделей, запуск футбола в production и перезапуск системных
  служб через бот в scope не входят.
- Сейчас `/predict/upcoming` отдаёт только опубликованные прогнозы `ok`,
  NHL source гарантирует около 48 часов расписания, а админский `/refresh`
  обращается к Airflow при описанном systemd production-контуре.
- Фактическое состояние production timer не доказано: read-only SSH
  2026-09-26 завершился таймаутом до входа. Для release gate нужна
  операционная проверка.
- Численные SLA и допустимые значения частоты задаются при проектировании
  конфигурации; их должен можно менять без переделки контракта.
