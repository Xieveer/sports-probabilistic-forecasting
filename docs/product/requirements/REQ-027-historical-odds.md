# REQ-027 — История наблюдений коэффициентов

> **Статус:** confirmed
> **Владелец продукта:** пользователь
> **Создано:** 2026-10-10
> **Подтверждено:** 2026-10-10
> **Инициатива:** [EPIC-027](../../backlog/EPIC-027-historical-odds.md)

## Цель и ценность

Владелец прогнозов должен воспроизводить цену и смысл рынка, доступные для
сравнения с прогнозом на выбранный момент времени, чтобы не подменять прошлую
линию текущей или единственным итоговым значением матча. Первый срез, выбранный
владельцем 2026-10-10: NHL, рынок победителя **с учётом овертайма**
`winner_withOT`, букмекер Pinnacle. Источник первого среза — уже имеющиеся
исторические ответы The Odds API в локальном кэше.

## Факты и решение владельца

- Локальный кэш The Odds API содержит 1790 historical JSON за 2023–2026 годы.
  В них обнаружены 4144 NHL события с двухисходным `pinnacle/h2h`; 3767 событий
  имеют не менее двух разных snapshot, у 3742 менялся вектор цен. Это проверка
  локальных файлов 2026-10-10, а не гарантия будущего покрытия или доступа к API.
- Локальный `pinnacle_odds.parquet` содержит 4154 строки, но действующий V3
  OddsStore дедуплицирует матч по дате и командам и сохраняет одну wide-строку.
  Накопленную динамику из него одного восстановить нельзя.
- Existing `odds_observations` в сервисной БД уникален по событию, рынку и
  букмекеру и хранит последнюю подтверждённую линию. Это текущая проекция,
  а не журнал всех наблюдений.
- Historical API возвращает время снимка/обновления провайдера. Локальный
  `fetched_at` существующего OddsStore для матчей 2023–2026 годов относится к
  загрузке в 2026 году. Поэтому прошлое время провайдера само по себе не
  доказывает, что цена была известна **нашей системе** в тот прошлый момент.
- **Решение владельца:** historical provider snapshots, загруженные позднее,
  допустимы для ретроспективного бэктеста при явной пометке происхождения и
  раздельном хранении времени снимка провайдера (`observed_at`) и времени
  локального получения (`retrieved_at`). Такой результат нельзя маркировать
  как известный локальной системе в прошлый момент `T`.

## Scope первого среза

- Импортировать уже имеющиеся исторические ответы The Odds API для NHL/Pinnacle;
  новый online backfill не требуется для приёмки первого среза.
- Для подтверждённо связанного события NHL хранить отдельные наблюдения
  Pinnacle `winner_withOT`: исход home/away, decimal price, `observed_at`
  провайдера, достоверный `retrieved_at` системы при его наличии,
  идентификатор источника и provenance связи с событием. Отсутствующее время
  прежнего получения должно быть явно обозначено. Время и смысл рынка должны
  читаться вместе с ценой.
- Дать ретроспективный запрос по событию, букмекеру, рынку, исходу и моменту
  `T`, который выбирает только снимок провайдера с `observed_at <= T` и явно
  показывает `retrieved_at` либо его отсутствие, источник и факт поздней
  загрузки, если она доказана.
  Повторный импорт того же снимка идемпотентен; другой снимок или изменение
  цены не затирает прежнее наблюдение.
- Сопоставить известные названия одного и того же рынка с единым ключом;
  `winner` в основное время, `winner_withOT` и рынки с ничьей остаются разными
  смыслами. Неизвестный рынок и неоднозначное событие не подтверждаются
  автоматически.
- Показывать покрытие отдельно по отсутствующей линии, отсутствию подходящего
  исторического снимка и ошибке сопоставления события/рынка. Минимальный
  процент покрытия не задаётся; отчёт показывает фактические числа.
- Сохранить прежние OddsStore, `odds_observations`, прогнозы и выдачу при
  внедрении аддитивного журнала. Данные старой wide-строки без достаточного
  provenance не превращать в вымышленные независимые исторические снимки.

## Non-scope

- Сравнение всех букмекеров, лучшие исполнимые цены, лимиты ставок и расчёт
  реальной доходности: отдельные EPIC-030/031.
- Другие турниры, рынки и исход draw; новый scheduler на турнир или спорт.
- Историческая выдача через API/бота и изменение их текущей линии; первый
  запрос истории и отчёт покрытия предназначены для локального анализа.
- Новый online backfill и гарантия будущего покрытия The Odds API.
- Использование коэффициентов как обучающих признаков и переключение
  production-модели.
- Production-подключение истории до серверного gate EPIC-026 и отдельного
  запроса на выпуск.

## Подтверждённые критерии приёмки

Владелец подтвердил границы первого среза и допустимость поздней загрузки
provider snapshots для ретроспективного бэктеста.

1. Для одного подтверждённого события два последовательных Pinnacle h2h
   снимка сохраняются раздельно; повторная загрузка не создаёт дубль и не
   переписывает раннюю цену. Запрос на время между снимками возвращает ранний,
   после второго — поздний, при отсутствии допустимого снимка — явное
   отсутствие данных.
2. Ретроспективный запрос выбирает снимок с `observed_at <= T` даже при
   `retrieved_at > T`, но ответ явно показывает время локального получения
   либо отсутствие достоверного времени и позднюю загрузку, если она доказана.
   Такой ответ не маркируется как локально известный в прошлом.
3. Два варианта названия подтверждённого Pinnacle h2h дают один ключ
   `winner_withOT`. Регламентный `winner` и рынок с ничьей не попадают в этот
   ключ; неизвестное описание рынка остаётся неподтверждённым.
4. Неоднозначное или неподтверждённое событие не получает связанную цену.
   После решения через registry та же запись становится доступна без
   изменения исходного observation/provenance.
5. Отчёт по выбранному интервалу и рынку раздельно считает события без линии,
   без снимка, допустимого к `T`, и с ошибкой сопоставления; показывает
   фактическое покрытие без порога приёмки. Нулевое покрытие не подменяется
   текущими котировками.
6. Существующая NHL выдача и старые close/T−15 значения остаются читаемыми;
   новая история проверяется на реальном локальном примере с двумя изменившимися
   Pinnacle снимками и на контрольном отсутствии линии.

## Зависимости и интеграция

- [EPIC-026](../../backlog/EPIC-026-entity-registry.md) предоставляет
  подтверждённую идентичность событий. Инженерный контракт есть в `main`;
  серверный gate остаётся зависимостью только production-подключения.
- Значимое решение о контракте observation, ключе рынка и временном запросе
  нужно закрепить ADR перед реализацией.
- Будущие изменения EPIC-027 ограничены историей odds и смыслом рынка.
  Общие миграции service DB согласуются с параллельным EPIC-028; поля model
  bundle и metadata прогнозов остаются в границе EPIC-028.

## Открытые технические вопросы для ADR

Формат наблюдения, идемпотентный ключ, способ фиксации provenance импортируемого
кэша и локальное хранилище выбираются в ADR. При импорте legacy-кэша нельзя
выдумывать `retrieved_at`: если достоверного времени локального получения в
артефакте нет, это отсутствие должно быть явно представлено. Время снимка
провайдера также нельзя заменять временем импорта.

## Доказательства и следующий gate

Проверить на локальных снимках цену, время провайдера, время загрузки,
подтверждённую связь события и фактическое покрытие выбранного окна. Перед
реализацией принять ADR о контракте истории, затем выделить минимальные TASK
и тесты для каждого критерия. Локальная разведка не подтверждает коммерческую
доступность будущих данных у API.
