# REQ-013 — Opt-in Research Mode

> **Статус:** confirmed
> **Владелец продукта:** пользователь проекта
> **Создано:** 2026-08-23

## Результат и ценность

Пользователь может явно запустить автономное исследование спортивного прогнозирования,
когда известна цель, но неизвестен способ её достижения. Research Mode сохраняет
каноническое состояние и знания вне LLM-контекста, последовательно проводит гипотезы через
data research, Engineering Workflow, эксперимент и независимую оценку и завершает работу
формальным состоянием. Существующий Engineering Workflow остаётся поведением по умолчанию.

## Scope

- Явное разделение Engineering Mode и opt-in Research Mode.
- Программная state machine, типизированные контракты и файловое каноническое состояние.
- Роли `research-scientist`, `data-researcher` и `research-evaluator` с Codex-профилями.
- Goal Contract, Research Memory, Context Package и расширяемый Data Source Catalog.
- Минимальный вертикальный срез с несколькими изолированными итерациями и Engineering boundary.

## Non-scope

- Изменение FastAPI, DVC, Airflow, MLflow, production-кода прогнозирования или выпуск версии.
- Автоматическое получение данных, обход аутентификации, работа с приватными API и deployment.
- Реальный длительный поиск betting edge или собственный рантайм для вызова Codex LLM.

## Сценарии

1. Пользователь явно выбирает Research Mode и передаёт Goal Contract; orchestrator создаёт
   независимое от чата состояние и выдаёт Scientist минимальный Context Package.
2. Гипотеза требует изучения источника и изменения кода: data-researcher возвращает
   DataResearchResult, а orchestrator передаёт EngineeringRequest существующему workflow и
   ждёт подтверждённую TASK до эксперимента.
3. Две последовательные итерации переживают создание нового orchestrator между шагами;
   evaluator детерминированно отклоняет первую и принимает вторую.
4. Превышение бюджета, внешняя зависимость или внутренняя ошибка приводит только к
   `EXHAUSTED`, `BLOCKED` или `FAILED`; успешная оценка — к `SUCCESS`.

## Критерии приёмки

- [x] Engineering Mode остаётся default; Research Mode запускается только явным контрактом.
- [x] Каждый переход state machine валидирует typed contract до сохранения состояния.
- [x] Каноническая память, findings, каталог источников и packages достаточны для продолжения
  после уничтожения LLM-сессии.
- [x] Нет параллельной engineering-команды: изменения кода проходят через EngineeringRequest
  с ссылкой на обычную TASK и статусом verified.
- [x] Evaluation Harness детерминированно выдаёт `PASS` / `FAIL` / `INVALID` и учитывает
  базовые ограничения holdout и budget.
- [x] Тест доказывает минимум две автономные итерации с data research, engineering boundary,
  experiment, evaluation и обновлением памяти.

## Ограничения, зависимости и риски

- Локальные Codex profiles не документируют гарантий наследования или изоляции context;
  архитектура не зависит от этого поведения.
- v1 использует адаптеры ролей и experiment runner, поэтому фактический LLM provider и
  исполнение Engineering TASK остаются внешними, заменяемыми границами.
- Раскрытый locked holdout помечается как скомпрометированный и не может использоваться как
  повторяемый сигнал успеха.

## Предположения и открытые вопросы

- Пользователь подтвердил, что v1 не требует релиза, версии и реального многодневного поиска.
- Выбор внешнего LLM runner, формата очереди и хранилища для длительных run остаётся future scope.
