# REQ-014 — Каталог контрактов исследованных спортивных API

> **Статус:** confirmed
> **Владелец продукта:** пользователь проекта
> **Создано:** 2026-08-25

## Результат и ценность

Research Mode должен возвращать не свободный текст о том, что источник «нашёлся», а
проверяемый каталог API, с которым research-scientist может сформировать воспроизводимую
гипотезу и запросить ровно нужный engineering-срез. Для каждого исследованного источника
scientist видит методы, параметры, сущности, поля, их тип и смысл, связь с другими объектами,
время фактической доступности и ограничения. Каталог исключает догадки о схеме и скрытый
look-ahead bias.

## Scope

- Расширить канонический контракт Data Source Catalog так, чтобы он описывал endpoint и
  поле структурированно, а не только строковыми списками.
- Для каждого подтверждённого endpoint фиксировать HTTP-метод, путь, параметры, тип ответа,
  пагинацию, ключи сущностей, покрытие, способ и дату проверки, ограничения доступа и
  наблюдаемые ошибки.
- Для каждого пригодного поля фиксировать JSON path, тип, nullable, единицы/домен значений,
  смысл, сущность, первичный/внешний ключ, доступность относительно начала события,
  риск leakage и назначение: target, feature, label, odds или metadata.
- Сохранить отдельные машиночитаемые карточки и человекочитаемый data dictionary для
  исследованных источников; связать их с DataResearchResult и provenance.
- Провести повторное исследование согласованных футбольного и хоккейного источников только
  по законно доступным публичным данным и официальной документации либо явно помеченным
  наблюдениям.
- Явно фиксировать неизвестные или недоступные методы/поля как ограничение, а не как
  отсутствие результата.

## Non-scope

- Реализация ingest, обход аутентификации/CAPTCHA/robots, сохранение cookies, HAR,
  credentials или полных ответов API.
- Подключение источника к обучению, DVC, Airflow или production API.
- Гарантия неизменности неофициального внешнего API.

## Сценарии

1. Scientist запрашивает предматчевую форму команды. Он открывает карточку источника,
   находит endpoint, нужные поля и их temporal availability; post-match поля автоматически
   исключаются как leakage.
2. Data Researcher исследует метод, который отвечает 403, 404 или требует недоступного
   доступа. Карточка содержит воспроизводимое ограничение и безопасный summary без payload,
   а не выдуманную схему.
3. Engineer получает запрос на ingestion. Он использует endpoint contract и data dictionary
   для выбора ключей, pagination, типа и nullable-полей, не извлекая схему из чата.

## Критерии приёмки

- [ ] Контракт не может быть валиден, если endpoint или поле представлены только именем без
  обязательной семантики и temporal availability.
- [ ] Машиночитаемая карточка содержит отдельные записи endpoint'ов, параметров и полей и
  имеет provenance с датой проверки и уровнем доказательства.
- [ ] Человекочитаемый каталог позволяет по любому полю определить источник/endpoint/JSON
  path, тип, nullable, смысл, ключи, допустимый момент использования и риск leakage.
- [ ] Для каждого из согласованных футбольного и хоккейного источников есть завершённая
  карточка с охватом, исторической глубиной, pagination, rate limits/access, пропусками,
  известными проблемами и research value; неподтверждённые сведения отмечены.
- [ ] Есть тесты валидации расширенного контракта и негативный тест неполной карточки.
- [ ] Документация Research Mode объясняет scientist и data-researcher, где находится каталог
  и как использовать temporal-метки полей.

## Ограничения, зависимости и риски

- NHL Web API и Smart Tables backend не имеют стабильного публичного versioned контракта;
  результаты являются снимком на дату проверки.
- Smart Tables уже помечен в репозитории как источник с правовыми и ToS-ограничениями;
  исследование не даёт разрешения на массовый сбор или production-использование.
- Нужны точные названия двух источников и приоритет глубины: полный каталог всех методов
  либо методы, нужные для match/team/player/odds research.

## Предположения и открытые вопросы

- Предположение: под футболом имеется в виду `backend.smart-tables.ru`, под хоккеем —
  `api-web.nhle.com`; требуется подтверждение владельца.
- Открытый вопрос: нужно ли в первой поставке документировать только исследовательски
  пригодные методы или весь публично наблюдаемый surface API, включая UI/low-value methods.
- Открытый вопрос: карточки должны быть постоянной частью репозитория или runtime-данными
  отдельного Research workspace с публикуемым data dictionary в `docs/`.

## Подтверждение

Владелец продукта подтвердил 2026-08-25: первый scope — `backend.smart-tables.ru` для
футбола и `api-web.nhle.com` для хоккея; глубина — все публично наблюдаемые методы, а не
только методы текущего ingest.
