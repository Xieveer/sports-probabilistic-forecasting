# REQ-023 — Пилот агентского цикла: расписание NHL в Telegram

> **Статус:** confirmed
> **Владелец продукта:** пользователь проекта
> **Создано:** 2026-09-16
> **Основание:** интервью владельца после аудита EPIC-022.

## Результат и ценность

Пользователь Telegram-бота получает расписание будущих матчей выбранного турнира
на заданный горизонт в днях вместе с уже существующими прогнозом, коэффициентами и
рассчитанным value для ставки. Первый доступный турнир — NHL.

Изменение должно стать одним реальным вертикальным срезом для проверки минимального
агентского цикла: независимый агент способен продолжить работу из канонических
артефактов, довести небольшую engineering-задачу до принятого Git-инкремента и
через выделенный `operations-agent` безопасно развернуть её в существующем production
контуре. Успех измеряется полезной функцией бота и принятым инкрементом, а не
количеством workflow-артефактов.

Основные пользователи:

- пользователь Telegram-бота, выбирающий турнир и горизонт расписания;
- владелец продукта, проверяющий тестового бота и фактический production-результат;
- implementer/reviewer и `operations-agent`, передающие друг другу проверяемый
  минимальный контекст.

## Scope

- Бот предлагает выбрать турнир; в пилоте доступен NHL, но взаимодействие оставляет
  место для добавления других поддерживаемых турниров.
- После выбора турнира бот принимает целое `N` от 0 до 30.
  `0` показывает остаток текущего дня, `N` — период до конца дня, наступающего через
  `N` календарных дней; граница времени — МСК.
- Ответ группирует будущие матчи по датам. Для каждого матча показывает время начала
  в МСК, команды, существующий формат прогноза, существующий формат коэффициентов и
  рассчитанный value для ставки.
- Если для отдельного матча отсутствуют прогноз, коэффициенты или value, матч остаётся
  в ответе с явной пометкой «нет данных» для соответствующего поля.
- Если будущих матчей в периоде нет, бот сообщает об этом явно.
- До production-deploy выполняются полный набор тестов, линтеры, обязательные Git CI и
  самостоятельная браузерная e2e-проверка агентом через отдельный тестовый бот.
- После успешных gates `operations-agent` выполняет только заранее ограниченный deploy
  и rollback существующего сервиса. Он не получает произвольный shell/Docker/sudo
  доступ и не получает секреты в чате, Git, evidence или логах.
- После deploy `operations-agent` проверяет только технические health-checks и
  разрешённые безопасные логи. Пользовательскую production-проверку выполняет владелец.
- При сбое production health-check агент автоматически возвращает предыдущую рабочую
  версию и возвращает TASK в работу с диагностикой.
- Операционный паспорт и правила `operations-agent` синхронизируются с фактическим
  production-состоянием и этим делегированным deploy-контрактом.

## Non-scope

- Изменение моделей, источников данных, расчёта прогнозов, коэффициентов или value.
- Research Mode, Research integration, session memory, file-backed registry, lease,
  GPG/evidence workflow и обязательный CI gate из EPIC-022.
- Новые турниры, подписки, уведомления, админ-команды и общая переработка Telegram UX.
- Новый production-сервер, изменение DNS/TLS/firewall/SSH, ротация секретов либо выдача
  агенту неограниченных инфраструктурных прав.
- Автоматическая отправка пользовательских запросов production-боту после deploy.

## Сценарии

1. Пользователь выбирает NHL, вводит допустимый `N` и получает будущие матчи,
   сгруппированные по датам в МСК, с существующими прогнозом, коэффициентами и value.
2. Пользователь вводит `N` вне диапазона или нецелое значение; бот объясняет допустимый
   формат (`0–30`) и не выполняет неверный запрос.
3. У матча нет одного или нескольких обогащающих полей; бот сохраняет матч в выдаче и
   явно маркирует отсутствующее поле как «нет данных».
4. На выбранном горизонте нет будущих матчей; бот сообщает, что матчей нет.
5. Агент получает только REQ/TASK и репозиторный контекст, реализует и тестирует
   функцию, а независимый reviewer принимает Git-инкремент.
6. После зелёных локальных и Git gates агент проверяет отдельный тестовый бот через
   браузер; затем `operations-agent` разворачивает принятый release и проверяет
   production health/logs.
7. Production health-check не проходит; `operations-agent` откатывает предыдущую
   рабочую версию, фиксирует диагностику и не объявляет TASK выполненной.

## Критерии приёмки

- [ ] Бот позволяет выбрать NHL и запросить будущие матчи на горизонт `N=0–30` по
  правилам календарного периода в МСК.
- [ ] В выдаче матчи сгруппированы по датам; для каждого видны время, команды,
  существующие прогноз/коэффициенты/value либо пометка «нет данных» для отсутствующего
  значения.
- [ ] Пустой период и неверный ввод имеют понятный детерминированный ответ.
- [ ] Поведение покрыто unit/integration-тестами, а тестовый бот проходит браузерный
  e2e-сценарий без использования production-токена.
- [ ] Перед deploy фактически успешны полный набор тестов, линтеры и Git CI для exact
  принятого commit; evidence содержит только ссылки/краткие результаты без секретов.
- [ ] Независимый reviewer принимает exact Git commit, и следующий агент может найти
  scope, проверки, риски и release-идентификатор только по каноническим артефактам.
- [ ] `operations-agent` разворачивает только принятый immutable release через
  ограниченный существующий механизм; health/log checks успешны либо автоматически
  выполнен rollback к подтверждённой предыдущей версии.
- [ ] В операционной документации отсутствует ложное утверждение о неразвёрнутом
  сервисе; описаны фактический target, deploy boundary, health checks и rollback.

## Ограничения, зависимости и риски

- Источником данных остаются существующие API и формат Telegram-прогноза; их точный
  контракт требуется подтвердить перед реализацией, не угадывать.
- Тестовый и production-боты используют разные серверные токены. Их значения не
  передаются агентам через Git, документы, логи или чат.
- Доступ `operations-agent` описан в отдельном проекте
  `/home/xieveer/Документы/codex_projects/operations-agent`. Его текущий сервисный
  паспорт противоречит заявленному владельцем факту работающего production-бота и
  должен быть исправлен на основании read-only discovery до deploy.
- Автоматический deploy допустим владельцем только для этого ограниченного сервиса и
  только после перечисленных gates. Изменение target, прав, downtime или persistent
  data требует возвращения к владельцу за отдельным решением.
- Автоматический rollback снижает последствия deployment failure, но не заменяет
  pre-deploy проверки и сохранённый совместимый rollback target.
- Release candidates `v1.1.15`–`v1.1.17` остановлены до publication и server mutation
  на MinIO startup (Docker exit 125). `v1.1.18` остановился до first-rollout: Docker Hub
  отклонил pull pinned `minio/minio` digest. `v1.1.19` успешно прошёл first-rollout с
  project-owned S3-compatible fixture из locked dependencies, но остановился после
  publication из-за невалидного regex в `jq` manifest-platform gate. `v1.1.20` исправляет
  только этот gate и обязан пройти полный tag pipeline до rollout; переиспользование либо
  перемещение предыдущих тегов запрещено. Решение о fixture зафиксировано в ADR-024.

## Предположения и открытые вопросы

- **Подтверждено пользователем:** production-бот уже работает, а тестовый бот изолирован
  от него отдельным токеном.
- **Подтверждено пользователем:** владелец делегирует `operations-agent` самостоятельный
  ограниченный deploy и rollback после зелёных local/Git/e2e gates.
- **Предположение:** существующий ограниченный deployment entrypoint может принять
  release этого сервиса и сохранить предыдущую рабочую версию. Это подтверждается
  read-only discovery до планирования deploy.
- **Открытый вопрос:** какие конкретные server-side health/log checks являются
  достаточным доказательством для текущего фактического runtime; ответ даёт
  `operations-agent` по read-only discovery, а владелец подтверждает как часть плана.
