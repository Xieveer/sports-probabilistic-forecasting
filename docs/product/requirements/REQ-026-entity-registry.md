# REQ-026 — Устойчивая идентичность спортивных сущностей

> **Статус:** confirmed
> **Владелец продукта:** пользователь проекта
> **Создано:** 2026-10-04
> **Эпик:** [EPIC-026](../../backlog/EPIC-026-entity-registry.md)

## Цель

Внутренняя сущность проекта имеет собственный неизменяемый ID и редактируемое
проектное имя. Идентификаторы и названия спортивных и букмекерских источников
привязываются к ней как внешние обозначения. Этот процесс должен работать для
многих видов спорта и сотен турниров, а не быть отдельным справочником NHL.

## Подтверждённые владельцем правила

- Переименование той же сущности сохраняет её внутренний ID.
- Неочевидные связи источников подтверждает лично владелец проекта. Для этого
  нужна локальная веб-страница с поиском и пакетным подтверждением. Процесс
  принятия решений на сервер не переносится.
- Прогнозы опираются на события спортивного источника. Проектная идентичность
  события и его название должны быть собственными; к ним привязываются все
  поддерживаемые источники.
- EPIC-026 завершается работающим повторяемым процессом для многих турниров,
  а не только демонстрацией на NHL.
- Полный актуальный набор проектных сущностей и подтверждённых привязок должен
  быть доступен локально: история загружается и модели обучаются без запроса
  к серверному registry во время обработки.
- Новые сущности прежде всего обнаруживаются при локальной загрузке данных;
  локальный registry владеет подтверждёнными решениями.
- Сервер получает проверенный снимок registry только для чтения. Если сервер
  первым обнаружил неизвестную сущность, он сохраняет её неподтверждённой,
  передаёт кандидата локально и ждёт опубликованного решения владельца.
- Архитектура идентичности должна допускать будущих игроков: игрок имеет
  собственный ID и привязки имён/ID источников, а его связь с командой может
  меняться во времени. Выпуск прогнозов на игроков в EPIC-026 не входит.

## Проверяемые критерии EPIC-026

1. Система создаёт собственные ID и проектные имена турнира, команды и события;
   редактирование имени не меняет ID. `COL` из NHL API и `Colorado Avalanche`
   из The Odds API указывают на одну проектную команду.
2. Для внешнего ID или имени сохраняются источник, исходное значение, область
   применимости и состояние подтверждения. Повторный импорт и повторное
   разрешение подтверждённой связи не создают новый ID и не стирают решение.
3. Неизвестная либо неоднозначная связь попадает в локальную очередь проверки с
   предложенными кандидатами и основаниями. До решения владельца она не
   выдаётся как подтверждённая. Локальная веб-страница позволяет искать,
   фильтровать и пакетно подтверждать связи; владелец может также отклонить
   или отложить связь. Решение и его автор фиксируются.
4. Событие спортивного источника остаётся доступным для календаря и прогноза,
   даже если его букмекерская привязка не определена. Связь с букмекерским
   событием и его коэффициентами появляется только после однозначного
   разрешения либо решения владельца; конфликт не разрешается молча.
5. Один и тот же механизм, схема хранения и процесс проверки работают на NHL
   и на контрольном случае другого турнира без правки Python-кода под его
   конкретные названия и ID. Это не включает полный training/production
   onboarding нового турнира из [EPIC-029](../../backlog/EPIC-029-configured-tournament-onboarding.md).
6. Существующие NHL-календарь, прогнозная выдача, source ID и архивы остаются
   читаемыми на прежних входах. Миграция аддитивна, проверяема и не удаляет
   накопленные события или прогнозы.
7. Контракт сущностей допускает тип `player` и независимую от его ID связь с
   командой, действующую в определённый период. Проверка контрактным тестом
   не требует реализации player-прогнозов или загрузки составов.
8. Локальная загрузка истории и обучение используют полный локальный registry,
   содержащий проектные ID, имена, внешние ID и названия всех поддерживаемых
   сущностей и источников. Импорт не требует доступности серверного API.
9. Подтверждённое локальное состояние можно экспортировать как полный
   проверяемый снимок с версией и контрольными суммами. Обучение фиксирует
   версию использованного registry для воспроизводимости. Применение снимка
   на сервере не меняет принятые локально решения.
10. Сервер использует только опубликованный проверенный снимок для разрешения;
    новые найденные им обозначения передаются в локальную очередь как
    кандидаты. До получения решения сервер не утверждает новую связь, а
    ошибка публикации сохраняет предыдущий рабочий снимок.
11. Object Storage хранит текущую опубликованную версию и проверяемую историю
    снимков. Сервер получает новую версию оттуда без ручной SSH-передачи;
    временная недоступность Object Storage не лишает runtime последней
    проверенной установленной версии.

## Границы и миграция

- Существующий [ADR-026](../../architecture/adr/ADR-026-calendar-and-data-cycle-control.md)
  использует `canonical_events.id` как публичный непрозрачный `event_id`.
  Новое решение должно сохранить этот вход/выход и определить, как отделить
  проектный ID события от единственного source key без потери ссылок.
- `conf/bookmaker/team_name_registry/nhl.yaml` служит входом проверенных
  соответствий. Импорт не перезаписывает последующее решение владельца.
- Существующий [NHL source-state archive](../../architecture/adr/ADR-012-nhl-source-state-archive.md)
  использует Object Storage для проверяемых артефактов, но не является
  источником решений по идентичности. Registry получает отдельный prefix и
  контракт полного снимка с направлением локально → Object Storage → сервер.
  Версии, использованные обучением, сохраняются по политике воспроизводимости,
  независимо от краткоживущего source-state.
- Предлагаемый путь публикации: локальная система загружает неизменяемый
  снимок, проверяет его в Object Storage и только после этого обновляет
  указатель текущей версии. Серверный sync-процесс читает указатель, скачивает
  и проверяет снимок, затем атомарно устанавливает его в PostgreSQL. Runtime
  читает установленную версию из БД. Точный формат, частоту проверки,
  разрешения Object Storage и откат фиксирует ADR.
- Автоматические кандидаты допустимы, но неоднозначность не превращается в
  подтверждение по похожести строк. Правила сопоставления событий и пороги
  времени определяются в ADR и проверяются тестами.
- Production-переключение и удаление старого YAML-мэппинга не входят в
  автоматическую миграцию. До проверки совместимости сохраняется обратимый
  путь чтения прежних данных.

## Доказательства приёмки

- Автоматические тесты на идентичность, переименование, конфликт, решение
  владельца, повторный импорт и отсутствие неподтверждённой связи.
- Интеграционный сценарий для NHL и контрактный пример другого турнира с тем
  же механизмом, плюс регрессии календаря и прогнозной выдачи.
- Проверка локального offline-разрешения, версии в provenance обучения,
  полного экспорта и сохранения предыдущего серверного снимка при ошибке.
- Проверенный миграционный и откатный план, независимый review и terminal CI.
