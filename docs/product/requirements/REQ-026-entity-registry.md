# REQ-026 — Устойчивая идентичность спортивных сущностей

> **Статус:** confirmed
> **Владелец продукта:** пользователь проекта
> **Создано:** 2026-10-04
> **Эпик:** [EPIC-026](../../backlog/EPIC-026-entity-registry.md)

## Цель

Внутренняя сущность проекта имеет собственный неизменяемый ID и редактируемое
проектное имя. Идентификаторы и названия спортивных и букмекерских источников
привязываются к ней как внешние обозначения. Этот процесс должен работать для
многих видов спорта и сотен турниров, а не быть отдельным справочником NHL.

## Подтверждённые владельцем правила

- Переименование той же сущности сохраняет её внутренний ID.
- Неочевидные связи источников подтверждает лично владелец проекта. Для этого
  нужна локальная веб-страница с поиском и пакетным подтверждением. Процесс
  принятия решений на сервер не переносится.
- На той же локальной веб-странице владелец должен видеть и редактировать
  текущий реестр сущностей и подтверждённых обозначений, даже когда очередь
  новых кандидатов пуста. Редактирование не требует прямой правки SQLite или YAML.
- Registry содержит подтверждённые словари турниров, команд, рынков и исходов
  по источникам. Для рынков явно хранятся правила расчёта: овертайм, ничья,
  состав исходов и область применимости букмекерского обозначения.
- Календарь и прогнозы опираются на события спортивного источника. Его ID и
  bookmaker event ID остаются в исходных записях и provenance. Постоянную
  связь двух ID каждого матча в owner registry не ведём: событие букмекера
  сопоставляется при обработке по подтверждённым турниру, командам, сторонам
  и времени с ограниченным допуском. Для NHL начальный автоматический допуск —
  не более 15 минут по UTC. Неоднозначность требует решения владельца.
- EPIC-026 завершается работающим повторяемым процессом для многих турниров,
  а не только демонстрацией на NHL.
- Полный актуальный набор проектных сущностей и подтверждённых привязок должен
  быть доступен локально: история загружается и модели обучаются без запроса
  к серверному registry во время обработки.
- `conf/bookmaker/team_name_registry/nhl.yaml` — временный legacy seed для
  переноса уже собранных связей. После сверки полноты реестра NHL работает
  только по подтверждённым связям registry; YAML перестаёт быть вторым
  редактируемым справочником. Код старого пути сохраняется для явного отката;
  его удаление выполняется позже отдельным изменением.
- Новые сущности прежде всего обнаруживаются при локальной загрузке данных;
  локальный registry владеет подтверждёнными решениями.
- Сервер получает проверенный снимок registry только для чтения. Если сервер
  первым обнаружил неизвестную сущность, он сохраняет её неподтверждённой,
  передаёт кандидата локально и ждёт опубликованного решения владельца.
- Архитектура идентичности должна допускать будущих игроков: игрок имеет
  собственный ID и привязки имён/ID источников, а его связь с командой может
  меняться во времени. Обозначение игрока разрешается с учётом команды и
  периода её действия. Выпуск прогнозов на игроков в EPIC-026 не входит.

## Проверяемые критерии EPIC-026

1. Система создаёт собственные ID и проектные имена турнира, команды, рынка и
   исхода; редактирование имени не меняет ID. `COL` из NHL API и
   `Colorado Avalanche` из The Odds API указывают на одну проектную команду.
2. Для внешнего ID или имени сохраняются источник, исходное значение, область
   применимости и состояние подтверждения. Повторный импорт и повторное
   разрешение подтверждённой связи не создают новый ID и не стирают решение.
3. Неизвестная либо неоднозначная связь попадает в локальную очередь проверки с
   предложенными кандидатами и основаниями. До решения владельца она не
   выдаётся как подтверждённая. Локальная веб-страница позволяет искать,
   фильтровать и пакетно подтверждать связи; владелец может также отклонить
   или отложить связь. Решение и его автор фиксируются.
4. Событие спортивного источника остаётся доступным для календаря и прогноза,
   даже если котировка не сопоставлена. Котировка присоединяется лишь при
   подтверждённых обозначениях турнира и обеих команд, совпадении сторон и
   рынка с его правилами, времени в установленном допуске (для NHL не более
   15 минут по UTC) и единственном
   взаимном соответствии матчей двух источников. Иначе она остаётся отдельно
   с причиной; конфликт не разрешается молча и не создаёт постоянную связь
   event ID в owner registry.
5. Один и тот же механизм, схема хранения и процесс проверки работают на NHL
   и на контрольном случае другого турнира без правки Python-кода под его
   конкретные названия и ID. Это не включает полный training/production
   onboarding нового турнира из [EPIC-029](../../backlog/EPIC-029-configured-tournament-onboarding.md).
6. Существующие NHL-календарь, прогнозная выдача, source ID и архивы остаются
   читаемыми на прежних входах. Миграция аддитивна, проверяема и не удаляет
   накопленные события или прогнозы.
7. Контракт сущностей допускает тип `player`, обозначения игрока по источникам
   и независимую от его ID связь с командой, действующую в определённый
   период. Одинаковое имя в разных командах или периодах не разрешается по
   одной строке. Проверка контрактным тестом не требует player-прогнозов.
8. Локальная загрузка истории и обучение используют полный локальный registry,
   содержащий проектные ID, имена, внешние ID и названия всех поддерживаемых
   сущностей и источников. Импорт не требует доступности серверного API.
9. Подтверждённое локальное состояние можно экспортировать как полный
   проверяемый снимок с версией и контрольными суммами. Обучение фиксирует
   версию использованного registry для воспроизводимости. Применение снимка
   на сервере не меняет принятые локально решения.
10. Сервер использует только опубликованный проверенный снимок для разрешения;
    новые найденные им обозначения передаются в локальную очередь как
    кандидаты. До получения решения сервер не утверждает новую связь, а
    ошибка публикации сохраняет предыдущий рабочий снимок.
11. Object Storage хранит текущую опубликованную версию и проверяемую историю
    снимков. Сервер получает новую версию оттуда без ручной SSH-передачи;
    временная недоступность Object Storage не лишает runtime последней
    проверенной установленной версии.
12. Локальный веб-интерфейс показывает весь текущий registry, включая
    подтверждённые сущности и обозначения без кандидатов в очереди. Владелец
    может найти существующую команду, увидеть связанные обозначения каждого
    источника и изменить подтверждённую связь или проектное имя с аудитом и
    защитой от устаревшей формы. Изменение попадает на сервер только через
    новый проверенный snapshot и публикацию.
13. После переноса и проверки NHL-связей включённый strict runtime разрешает
    их через registry без чтения YAML и не требует правки YAML при обновлении
    registry. Перед переключением проверены паритет известных обозначений,
    NHL-прогнозный цикл и обратимый возврат. Legacy-код остаётся доступным
    для явного отката; его удаление не входит в этот релиз.
14. При загрузке официального NHL schedule события календаря создаются по
    source event ID с подтверждёнными турниром и командами. Повторный импорт
    обновляет тот же матч, сохраняя его исходный ID и прогнозные ссылки.
    Загрузка не создаёт owner designation для каждого event ID. Отсутствие
    bookmaker котировки не препятствует прогнозу.
15. Подтверждённые словари рынков и исходов позволяют связать NHL/Pinnacle
    `h2h` с `winner_withOT` и исходами `home_win`/`away_win` без ничьей.
    Футбольный рынок с ничьёй не превращается в двухисходный; неизвестный
    или несовместимый рынок не присоединяет котировку.

## Границы и миграция

- Существующий [ADR-026](../../architecture/adr/ADR-026-calendar-and-data-cycle-control.md)
  использует `canonical_events.id` как публичный непрозрачный `event_id`.
  Этот вход/выход и source key сохраняются без потери ссылок. Уже созданные
  event entities и designation нельзя удалять до проверки миграции; они не
  являются целевым справочником для повседневного сопоставления котировок.
- `conf/bookmaker/team_name_registry/nhl.yaml` служит только исходным seed для
  первоначального переноса проверенных соответствий. Импорт не перезаписывает
  последующее решение владельца; код старого чтения удаляется позднее
  отдельным изменением после подтверждённой работы registry.
- Существующий [NHL source-state archive](../../architecture/adr/ADR-012-nhl-source-state-archive.md)
  использует Object Storage для проверяемых артефактов, но не является
  источником решений по идентичности. Registry получает отдельный prefix и
  контракт полного снимка с направлением локально → Object Storage → сервер.
  Версии, использованные обучением, сохраняются по политике воспроизводимости,
  независимо от краткоживущего source-state.
- Предлагаемый путь публикации: локальная система загружает неизменяемый
  снимок, проверяет его в Object Storage и только после этого обновляет
  указатель текущей версии. Серверный sync-процесс читает указатель, скачивает
  и проверяет снимок, затем атомарно устанавливает его в PostgreSQL. Runtime
  читает установленную версию из БД. Точный формат, частоту проверки,
  разрешения Object Storage и откат фиксирует ADR.
- Автоматические кандидаты допустимы, но неоднозначность не превращается в
  подтверждение по похожести строк. Допуск времени и правила взаимной
  уникальности определяются в ADR и проверяются тестами. Source event ID
  хранится с календарём или котировкой как provenance, а не как словарная
  привязка к каждому матчу.
- Production-переключение не выполняется автоматически при импорте seed.
  Старый путь чтения сохраняется для явного отката; после подтверждённого
  периода работы registry его удаляют отдельным проверенным изменением.

## Доказательства приёмки

- Автоматические тесты на идентичность, переименование, конфликт, решение
  владельца, повторный импорт и отсутствие неподтверждённой связи.
- Интеграционный сценарий для NHL и контрактный пример другого турнира с тем
  же механизмом, плюс регрессии календаря и прогнозной выдачи.
- Проверка локального offline-разрешения, версии в provenance обучения,
  полного экспорта и сохранения предыдущего серверного снимка при ошибке.
- Проверенный миграционный и откатный план, независимый review и terminal CI.
- Сценарий просмотра и изменения уже подтверждённой команды через веб при
  пустой очереди; audit/revision, новый snapshot и установка на сервер.
- Сверка всех перенесённых NHL-обозначений с legacy YAML и контрольный цикл
  после отключения YAML пути, без расхождения команд или прогнозов.
- Воспроизводимый импорт событий NHL API и котировок с проверкой повторного
  запуска, допуска времени, взаимной уникальности и сохранения несопоставленных
  записей; постоянные event designation для штатного случая не создаются.
- Веб-проверка словарей рынков и исходов, включая правила овертайма и ничьей;
  контрактный пример одинаковых имён игроков в разных командах и периодах.
