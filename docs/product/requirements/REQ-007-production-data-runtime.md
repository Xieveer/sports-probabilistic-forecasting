# REQ-007 — Автономный production data-runtime

> **Статус:** confirmed
> **Владелец продукта:** пользователь
> **Создано:** 2026-08-14

## Результат и ценность

Нужно подтвердить целевую жизненную модель данных и моделей, при которой VPS
самостоятельно и безопасно обновляет прогнозы независимо от доступности
устройства разработчика, а локальная разработка сохраняет воспроизводимое
обучение и контролируемую поставку моделей. Production должен обслуживать
турниры с разной частотой: ежедневный NHL, редкий футбольный турнир и
круглосуточный киберспорт с refresh до одного раза в 15 минут. Причина —
текущий контур release 1.0.1 реализует только materialization заранее
подготовленного `inference_long.parquet` и не соответствует этому назначению.
Первый functional release ограничен NHL, но архитектурные контракты не должны
быть привязаны к одному спорту, турниру, рынку или частоте refresh.

## Scope

- Продуктовое интервью и фиксация инвариантов: границы VPS, локального контура,
  Object Storage, PostgreSQL и DVC.
- Определение жизненного цикла: initial bootstrap, daily refresh, выгрузка
  server-to-local archive, обучение, promotion, rollback и разрешение конфликтов
  исторических данных.
- Разделение online operational store, аналитических snapshots и model/training
  compute с возможностью в будущем перенести обучение в облако.
- Ручное локальное обучение и ручное promotion; наблюдение drift рассматривается
  как будущая отдельная возможность и не является триггером обучения.
- Безопасная initial delivery уже имеющейся выбранной модели на VPS; сравнение
  кандидата с текущей production-моделью является последующей возможностью.
- Проверяемые требования к свежести, полноте истории, идемпотентности,
  оповещению Telegram, ресурсам и восстановлению.

## Non-scope

- Реализация, deployment, выпуск образов, изменения VPS и публикация релиза.
- Выбор конкретного scheduler, S3-клиента, БД или оркестратора до подтверждения
  продуктовых требований.
- Автоматическое или облачное обучение, автоматический promotion и реализация
  мониторинга drift.
- Автоматическое решение, что новая модель лучше текущей, и champion--challenger
  отчёт по единому набору исторических матчей.

## Сценарии

1. VPS по профилю турнира получает новые результаты и расписание, обновляет
   достаточную для корректных feature/EWM историю, строит витрину прогнозов и
   публикует digest только после успешного run. Успешный run требует получения
   и валидации финальных результатов всех ранее опубликованных прогнозов,
   матчи которых уже должны были завершиться.
2. Локальный контур получает проверяемый архив серверного состояния и использует
   его как обязательный контролируемый вход дальнейшей работы с историей и DVC
   перед каждым обучением или переобучением. Локальный контур строит features
   и EWM самостоятельно из полученных данных, не использует server-side
   processed features как training input. Каждый успешно committed refresh VPS
   публикует immutable snapshot manifest; локальный контур докачивает только
   отсутствующие или изменённые data partitions.
3. Локально одобренная модель доставляется на VPS в immutable bundle; VPS
   проверяет совместимость и может переключиться на предыдущий bundle.
4. Повторный запуск, неполные данные провайдера, поздняя коррекция результата,
   повреждённый архив или bundle не портят последнюю валидную витрину и не
   вызывают дублирующую отправку. При неполучении новых данных пользователь не
   получает ни устаревший, ни пустой прогноз; администратор получает безопасное
   операционное уведомление.

## Критерии приёмки

- [ ] Для каждого контура определены владелец, данные, допустимые операции и
  источник истины.
- [ ] Первый release обслуживает NHL, а идентичности данных, job, модели и
  витрины включают независимые sport/tournament/model-pool/market/spec границы;
  частота и quality rules задаются tournament profile.
- [ ] Указаны измеримые freshness/retention/RPO-RTO требования и условия,
  когда прогнозы разрешено публиковать.
- [ ] Частота refresh, допустимая задержка и политика при overlap/failure
  определены отдельно для каждого профиля турнира, а не зашиты в NHL schedule.
- [ ] При неуспешном refresh или недостижении freshness-критерия публичный API
  и Telegram не выдают прогноз по затронутому турниру; уведомление получает
  только администратор, а последняя валидная витрина сохраняется для аудита и
  восстановления.
- [ ] Успех refresh не определяется только транспортной доступностью источника:
  для всех ранее спрогнозированных и уже ожидаемо завершившихся матчей получен
  и пройден валидацию финальный результат.
- [ ] Для каждого tournament profile конфигурация задаёт максимальную
  длительность матча и grace period поставщика; deadline финального результата
  вычисляется из времени начала матча и этих параметров.
- [ ] Описан однозначный путь server-to-local: содержимое архива, верификация,
  импорт, provenance и правило разрешения конфликтов с локальной историей.
- [ ] VPS является единственным источником истины для исторических фактов,
  получаемых от поставщиков; локальное обучение использует только проверенный
  immutable snapshot VPS, зафиксированный в DVC/experiment provenance.
- [ ] Server-to-local archive содержит канонические данные, но не является
  training feature store: features/EWM строятся локально из snapshot текущими
  кодом и конфигурацией и фиксируются в provenance модели.
- [ ] Обучение и promotion выполняются только вручную из локального контура;
  отсутствие или будущий сигнал drift не запускает их автоматически.
- [ ] Уже выбранная production-модель может быть однократно доставлена с
  локального контура в immutable bundle с файлами inference, feature contract,
  metadata совместимости и checksum; VPS проверяет его до активации и не
  обучает модель.
- [ ] Initial bootstrap импортирует полную существующую локальную историю NHL
  в проверяемом immutable data bundle и не выполняет повторный сбор этой
  истории у внешних API; после успешного импорта VPS становится canonical
  источником последующих обновлений.
- [ ] Каждый успешно committed refresh VPS сразу публикует immutable snapshot
  manifest в Object Storage; следующая локальная подготовка обучения использует
  последний проверенный manifest и передаёт только изменившиеся partitions, а
  не полную копию истории.
- [ ] Описан однозначный путь local-to-server: bootstrap данных, model bundle,
  проверка, активация и rollback.
- [ ] Все архитектурно значимые решения имеют варианты, последствия и способ
  проверки до перехода к реализации.

## Ограничения, зависимости и риски

- Текущие REQ-005 и ADR-005 ограничивают VPS семью днями runtime-данных;
  изменение этого инварианта требует отдельного согласованного ADR и, вероятно,
  замены соответствующих частей REQ-005.
- EWM зависит от полной истории, а доказательство v1.0.1 измеряло только
  1 624 матча / 3 248 inference-строки и не подтверждает бюджет полного refresh.
- Текущая реализация EWM вычисляет Pandas `groupby → shift → ewm` по полному
  `matches_interim.parquet` и не хранит state/checkpoints. Для первого NHL
  release допустим полный пересчёт истории; stateful-инкрементальность для
  высокочастотных турниров требует отдельного подтверждённого решения,
  реализации и измерений.
- Локальный DVC хранит версии входов training run, но не является первичным
  источником исторических фактов: изменения поставщиков сначала применяются на
  VPS и затем поступают в локальный контур immutable archive.

## Предположения и открытые вопросы

- Предположение: первый production профиль — NHL `winner_withOT` утром в
  10:00 МСК; это не ограничивает целевую мультиспортивную архитектуру.
- Открыты: целевой freshness, допустимое окно неполных/исправленных результатов,
  состав полного runtime dataset, политика ручных исправлений поверх данных
  поставщика, RPO/RTO и объём истории.

## Подтверждение

Требование подтверждено владельцем продукта в интервью 2026-08-14. Оно заменяет
части REQ-005/ADR-005 о семидневном runtime dataset и compact serving-data
bundle, но не разрешает deployment, выпуск Git-тега или публикацию образов.
