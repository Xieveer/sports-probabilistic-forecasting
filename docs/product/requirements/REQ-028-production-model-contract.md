# REQ-028 — Контракт выбранной production-модели

> **Статус:** confirmed
> **Владелец продукта:** пользователь
> **Создано:** 2026-10-10
> **Инициатива:** [EPIC-028](../../backlog/EPIC-028-production-model-contract.md)

## Результат и ценность

Владелец выбирает проверенную модель для пары `model_pool / market_spec` и получает
регулярные прогнозы без правки Worker или API под алгоритм модели. Для каждого
опубликованного прогноза можно восстановить точный immutable bundle, контракт
признаков, время расчёта и вероятности, в том числе после следующей
материализации или отката. Это нужно для воспроизводимости выдачи и будущей
ссылки из журнала ставок.

## Scope

- Проверить согласованность выбранной версии в model registry, immutable bundle и
  реально загружаемом Worker артефакте до публикации.
- На изолированном контуре проверить одобренную legacy NHL CatBoost и локальный
  LightGBM для того же `nhl / winner_withOT` и того же состава исходов через
  один путь `bundle → Worker → materialize → витрина`.
- Сохранять неизменяемую версию опубликованного прогноза с `bundle_id`,
  `model_identity`, `feature_contract_id`, временем расчёта, рыночным ключом и
  вероятностями; текущую витрину оставить читаемой для API и бота.
- Проверить ручной rollback к ранее одобренному совместимому bundle.
- Проверить загрузку прежней одобренной NHL-модели на совместимом runtime.

## Non-scope

- Автоматический promotion по одной метрике, обучение новой production-модели,
  смена действующего NHL pointer и production-развёртывание.
- Внедрение нового турнира, рынка, источника коэффициентов или журнала ставок.
- Перенос всех исторических прогнозов, для которых точный bundle неизвестен.

## Сценарии

1. Владелец явно выбирает кандидата для пары `model_pool / market_spec`.
   Проверенный bundle активируется на тестовом контуре; Worker использует именно
   его, сохраняет прогноз и API читает результат.
2. Затем выбирается локальная LightGBM-модель. Один и тот же Worker и
   API работают без изменений их алгоритмического кода; прежний прогноз остаётся
   доступен как отдельная версия.
3. Bundle повреждён, не соответствует runtime или выбранной паре
   `model_pool / market_spec`. Активация или публикация останавливается;
   прежняя валидная витрина остаётся доступной.
4. Ручной rollback возвращает ранее проверенный bundle. Новые прогнозы
   ссылаются на него, а версии прогнозов до rollback сохраняются.
5. Совместимый runtime загружает прежнюю одобренную NHL-модель без обучения и
   без подмены её неизвестных provenance-полей вымышленными значениями.

## Критерии приёмки

- [ ] На изолированном контуре legacy NHL CatBoost и локальная LightGBM-модель
  того же `winner_withOT` проходят один путь загрузки и публикации без изменения
  Worker и API между активациями.
- [ ] Каждая новая опубликованная версия прогноза имеет стабильный ID, точный
  `bundle_id`, `model_identity`, `feature_contract_id`, время расчёта и полный
  набор вероятностей для явно заданного `market_spec` и outcomes. Повторная
  материализация сохраняет прежнюю версию; API продолжает показывать актуальную.
- [ ] Bundle, не прошедший проверку целостности, совместимости или соответствия
  выбранной модели/рынку, не меняет действующий pointer и текущую публикацию.
- [ ] Ручной rollback на проверенный совместимый bundle успешен; версия прогноза,
  созданная до отката, остаётся доступной по своему ID.
- [ ] Прежняя одобренная NHL-модель загружается на совместимом runtime;
  неизвестные поля её истории остаются явно неизвестными.

## Ограничения, зависимости и риски

- Сейчас `runtime_root/current` — файловый pointer на один bundle, а
  `model_deployments.is_active` — DB pointer на пару `model_pool / market_spec`.
  `materialize` берёт `model_identity` из registry отдельно от загрузки файла;
  достаточного доказательства их совпадения пока нет. Источник истины и правило
  атомарной активации требуют ADR до реализации.
- `Prediction` хранит текущую строку: `upsert_prediction` перезаписывает
  вероятности, `prediction_ts` и provenance. Поле `immutable_model_version`
  является identity из registry, но не `bundle_id`. `feature_contract_id` может
  формироваться из runtime Hydra-конфигурации; связь с bundle требует проверки.
- Для NHL `model_pool` может отсутствовать, а legacy provenance может быть
  неполным. Нельзя объявить такую строку точно воспроизводимой задним числом.
- EPIC-027 создаёт историю коэффициентов. Версия прогноза должна получить
  стабильный ID для будущей ссылки журнала ставок; при наличии подходящего
  наблюдения коэффициентов — ссылку на его immutable ID. Схему общей БД и
  миграции согласовать с EPIC-027 перед разработкой, не создавать их в этом REQ.
- В репозитории есть legacy NHL manifest и конфигурация LightGBM, но нет самих
  проверенных model payloads. Одобренный NHL bundle нужно предоставить
  изолированному контуру; LightGBM допустимо обучить только как локальный тестовый
  fixture на совместимом входе, не продвигая в production. Если у legacy bundle
  отсутствует точный контракт исходов, сначала установить его по артефакту.

## Предположения и открытые вопросы

- **Технический blocker:** найти одобренный legacy NHL payload для изолированного
  теста. Ссылка в `conf/legacy/nhl-model-manifest.yaml` и REQ-019 указывает на
  артефакт вне Git; наличие на локальном контуре ещё не проверено.
- **ADR:** выбрать источник истины, соответствие registry и файлового pointer,
  а также cardinality pointer для будущих пар `model_pool / market_spec`.
- **Предположение о первом срезе:** проверить последовательную замену моделей
  одной пары; одновременная публикация нескольких пар остаётся за EPIC-029.
- **Предположение о доступе:** для истории достаточно устойчивого внутреннего ID;
  внешний API для получения произвольной прежней версии пока не требуется.
- **Предположение:** переключение production pointer остаётся ручным после
  проверки кандидата; это соответствует [REQ-003](REQ-003-scalable-multisport-platform.md).
- **Предположение:** старые NHL-прогнозы без достоверного `bundle_id` не получают
  искусственно заполненный ID при миграции.

## Подтверждение

В диалоге 2026-10-10 владелец подтвердил проверку пары «legacy NHL и модель
другого алгоритма на локальном контуре». Из доступных конфигураций для второго
алгоритма выбран LightGBM. Прочие критерии наследуют проверяемый результат
[EPIC-028](../../backlog/EPIC-028-production-model-contract.md); допущения о
первом срезе перечислены выше. Production pointer не меняется.
