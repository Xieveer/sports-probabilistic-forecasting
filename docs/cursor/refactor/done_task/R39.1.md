## Решение

Зафиксирован **prod-like** операционный контракт R39 в runbook NHL: последовательность стадий **триггер DAG → refresh (source … materialize) → validate → digest** (digest — планируемый финальный шаг); явно указано, что канонический путь — **один триггер Airflow** после появления digest в DAG, а `make nhl-morning-test-notify` / `scripts/run_nhl_refresh_notify.py` — **временный** обходной путь вне DAG, не заменяющий целевой хвост.

Добавлен **чеклист «от триггера DAG до сообщения»** (с пометкой текущего состояния до R39.5), таблицы **Airflow Variables** (`SF_PROJECT_DIR`, `SF_UV_RUN`, pool/lock, NHL- и data_refresh-специфичные) и **переменных окружения** для compose/API/бота/worker Airflow. В `.env.example` — блок про prediction store для хостового CLI и комментарий про будущие `SF_TELEGRAM_DIGEST_*` / `SF_POST_REFRESH_DIGEST_CMD`. В `docs/deploy/secrets.md` — требование доступности тех же секретов бота и Odds API для **процесса Airflow** на VPS, не только для `api`/`telegram-bot`.

## Проблема (из эпика R39)

Нужен **операционный e2e-контракт в документации**: чеклист от триггера DAG до финального сообщения, явный перечень env и Airflow Variables, без представления glue-скрипта как единственного канонического пути.
