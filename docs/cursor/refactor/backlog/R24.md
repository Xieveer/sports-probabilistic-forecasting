# R24. Telegram: UX как у панели пользователя

> **Статус:** 🟡 В работе
> **Приоритет:** 🟡 Medium
> **Сложность:** Medium

---

## Проблема

Бот (R19.13–R19.16) уже даёт `/predict`, `/upcoming`, `/status`, `/refresh`, `/models`, но это **MVP по командам**. Нужен отдельный эпик на превращение Telegram в понятный UI: меню, подписки, безопасный админ-контур, устойчивость к сбоям API — **без** смешения с обучением (**R22**) и пайплайном деплоя (**R23**).

**Граница эпика:** только `sports_forecast/bot/`, конфиг `conf/bot.yaml`, при необходимости небольшие контракты с API — не CI и не ML.

---

## Связь с другими эпиками

- Зависит от работающего API (локально или после **R23**); разработку **R24.1–R24.2** можно вести против `make api-dev`.
- Админ-команды (**R24.3**) должны согласовываться с тем, что реально доступно на сервере (Airflow REST, логи) после **R23**.

---

## Что сделать

- [ ] **R24.1** Inline-меню и навигация: главный экран после `/start` — кнопки «Прогнозы», «Расписание», «Статус»; вложенные меню турнир → матч → детали; `CallbackQuery` с префиксами (`predict:{tournament}:{game_id}`).
- [ ] **R24.2** Уведомления: daily digest на сегодня; таблица подписок (SQLite/Postgres); `/subscribe` / `/unsubscribe`; планировщик (`apscheduler` или триггер из Airflow).
- [ ] **R24.3** Safe admin: отдельное меню для `admin_user_ids`; `/retrain` (если есть endpoint/DAG trigger), `/logs`, `/health`; подтверждение перед destructive действиями.
- [ ] **R24.4** UX и устойчивость: дружелюбные ошибки при падении API; rate limit per user; логирование команд для usage-аналитики.
