# R26. Единый контракт odds для беттинг-метрик в `train` (NHL + масштабирование)

> **Статус:** 🟡 В работе
> **Приоритет:** 🟡 Medium
> **Сложность:** High

---

## Проблема

Для **киберхоккея (UEL)** и **настольного тенниса (LP)** беттинг-метрики в `SingleExperimentRunner` уже считаются на **test**: коэффициенты попадают в `odds_raw` (строка Python-dict), маппинг ключей задаётся в `conf/bookmaker/fonbet.yaml`, извлечение — `extract_odds_from_raw` → `BettingSimulator`.

Для **NHL** линии приходят из **The Odds API** и после `merge_odds_into_source_dataframe` лежат в **wide-колонках** в `source.csv` (реестр команд + дата матча + home/away; один матч на календарный день — контракт merge уже есть). В `conf/tournament/nhl.yaml` эти поля **не проходят** в `data_clean.select_columns` → в **processed `train_long`** нет ни `odds_raw`, ни числовых closing-колонок → `_compute_business_metrics` фактически **не видит** коэффициентов при `bookmaker=fonbet` по умолчанию в корневом `config.yaml`.

В результате **один и тот же тренер** ведёт себя по-разному по турнирам: где odds в dict — метрики есть; где odds в merge wide — их нет, без отдельного CLI.

Цель эпика: **воспроизвести UX «как UEL/LP»** — при обучении NHL (и будущих турнирах с merge-odds) на holdout/test снова считаются **те же** беттинг-метрики, с **конфигурируемым** букмекером и **единым** путём данных (`odds_raw` и/или явный transport в YAML), без отдельного одноразового eval-модуля под один бук.

---

## Принципы (масштабирование)

1. **Один вход для тренера**: по возможности сохранить вызов из `trainer.py` через общую функцию вида `extract_betting_odds(df, market_spec, bookmaker_cfg)` (имя на усмотрение worker), внутри — ветвление по `bookmaker_cfg` / `odds_transport`, без копирования `BettingSimulator`.
2. **Конфиг, а не код**: имена колонок store / source (Pinnacle close, 1xbet, …), ключи synthetic `odds_raw`, привязка `market_spec` → источник decimal — в **YAML** (`conf/bookmaker/the_odds_api.yaml` и/или `conf/source/nhl.yaml`), чтобы новый турнир = новый конфиг + реестр, а не новый модуль.
3. **Фичи не течут**: `odds_raw` и прочие odds-колонки остаются **вне** обучаемых признаков (текущие исключения в `column_utils` / `_common` — проверить и дополнить при появлении новых имён).
4. **Формулы vs рынок**: логику «decimal на сторону игрока в long» и 2-way implied (если нужна бенчмарк-вероятность рынка) держать в **одном** месте — `sports_forecast/betting/` (или `data/providers/odds/`) с юнит-тестами, чтобы train и будущие отчёты не расходились.

## Риски

- **Дублирование объёма данных** в parquet, если хранить и wide odds-колонки, и fat `odds_raw` — оценить размер; приоритет — корректность и один контракт.
- **Семантика рынка** (regulation vs OT) уже задана в `bookmaker_profiles`; ошибка в ключах → тихая деградация метрик — усилить тестами и логами покрытия.
- **Prod train+test** (существующая политика) искажает интерпретацию метрик; в доке R26 явно указать: train-time betting = «на test-срезе с теми odds, что в таблице», не претендует на чистый OOD для prod-весов.

---

## Критерий готовности эпика

На `tournament=nhl_train`, `market=winner_withOT`, `market_spec=winner_withOT`, при непустом merge odds в source: в логе тренинга снова появляется блок **«БИЗНЕС-МЕТРИКИ (BettingSimulator)»** с ненулевым числом валидных odds; метрики уходят в MLflow как для LP/UEL. Новый турнир с merge-odds может подключиться **конфигом**, без отдельного eval-модуля под одного букмекера.
