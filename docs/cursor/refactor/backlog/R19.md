# R19. NHL — полный production-цикл + Odds API + Telegram-бот

> **Статус:** 🟡 В работе
> **Приоритет:** 🔴 High
> **Сложность:** High

---

## Проблема

R17 создал провайдер данных `NhlWebApiSourceProvider` (ingest из NHL Web API → `source.csv`), конфигурации `ice_hockey`, `source/nhl`, `tournament/nhl` и юнит-тесты. Однако NHL-турнир не интегрирован в production-цикл проекта:

1. **Нет инкрементального обновления.** `NhlDataAssembler` выполняет полный проход от `date_from` до `date_to` при каждом запуске. Для ежедневного refresh через Airflow нужен режим «только новые матчи».
2. **Нет коэффициентов букмекеров в слое данных.** В R17 odds были явно вне скоупа. Для **валидации и бенчмарка** моделей на тестовых данных нужны opening/closing линии (Pinnacle) — внешний источник [The Odds API](https://the-odds-api.com/liveapi/guides/v4/#overview). Политика: **кэфы из The Odds API не идут в feature pipeline** (историческая глубина линий у провайдера ограничена; для проверки модели достаточно **2–3 сезонов** истории кэфов). Подробно: `docs/cursor/source_data/the_odds_api.md`.
3. **Нет прохождения через полный pipeline.** NHL не включён в DVC `features` multirun, нет trained-моделей, нет materialize, нет отображения в API.
4. **Бедный feature engineering.** `data_clean.select_columns` в `tournament/nhl.yaml` отбрасывает большую часть статистики NHL (SOG, hits, PIM, BS, FOW, standings, rosters). Для хоккея нужны специфические фичи: schedule density, усталость, roster-фичи, team ratings.
5. **Нет Telegram-бота.** Пользователь хочет «центр управления» для получения прогнозов и операций по сервису.

**Цель:** NHL как полноценный production-турнир: ежедневный инкрементальный refresh → сохранение кэфов (The Odds API) в `source` для валидации/бенчмарка → clean → features (**без** odds-колонок) → train → materialize → API → Telegram-бот.

---

## План (фазы и зависимости)

### Фаза 1 — Инкрементальный refresh + pipeline integration

Включить NHL в рабочий контур `data_refresh` DAG с инкрементальной загрузкой. Расширить `data_clean` чтобы пропускать NHL-статистику. Добиться прохождения ingest → clean → features для NHL.

Зависимости: ничего (фундамент для всех последующих фаз).

### Фаза 2 — The Odds API (сбор кэфов, не фичи)

Создать HTTP-клиент для The Odds API, backfill с экономией квоты на **окно 2–3 сезонов** (достаточно для валидации на тестовых данных), merge в `source.csv` для офлайн-анализа. Колонки кэфов **не подключать** к генераторам фич и не использовать в обучении. См. `docs/cursor/source_data/the_odds_api.md`.

Зависимости: R19.1 (инкрементальный assembler) для понимания merge-логики.

### Фаза 3 — NHL-специфичный feature engineering (MVP)

Расширить feature pipeline NHL-специфичными фичами: schedule density, rest/fatigue, standings-based ratings, roster features. Фазированно: MVP-фичи и stretch.

Зависимости: R19.3 (расширенные clean-колонки).

### Фаза 4 — Training + production cycle

Первый baseline training sweep, promote, materialize, проверка в API.

Зависимости: Фазы 1 + 3 (features должны быть готовы).

### Фаза 5 — Telegram-бот

Scaffolding aiogram 3, команды прогнозов, операционные команды, деплой.

Зависимости: R19.12 (API должен отдавать NHL-прогнозы).

### Фаза 6 — Stretch (документировать пробелы, реализовать при наличии времени)

Продвинутые фичи: travel distance, motivation/clinch context, injury report. (Odds-фичи не планируются — см. The Odds API policy.)

- [ ] **R19.1** Инкрементальный режим `NhlDataAssembler`: при наличии `source.csv` определить дату последнего завершённого матча и установить `date_from` от неё (минус буфер 3 дня на корректировки). Добавить параметр `incremental: true/false` в `conf/source/nhl.yaml`. Полный режим остаётся для первоначальной загрузки.
- [ ] **R19.2** Source-refresh команда для NHL в Airflow: реализовать shell-команду (аналог `SF_SOURCE_REFRESH_CMD` с `{tournament}`), которая вызывает `provider.fetch()` в инкрементальном режиме. Добавить `nhl` в `SF_REFRESH_TOURNAMENTS`. Учесть, что NHL refresh медленнее CSV-турниров (отдельный execution_timeout).
- [ ] **R19.3** Расширить `conf/tournament/nhl.yaml` — `data_clean.select_columns` должен пропускать расширенный набор: все FT/MT-статистики (SOG, hits, PIM, 2PIM, BS, FOW), standings (conference_standing, P, GP), game_type, match_end, season. Добавить `column_mapping` и `dtype_mapping` в `conf/sport/ice_hockey.yaml` для новых колонок. Валидация Pandera — расширить схему.
- [ ] **R19.4** Включить NHL в DVC `features` multirun: добавить `nhl` в список турниров в `dvc.yaml` стадии `features`. Верифицировать end-to-end pipeline: `ingest → clean → features` на небольшом срезе данных. Зафиксировать smoke-test.

### Фаза 2 — The Odds API (валидация / бенчмарк, не обучение)

- [ ] **R19.5** HTTP-клиент `OddsApiClient` (`sports_forecast/data/providers/odds/client.py`): requests-based, API key из `os.environ["ODDS_API_KEY"]`, quota tracker (headers `x-requests-remaining` / `x-requests-used`), rate limiting, retry (429/5xx), кэширование ответов в JSON-файлы (idempotent re-fetch). Фокус на endpoint `/v4/sports/{sport}/odds/` и `/v4/historical/sports/{sport}/odds/`. Читать параметры из `conf/bookmaker/the_odds_api.yaml` (или `load_bookmaker_config("the_odds_api")`).
- [ ] **R19.6** Модуль backfill odds (`sports_forecast/data/providers/odds/backfill.py`): идемпотентное заполнение **окна 2–3 сезонов** (целевой горизонт для тестовой валидации; не гонять всю историю NHL). Pinnacle opening + closing lines где доступно. Batching по дате (один запрос = один день), кэш на диск, пропуск закэшированных дат. CLI с параметрами `--from` / `--to`. Экономия квоты: см. `docs/cursor/source_data/the_odds_api.md`.
- [ ] **R19.7** Merge кэфов в `source.csv` для офлайн-использования: merge odds → source по game_date + teams (fuzzy match). Колонки (пример): `pinnacle_home_open`, …, `pinnacle_total_close`. В `data_clean` для NHL: пропускать колонки в **отдельной** группе или явно **исключить** из списка признаков в `conf/features`/tournament (кэфы **не** входят в модель). Обновить `conf/source/nhl.yaml` секцию `odds: enabled: true`. Зафиксировать в коде/конфиге, что odds-колонки не подаются в `FeaturePipeline`.

### Фаза 3 — NHL-специфичный feature engineering (MVP)

Фичи: `days_since_last_game` (home/away), `games_in_last_7d`, `games_in_last_14d`, `is_back_to_back`, `rest_advantage` (разница дней отдыха). Данные берутся из interim (datetime + team). - [ ] **R19.9** Standings/ratings фичи: `NhlStandingsFeatureGenerator`. Фичи: `conf_rank_diff`, `points_pct` (P / (GP*2)), `points_pct_diff`, `recent_form_5` (W-L из последних 5 игр, вычисляется из interim). Используют колонки `conference_standing`, `P`, `GP` из interim. Конфиг: `conf/features/generators/standings/nhl.yaml`.
- [ ] **R19.10** Roster-фичи (MVP): `NhlRosterFeatureGenerator`. Парсинг JSON-колонки `home_roster`/`away_roster` → `roster_size`, `avg_player_age` (birth_date → age на дату матча), `num_forwards/defensemen/goalies`. ## Data gaps и ограничения

| Проблема | Влияние | Mitigation |
|----------|---------|------------|
| NHL Web API неофициальный | Контракт может измениться | Абстракция через client; версионирование парсинга |
| Injury report — заглушка | Roster-фичи неполные | R19.20 (stretch): внешний источник |
| Odds API quota ограничен | Backfill «всей истории» не нужен для валидации | Целевое окно **2–3 сезона** кэфов; кэширование |
| Кэфы The Odds API — короткая история vs train | Нельзя использовать как признаки на всём train-окне | Кэфы только для валидации/бенчмарка; см. `the_odds_api.md` |
| Старые сезоны — неполные boxscore | MT-статистика может быть пустой | Fallback на FT; фильтр `season_id_min` |
| EWM зависит от полной истории | Инкрементальный refresh всё равно пересчитывает features | Известное ограничение; stateful EWM — отдельный эпик |
| Travel distances — нет официального источника | Travel-фичи приблизительные | Статический справочник арен в YAML |

## Assumptions

1. **Формат API The Odds API v4** — стабилен; endpoint `/v4/historical/sports/{sport}/odds/` доступен в рамках подписки пользователя.
2. **Pinnacle** часто присутствует как bookmaker в ответах для NHL; при отсутствии в конкретном дне — пропуск/NA, не блокировка пайплайна.
3. **Кэфы не входят в модель** — политика зафиксирована в `docs/cursor/source_data/the_odds_api.md` (ограниченная историческая глубина сбора линий у провайдера).
4. **aiogram 3** — фреймворк для бота; polling-режим для MVP, webhook — stretch.
5. **Auth бота** — whitelist Telegram user_id (не OAuth, не пароль); достаточно для personal use.
6. **NHL feature generators** — реализуются как отдельные классы-генераторы, встраиваемые в существующий `FeaturePipeline` через конфиг (аналогично `time`/`form`/`rolling`).
7. **Бот общается с FastAPI** через HTTP (не через прямой import) — для изоляции контуров.

3. **Travel features:** есть ли предпочтения по источнику координат арен (ручной справочник vs API)?
