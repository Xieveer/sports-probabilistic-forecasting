# R37. NHL: локальный стек, 48h прогнозы, Pinnacle + edge, ежедневный пайплайн (12:00 MSK) → Telegram

> **Статус:** ✅ Выполнено
> **Приоритет:** 🔴 High
> **Сложность:** High

---

## Проблема

Модели для NHL (`winner_withOT` и др.) и пайплайн CatBoost + Optuna + walk-forward закрыты, но **операционный контур** для ежедневного потребления прогнозов (в т.ч. в Telegram) требует явной связки: работающий локальный стек (API, БД, материализация, при необходимости Airflow), **выборка предстоящих матчей NHL на 48 часов**, в каждом элементе — **выход модели**, **актуальные decimal-коэффициенты Pinnacle** с The Odds API (или согласованный с существующей интеграцией путь), и **решение bet / no-bet** по настраиваемому порогу edge. Дополнительно нужен **ежедневный запуск в 12:00 по Москве**: обновление данных NHL, истории коэффициентов, фич, материализация предиктов для последующей выдачи боту.

Текущее состояние репозитория (ориентиры для исполнителя):

- Архитектура read-only API и batch-пайплайнов: `docs/cursor/context/service_orchestration_architecture.md`.
- FastAPI: `sports_forecast/service/routers/predictions.py` (`/predict/upcoming/{tournament}` без временного окна; `_to_response` не отдаёт `odds_raw`).
- ORM: `sports_forecast/service/db/models.py` — колонка `odds_raw` уже есть; обогащение ответа и «живые» Pinnacle не зафиксированы в публичной схеме.
- The Odds API: `sports_forecast/data/providers/odds/client.py` (`OddsApiClient`), конфиг `conf/bookmaker/the_odds_api.yaml`; бэкфилл/инкремент — `sports_forecast/data/providers/odds/backfill.py` (контекст R20/R21).
- Материализация: `sports_forecast/materialize.py` — уже может писать `odds_raw` из processed, если колонка есть в фичах.
- Оркестрация: `airflow/dags/dag_data_refresh.py` (`data_refresh`, расписание каждые 4 ч), `sports_forecast/orchestration/cron_refresh.py` (хостовый cron), `Makefile` — `api-dev`, `docker-up`, `airflow-up`, `materialize`, `db-init`.
- Telegram: `sports_forecast/bot/handlers/predict.py`; эпик UX — `docs/cursor/refactor/backlog/R24.md` (подписки/digest частично пересекаются с R37.7).

**Связь с соседними эпиками:** R24 (Telegram UX), R15 (operations.rst), R33 (`market`/`market_spec`), при необходимости — уточнение строк в R22.7 (не блокер для operational edge API).

1. **Документация и среда** — воспроизводимый локальный запуск стека и переменных окружения.

## Что сделать

- [x] **R37.1** Локальный operational runbook: единый документ (предпочтительно расширение `docs/source/operations.rst` при работе R15 **или** отдельный раздел `docs/source/nhl_local_operations.rst` с включением в toctree) с пошаговым чеклистом: `make init` / `uv sync`, `make db-init`, `make api-dev`, `make docker-up` (состав сервисов из `docker-compose`), `make airflow-init` + `make airflow-up`, переменные из `.env.example` (`ODDS_API_KEY`, при боте — `BOT_*`), smoke-проверка `/health` и `/docs`.
  **Критерии приёмки:** документ с таблицей команд Makefile ↔ эффект; явное указание, что API runtime не считает фичи (ссылка на architecture); минимум одна smoke-команда на репозитории (например `curl` к `/health`) в тексте; без дублирования секретов — только имена переменных.

- [x] **R37.2** Репозиторий и HTTP: окно **следующие 48 часов** для предстоящих матчей — расширить `PredictionRepository.get_upcoming_predictions` (фильтр по `match_datetime` от «сейчас» UTC до `now + hours`, параметр `hours` по умолчанию 48) и пробросить в `GET /predict/upcoming/{tournament}` (`sports_forecast/service/routers/predictions.py`). Для NHL документировать в OpenAPI использование `market=winner` / `market_spec=winner_withOT` (или актуальные имена из `conf/market*`) согласованно с R33.
  **Критерии приёмки:** юнит-тест(ы) на фильтр времени; матчи без `match_datetime` явно исключаются или документировано поведение; ответ остаётся совместимым для турниров без изменения клиента (дефолтное окно может быть «без ограничения» **или** 48h — **зафиксировать одно поведение в описании задачи при реализации**).

- [x] **R37.3** Конфигурируемый **edge threshold** и чистая функция **bet / no_bet / insufficient_data**: новый узел (например `conf/service_api.yaml` или секция в `conf/betting.yaml`) с ключами `edge_threshold`, при необходимости `min_odds`, читаемый через Hydra/settings; логика сравнения модельной вероятности с implied prob из decimal odds (переиспользовать идеи из `sports_forecast/betting/odds.py`, без дублирования парсинга).
  **Критерии приёмки:** типизированная функция + тесты на порог (выше/на границе/ниже); порог задаётся конфигом без хардкода в роутере.

- [x] **R37.4** **Текущие коэффициенты Pinnacle** для предстоящих событий NHL: модуль поверх `OddsApiClient` (новый файл рядом с `data/providers/odds/`), маппинг событий The Odds API ↔ `match_id` турнира NHL (конфиг ключей в `the_odds_api.yaml` или отдельный mapping-узел). Обработка отсутствия линии / частичных данных.
  **Критерии приёмки:** unit-тест с моками HTTP или записанным фикстурным JSON; лимит квоты Odds API учтён (reuse `max_real_http_requests` где уместно); в логах нет секретов.

- [x] **R37.5** **Публичный payload** предсказания: расширить Pydantic-схемы (`sports_forecast/service/schemas.py`) полями для отдачи модели, **decimal Pinnacle** (home/away или структура по `market_spec`), вычисленного **edge**, **`bet_decision`**, при ошибке odds — явный статус/флаг. Решить и задокументировать: обогащение на этапе **повторного чтения из БД** (вызов odds внутри GET — только лёгкий HTTP) vs запись снимка при batch (materialize/DAG) в `odds_raw` или отдельной колонке (**миграция БД** при необходимости, см. `sports_forecast/service/migrations` если есть). Согласовать с принципом «API не считает тяжёлые фичи» из architecture doc.
  **Критерии приёмки:** OpenAPI отражает новые поля; для `/predict/{match_id}` и `/predict/upcoming/...` единый контракт там, где применимо NHL; если добавлена миграция — `db-init` / документация обновлены.

- [x] **R37.6** **Расписание 09:00 UTC = 12:00 MSK**: добавить операционный артефакт — либо новый DAG Airflow (например `nhl_morning_refresh` в `airflow/dags/`) с `schedule` в UTC и комментарием эквивалента MSK, либо шаблон crontab с **`CRON_TZ=Europe/Moscow`** и строкой `0 12 * * *`, вызывающий существующую цепочку (`cron_refresh` / bash из `build_refresh_per_tournament_command` только для `nhl`, затем инкремент odds при необходимости, затем materialize для `winner_withOT`). Переменные Airflow (`SF_*`) согласовать с текущими DAG.
  **Критерии приёмки:** в коде или README операций явно записаны оба представления времени (MSK и UTC); один проверяемый путь «как запустить вручную» теми же командами, что и DAG/cron; не ломает `max_active_runs`/lock контракт refresh-пула.

- [x] **R37.7** **Telegram:** обновить `sports_forecast/bot/handlers/predict.py` (и при необходимости `conf/bot.yaml`) так, чтобы команды расписания/«предстоящие» для NHL потребляли обогащённый API-ответ (HTTP к `API_BASE_URL`) или общий сервисный слой; краткая документация в комментарии к `bot.yaml`. При пересечении с R24.2 — не дублировать планировщик, а переиспользовать или явно указать «минимальный MVP без apscheduler до слияния R24».
  **Критерии приёмки:** бот показывает для NHL блок с edge и bet/no-bet при доступном API; graceful degradation при отсутствии `ODDS_API_KEY`.
