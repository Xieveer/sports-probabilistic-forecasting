# R13. Выравнивание реализации с Service & Orchestration Architecture

> **Статус:** 🟡 В работе
> **Приоритет:** 🔴 High
> **Сложность:** Medium

---

## Проблема

Текущая реализация в целом следует целевой схеме "API читает, пайплайны считают", но есть несколько расхождений с архитектурным контрактом из `service_orchestration_architecture.md`.

Критичные точки: `data_refresh` не включает явный этап `validate`, материализация опирается на локальную файловую структуру моделей вместо явного контракта с promoted-артефактом, а `training_sweep` использует единый `promote_best` для потенциально мульти-турнирного запуска. Дополнительно отсутствует формализованный operational-контракт по DVC runtime между окружениями.

---

## Что сделать

- [x] **R13.1** Добавить этап валидации в `data_refresh` DAG (`ingest → clean → features → validate`) и зафиксировать fail-fast поведение.
- [x] **R13.2** Ввести явный прод-контракт materialize: использовать артефакт, выбранный promote (через `deploy.yaml`/метаданные), а не только `algorithm/features` из переменных DAG.
- [x] **R13.3** Исправить `training_sweep` для мульти-турнирного режима: promote должен выполняться по каждому турниру/эксперименту отдельно.
- [x] **R13.4** Зафиксировать operational-контракт DVC по средам (prod/dev/CI): где разрешены прямые вызовы модулей, где обязателен `dvc repro`, как синхронизируются артефакты.
- [x] **R13.5** Декомпозировать контур обновления по турнирам без пропуска обязательных стадий: для изменённого турнира запускать `source → ingest → clean → features → materialize`, а также определить политику конкуренции (pool/lock/max_active_runs).
- [x] **R13.6** Разделить read-only API и операционные endpoint-ы (cache/stale) на уровне контракта и документации, чтобы не размывать SLA публичного слоя.
- [ ] **R13.7** Добавить smoke/integration проверки оркестрации (DAG-команды + CLI связка train/promote/materialize) как acceptance для архитектурного контура.
