# R39. Prod-like E2E: Airflow → данные/odds → фичи → promoted model → БД → live Pinnacle → один Telegram digest

> **Статус:** 🟡 В работе
> **Приоритет:** 🔴 High
> **Сложность:** High

---

## Проблема

Контур **refresh + materialize** уже оркестрируется через Airflow (`data_refresh`, `nhl_morning_refresh`) и `cron_refresh`: для каждого турнира выполняется `source → ingest → clean → features → materialize` с **promoted** моделью через контракт `models/.../best/deploy.yaml` / `model_version=prod` (см. `refresh_command.build_refresh_per_tournament_command`). Запись предсказаний идёт в **Prediction Store** (БД).

**Разрыв:** сравнение модели с **текущими** decimal Pinnacle (The Odds API) и расчёт **edge / bet-decision** сейчас в основном живут в **HTTP-слое** (`sports_forecast/service/live_odds_enrichment.py` при `live_pinnacle=true` на `GET /predict/*`). Операционный сценарий «утро NHL» заканчивается **validate**, а итоговая сводка для людей — либо через **adhoc** `scripts/run_nhl_refresh_notify.py` (отдельный клей), либо через интерактив бота по запросу. Нет **одного** триггерного пути Airflow, который гарантированно завершает цепочку **одним согласованным Telegram-сообщением** (edge/value vs Pinnacle или эквивалентный формат) без разброса отладочных постов и без обхода существующих **pool / flock / секретов** (R13, R23, R37).

Нужно закрыть gap между «данные обновились и витрина записана» и «оператор видит сводку против live Pinnacle» в рамках **той же** оркестрации, что и prod, на **локальном стеке** с тем же поведением.

---

## Предположения (assumptions)

1. **Первый scope — NHL**, рынок **`winner_withOT`** / спека **`winner_withOT`**, фичи как в утреннем DAG (`advanced` по умолчанию); обобщение на другие турниры — только после стабильного контракта (конфигом/переменными Airflow).
2. **Live Pinnacle** для сравнения — тот же провайдер и маппинг, что уже используются в `live_nhl_pinnacle` / `live_odds_enrichment` (не новый парсер).
3. **Promoted model** остаётся источником истины для инференса; в digest достаточно **короткой строки provenance** (например путь/тег из `deploy.yaml` или MLflow run id), без повторного обучения в этом эпике.
4. Airflow workers (и локальный compose) имеют доступ к **той же БД**, что и API, и к **`ODDS_API_KEY`** для Odds API при включённом digest; при отсутствии ключа — **graceful** текст в одном сообщении (как статусы `live_odds_status`).

## Риски

| Риск | Митигация |
|------|-----------|
| **Повтор Telegram при retry** Airflow | Явный флаг `SF_TELEGRAM_DIGEST_ENABLE`, короткий timeout; опционально dedup по `dag_run.run_id` + `task_id` (файл-маркер или запись в БД) — зафиксировать минимально достаточный вариант в R39.5/R39.7 |
| **Квота Odds API** | Переиспользовать существующий клиент с лимитами/кэшем; один батч на прогон как в API-слое |
| **Расхождение чисел** digest vs публичный API | Общая функция расчёта edge/decision от `Prediction` + quotes; регрессионный тест на равенство с текущим enrichment |
| **Секреты в worker** | Документировать переменные (`.env.example`, `docs/deploy/secrets.md`, `nhl_local_operations.rst`); не логировать ключи |

- **R19 / R20 / R21** — Odds API, store, маппинг событий (done).

- **R24** — UX бота / подписки; этот эпик **не** заменяет R24: digest — **операционное** уведомление по завершении пайплайна, а не полноценное меню/подписка.

## Non-goals

- Новый временной ряд **live odds** в БД (audit-колонки) — вне scope; при необходимости отдельный эпик.
- Полная унификация **всех** турниров в одном DAG без явного конфига.
- Замена **monitoring DAG** (R4) или качественно новый Prometheus-контур — только точечные логи/метрики, если уже есть Hooks.
- Рефакторинг всего **prediction_materialize** DAG под один mega-DAG — только согласованные границы задач и документация.

## Что сделать

- [x] **R39.1** **Операционный контракт e2e (док + переменные).** Зафиксировать целевую последовательность: после `materialize` и `validate` — финальный шаг **digest** (тот же стек, что prod). Дополнить `docs/source/nhl_local_operations.rst` (или согласованный существующий runbook) подразделом: локальный compose + Airflow Variables (`SF_PROJECT_DIR`, `SF_UV_RUN`, `SF_REFRESH_*`, `ODDS_API_KEY` на worker, опция `SF_TELEGRAM_DIGEST_*` / `BOT_*`).
  **Критерии приёмки:** чеклист «от триггера DAG до сообщения» без ссылок на устаревший glue как единственный путь; перечень env/Variable явный.

- [x] **R39.2** **Общий модуль сравнения pred vs live Pinnacle (вне FastAPI route).** Рефактор: вынести/централизовать логику «список `Prediction` из БД → батч Odds API → `edge_home` / `bet_decision_home` / статусы» так, чтобы её импортировали и HTTP-слой (`live_odds_enrichment`), и batch-клиент оркестрации. Исключить дублирование формул (использовать существующие `compute_edge` / `decide_bet`).
  **Критерии приёмки:** unit-тест: на синтетических Prediction + mock quotes результаты совпадают с текущим поведением enrichment для эквивалентных входов.

- [x] **R39.3** **Контракт текста Telegram digest.** Одна функция сборки сообщения (русский текст, лимит ~4096 символов): сводка по количеству матчей, топ-N по `|edge|`, строка provenance модели (из `deploy.yaml` или лог materialize), явный блок при `missing_api_key` / `fetch_failed`. Без множественных `sendMessage` в одном прогоне.
  **Критерии приёмки:** snapshot/golden test на фикстуре; контракт полей описан в docstring модуля.

- [ ] **R39.4** **CLI entrypoint оркестрации (без новых «лоскутных» bash-скриптов).** Реализовать `python -m sports_forecast.orchestration.<имя_модуля>`: читает конфиг турнира/рынка из args + env, загружает предсказания из БД за согласованное окно (как `/predict/upcoming` / репозиторий), вызывает R39.2+R39.3, отправляет одно сообщение (переиспользовать тот же transport, что `scripts/run_nhl_refresh_notify.py`, или тонкий wrapper). Поддержать `--dry-run` (печать в stdout).
  **Критерии приёмки:** команда документирована в runbook; non-zero exit при жёсткой ошибке БД/конфига; при отключённом digest — no-op или skip с логом.

- [ ] **R39.5** **Интеграция в Airflow.** Добавить финальный `BashOperator` в `dag_nhl_morning_refresh.py` после `validate` (и при необходимости feature-flag Variable для prod), **тот же** `SF_REFRESH_POOL` или отдельный мало-слотовый pool по согласованию — без нарушения `flock` на refresh (digest только после освобождения lock в предыдущей задаче). Команда через `Variable` override для гибкости (`SF_POST_REFRESH_DIGEST_CMD` или фиксированный шаблон с `UV_RUN` + module).
  **Критерии приёмки:** DAG импортируется; при `SF_TELEGRAM_DIGEST_ENABLE=false` задача skipped / no-op; не добавлять параллельный refresh без lock.

- [ ] **R39.6** **Локальный стек = prod-поведение.** Проверить `docker-compose` профили: worker Airflow с `.env`, доступ к БД и ключам; при необходимости одна строка в `docker-compose*.yml` или док только.
  **Критерии приёмки:** в runbook — «как поднять и триггернуть `nhl_morning_refresh` локально и получить digest».

- [ ] **R39.7** **Идемпотентность и observability.** Минимум: структурированный INFO-лог (counts, статус Odds API, длина сообщения). Опционально: защита от дубликатов Telegram при retry (описать выбранный механизм).
  **Критерии приёмки:** в коде или комментарии DAG явно указано поведение при `retries`; логи не содержат секретов.

- [ ] **R39.8** **Консолидация старого скрипта.** `scripts/run_nhl_refresh_notify.py`: thin-wrapper, вызывающий новый CLI, или пометка deprecated + ссылка на модуль — один канонический путь в документации.
  **Критерии приёмки:** Makefile/док не расходятся; CI/smoke при наличии не ломается.
