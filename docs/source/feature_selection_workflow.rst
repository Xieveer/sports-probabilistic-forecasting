Feature selection и MLflow-метрики
===================================

Цель — после отбора фичей иметь **один понятный набор основных метрик** в MLflow
(``test_*``, ``shadow_*``, ``betting_*``), совпадающий с сохранёнными shadow/prod
моделями, и отдельный **снимок** прогона на полном наборе колонок для сравнения.

Запуск
------

* Профиль Hydra: ``feature_selection=aggressive`` (отбор включён, по умолчанию
  ``apply_selected_to_fit=true`` — полный повтор цикла shadow на отобранных фичах).
* Только ранжирование без переобучения: ``feature_selection.apply_selected_to_fit=false``.

Пример (уточните ``train``/маркет под свой пайплайн)::

    python -m sports_forecast.training.train tournament=... market=... feature_selection=aggressive

Чтение MLflow
-------------

Теги:

* ``primary_feature_set=selected`` — основные метрики относятся к модели на **отобранных** фичах.
* ``primary_feature_set=full`` — отбор был, но переобучение отключено; основные метрики = полный набор.
* ``fs_fit_applied`` — ``true``, если был снимок полной модели (дублирование ``*_full_*``).
* ``fs_round`` — номер раунда отбора (сейчас всегда ``1``; задел под итерации).

Параметры: ``n_features`` (число фичей у сохранённой модели), при ``selected`` —
дополнительно ``n_features_full``, ``n_features_primary``.

Метрики:

* **Основные** ``test_*``, ``shadow_*``, ``tscv_*``, ``betting_*``, ``cal_*`` —
  модель после отбора (если ``apply_selected_to_fit=true``).
* **Снимок полного набора:** ``test_full_*``, ``shadow_full_*``, ``tscv_full_*``,
  префикс ``full_`` у беттинг-метрик (например ``full_betting_roi``),
  ``cal_full_ece_*``, артефакт ``feature_importance_full.csv``.

.. note::
   Прогоны **до** R31 могли логировать дубликаты как ``*_fs_fit_*``. В текущем коде
   используются имена ``*_full_*``.

Чеклист: повторять отбор или остановиться
-----------------------------------------

Учитывайте одновременно:

#. Улучшение holdout ``test_logloss`` (или доминирующей бизнес-метрики) относительно ``test_full_*``.
#. Беттинг: ``betting_roi``, просадка, число ставок (не «оптимизировать ROI в ущерб объёму» без осознанного порога).
#. Минимальное число фичей (полезно задать нижний предел, чтобы не урезать сигнал чрезмерно).

Если после отбора метрики ухудшились — оставьте полный набор или ослабьте отбор
(``min_score_pct``, ``top_k``, стратегия ``union`` / ``vote``).

Итеративный отбор (контракт R31.4)
----------------------------------

Автоматического multi-round цикла в репозитории нет. Предлагаемый контракт для
будущей утилиты или эпика **R32** (в бэклоге отложен, реализация под вопросом):

* **Вход:** конфиг обучения, ``feature_selection``, максимум раундов ``R``, критерий останова
  (например прирост ``test_logloss`` или ROI ниже порога между раундами).
* **Шаг раунда:** обучение с FS → читать основные MLflow-метрики (модель на текущем подмножестве);
  при улучшении — зафиксировать список фичей и запустить следующий раунд **с тем же списком
  как стартовым пространством** или с повторным ранжированием на новой shadow-модели.
* **Выход:** финальный список фичей, артефакты отбора, сравнение раундов по тегу ``fs_round``.

До появления скрипта — ручной цикл: сравнить run в MLflow → изменить конфиг/фичи → новый train.
