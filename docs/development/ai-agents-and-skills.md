# Работа агентов по бизнес-инициативе

Product Owner отвечает за исходную цель до полученного результата. Он выбирает
минимальный маршрут, вызывает специализированные роли по отдельности и хранит
компактное состояние в управляющем блоке EPIC или одношаговой TASK. Канонические
требования — [REQ-024](../product/requirements/REQ-024-initiative-agent-workflow.md),
решение о памяти и границах — [ADR-025](../architecture/adr/ADR-025-initiative-memory-and-orchestration-boundaries.md),
формат артефактов — [agent-artifacts.md](agent-artifacts.md).

## Роли и модели

| Роль | Модель | Когда нужна | Результат |
|---|---|---|---|
| Product Owner | `gpt-6-sol` | Каждая бизнес-инициатива | Маршрут, память, следующее действие и проверка исходной цели |
| Business Analyst | `gpt-6-luna` | Требования неоднозначны | Краткие подтверждённые критерии |
| Architect | `gpt-6-astra` | Значимый технический выбор | План, границы и ADR при необходимости |
| Developer | `gpt-6-luna` | Небольшая проверяемая TASK | Тест, код, refactor, проверки и `done` |
| Reviewer | `gpt-6-sol` | После реализации или перед research-отчётом | Независимая проверка correctness, архитектуры, security, тестов и регрессий |
| Data Researcher | `gpt-6-sol` | Нужных данных нет или источник не изучен | Практический каталог источника и задачи на сбор/пополнение |
| Research Scientist | `gpt-6-sol` | Нужно проверить гипотезу или модель | Baseline, эксперимент, финансовое сравнение, решение GO/ITERATE/STOP |
| Operations Agent | `gpt-6-sol` | Серверная задача или запрошенный выпуск | Эксплуатация, release artifacts, deployment и проверки |

Только Architect использует Astra. Модель закреплена за ролью, поэтому Product Owner
разбивает разработку на небольшие TASK для Developer, а не выбирает модель заново
при каждом вызове. Отдельных ролей для security, тестов, документации, оценки
исследования и release review нет: эти действия входят в ответственность основных
ролей и могут использовать соответствующие skills.

Operations Agent остаётся в отдельном репозитории
`/home/xieveer/Документы/codex_projects/operations-agent`. Его запуск получает ссылку
на инициативу, exact revision, нужные release/operations inputs и явный рабочий
каталог. Он читает свой `AGENTS.md`, обновляет собственные эксплуатационные записи
и необходимые документы/артефакты этого проекта. Код приложения он не меняет.

## Выбор workflow

| Вход | Минимальный путь | Завершение |
|---|---|---|
| Очевидный bug fix | PO → Developer → Reviewer → PR/CI | Merge в `main`; TASK и `done`, без REQ/ADR |
| Новая функция или изменение поведения | PO → BA при неоднозначности → Architect при значимом решении → Developer → Reviewer | Merge в `main`, если релиз не запрошен |
| Исследование на готовых данных | PO → Research Scientist → эксперимент → Reviewer один раз | Отчёт GO/ITERATE/STOP; production только по новому решению пользователя |
| Исследование без данных | PO → Data Researcher → Engineering сбор/пополнение → ожидание сбора пользователем → Research Scientist | Отчёт после доступности данных |
| Серверная задача без правки приложения | PO → Operations Agent | Проверенное состояние сервера и актуальные записи |
| Запрошенная новая версия | Инженерный путь → Operations preparation → финальный Reviewer → PR/CI → merge/tag pipeline → Operations deployment | Health и smoke на production |

Критерии новой функции или исследования, которых нет в исходном запросе, Product Owner
предлагает пользователю на подтверждение до основной работы. Для очевидного bug fix он
формулирует их сам. Architect самостоятельно выбирает технический вариант в рамках
подтверждённых бизнес-требований. Недостающий доступ, блокер или необходимость изменить
требования возвращаются пользователю.

PR с ожидающими проверками остаётся активной работой. Product Owner проверяет CI
примерно раз в пять минут до terminal result (`gh pr checks --watch --interval 300`).
Падение запускает диагностику причины,
исправление, затронутые тесты и новый независимый review; затем цикл CI повторяется.
Для релиза тег создаётся Reviewer только на проверенном commit в `main` после merge.
После тега нельзя незаметно менять содержимое этого выпуска. Подробнее:
[orchestration.md](../../references/orchestration.md).

## Research и данные

До серьёзных экспериментов Product Owner согласует финансовые критерии: порог доли
bootstrap-прогонов с положительным ROI (ориентир 80%) и coverage ставок (ориентир 20%,
зависит от турнира). Research Scientist после разведки определяет baseline и разумные
ML-пороги. GO требует большего суммарного симулированного profit на той же тестовой
выборке, чем baseline и, если есть, текущая модель. Все рассчитываемые проектом метрики,
неопределённость и устойчивость входят в отчёт. После пяти безуспешных полных циклов
Product Owner представляет пользователю цифры и проверенные гипотезы; ранний успех
можно представить сразу. Reviewer один раз независимо проверяет итоговый подход,
leakage, расчёты и воспроизводимость.

Data Researcher сначала ищет API-запросы и WebSocket. При нужном аккаунте или прокси
Product Owner обращается к пользователю; разбор страниц согласуется отдельно.
Перед длительным сбором Engineering реализует первичную загрузку, регулярное
пополнение и возобновление после обрыва. Накопленные данные защищаются тестами от
случайного удаления и полного пересоздания; исправление отдельной записи допустимо.
Сам длительный сбор запускает пользователь в своём терминале и затем возвращается
к сохранённой инициативе.

## Артефакты и skills

Роль отвечает за решение в своей области, skill — за повторяемый приём работы.
Используй `$requirements` для неясной задачи, `$architecture-decision` для значимого
выбора, `$tdd` и `$implement-incrementally` для кода, `$code-review` для независимой
проверки, `$security-review` внутри Review при достижимом риске, `$documentation`
для нужных документов и `$prepare-release` для запрошенной версии. Пропускай
неприменимые этапы. Исторический `docs/cursor/refactor/` не расширяется.

AI-слой проверяется командой `make ai-validate`; при изменении поведения применяются
относящиеся к нему тесты. Выполненные и невыполненные проверки записываются честно.
