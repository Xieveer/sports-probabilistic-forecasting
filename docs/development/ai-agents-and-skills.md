# Роли и skills для AI-агентов

Этот каталог — каноническая замена Cursor-специфичных ролей и skills из `.cursor/`.
Содержимое `.cursor/` можно сохранять локально для совместимости, но новые правила,
роли и процессы следует изменять в `AGENTS.md`, `agents/`, `.codex/agents/` и `skills/`.

Этот слой помогает проводить задачу через полный цикл разработки, не превращая проект
в конкретное приложение. Подход вдохновлён репозиторием
[addyosmani/agent-skills](https://github.com/addyosmani/agent-skills), но состав,
русскоязычные инструкции и проверки адаптированы для Python-проектов Sports Probabilistic Forecasting.

## Из чего состоит AI-слой

| Элемент | Где находится | Для чего нужен |
|---|---|---|
| Правила | `AGENTS.md` | Постоянные ограничения репозитория: язык, безопасность, TDD и критерии проверки |
| Роль | `agents/` | Определяет точку зрения, ответственность и формат результата |
| Профиль Codex | `.codex/agents/` | Закрепляет за именованным агентом модель, усилие и режим доступа |
| Skill | `skills/` | Задаёт повторяемый пошаговый процесс для конкретного типа работы |
| Reference | `references/` | Хранит общие чек-листы и критерии готовности без дублирования |
| Eval case | `evals/` | Проверяет ожидаемое поведение skills на характерных запросах |
| Plugin manifest | `.codex-plugin/` | Делает skills устанавливаемым плагином Codex |

Правила сохранения и передачи результатов ролей находятся в
[`agent-artifacts.md`](agent-artifacts.md). Для новых Codex-задач это канонические места для
REQ, ADR, epic/task и отчёта выполнения; `docs/cursor/refactor/` остаётся историей Cursor.

Роль отвечает на вопрос «в качестве кого анализировать задачу», а skill — «каким
процессом её выполнять». Для простой задачи достаточно одного skill; роль нужна, когда
важны отдельная перспектива и формальный результат.

## Рекомендуемый цикл

1. **Определить** — собрать контекст, ограничения и проверяемые критерии.
2. **Спланировать** — выбрать минимальное решение, внешние границы и тестовую стратегию.
3. **Реализовать** — пройти red → green → refactor небольшими проверяемыми шагами.
4. **Проверить** — выполнить независимое ревью корректности, безопасности и эксплуатации.
5. **Документировать** — синхронизировать README, документацию, конфигурацию и ADR.
6. **Подготовить выпуск** — подтвердить критерии готовности, но не выполнять deployment
   без отдельного разрешения.

Этапы не являются обязательной бюрократией. Для локальной правки опечатки можно сразу
использовать `documentation`; для нового внешнего API нужен полный цикл.

## Когда использовать роли

| Роль | Когда использовать | Ожидаемый результат |
|---|---|---|
| `product-analyst` | Запрос неоднозначен, появляется новая функция или меняется поведение | Границы задачи, сценарии, критерии приёмки и открытые вопросы |
| `architect` | Меняются компоненты, внешние границы, данные, зависимости или эксплуатация | Варианты, выбранное решение, риски и ADR при необходимости |
| `test-designer` | Нужно спроектировать первый падающий тест или набор уровней тестирования | Матрица поведения, негативные случаи и порядок тестов |
| `implementer` | Критерии понятны и можно менять код | Минимальная реализация с доказательствами red/green/refactor |
| `reviewer` | Изменение готово к независимой проверке | Findings по приоритету с файлами, строками и остаточными рисками |
| `security-reviewer` | Затронуты ввод, сеть, секреты, зависимости, Docker, CI или доступ | Модель угроз в границах изменения и проверяемые меры защиты |
| `documentation-writer` | Изменилось поведение, команда, конфигурация или публичный контракт | Актуальные русскоязычные документы и примеры |
| `devops-reviewer` | Меняются CI, Docker, сборка или подготовка выпуска | Проверка воспроизводимости, production-контракта и готовности к передаче Operations Agent |

Не используй роль как отдельную «личность» ради церемонии. Один AI-агент может
последовательно принять несколько ролей. Если платформа поддерживает несколько агентов,
главный агент сам управляет композицией; роли не запускают друг друга.

## Модели именованных агентов Codex

Основная модель намеренно не закреплена в проекте: её можно выбирать в интерфейсе под конкретную
задачу. Для неизвестного типа сабагента `.codex/config.toml` задаёт сбалансированный default
`gpt-5.6-terra` с усилием `medium`. Именованные профили используют следующую маршрутизацию:

| Роли | Модель | Усилие | Причина |
|---|---|---|---|
| `product-analyst`, `architect`, `reviewer`, `security-reviewer` | `gpt-5.6-sol` | `high` | Неоднозначные решения и анализ рисков |
| `implementer` | `gpt-5.6-terra` | `medium` | Обычная ограниченная реализация |
| `devops-reviewer` | `gpt-5.6-terra` | `high` | Техническая проверка с повышенным вниманием к рискам |
| `test-designer` | `gpt-5.6-terra` | `medium` | Узкая работа по подтверждённой спецификации |
| `documentation-writer` | `gpt-5.6-terra` | `low` | Ясная повторяемая текстовая задача |

Sol обозначается идентификатором `gpt-5.6-sol`. Явно указанная при запуске модель
может переопределить общий default, но настройки конкретного custom agent имеют приоритет.

## Когда использовать skills

| Skill | Использовать, когда | Не использовать, когда |
|---|---|---|
| `$requirements` | Нужно превратить идею в проверяемую задачу | Требования уже однозначны и подтверждены |
| `$plan-change` | Работа затрагивает несколько файлов или имеет зависимости между шагами | Изменение очевидно и локально |
| `$architecture-decision` | Решение дорого отменить или оно меняет системные границы | Достаточно локальной реализации |
| `$design-interface` | Создаётся публичный Python API, CLI, событие или внешний контракт | Меняется только внутренняя деталь |
| `$tdd` | Добавляется поведение или исправляется дефект | Меняется только текст без поведения |
| `$implement-incrementally` | План нужно выполнять небольшими проверяемыми порциями | Задача состоит из одного безопасного шага |
| `$debug-systematically` | Причина сбоя неизвестна или проблема воспроизводится нестабильно | Причина уже доказана и нужен только согласованный fix |
| `$code-review` | Нужна независимая проверка diff | Автор ещё не закончил реализацию |
| `$simplify-code` | Код корректен, но стал сложнее необходимого | Поведение ещё не подтверждено тестами |
| `$security-review` | Есть чувствительные данные, ввод, сеть, зависимости или права | Изменение не влияет на поверхность атаки |
| `$documentation` | Изменилось использование или эксплуатация | Документы уже точно отражают изменение |
| `$ci-troubleshooting` | Локально всё работает, но CI падает, либо нужно разобрать workflow | Сбой находится в прикладном коде и воспроизводится локально |
| `$prepare-release` | Версия готова к итоговой проверке и передаче | Пользователь просит автоматически развернуть систему |

Полный текст каждого процесса находится в соответствующем `skills/<name>/SKILL.md`.
Обязательные шаги, red flags и проверка результата не сокращаются.

## Как сформулировать запрос

Codex может выбрать skill по описанию задачи автоматически. Для предсказуемого результата
роль и skill можно назвать явно:

```text
Прими роль product-analyst и примени $requirements.
Собери критерии приёмки для импорта спортивных данных, код пока не пиши.
```

```text
Прими роль implementer и примени $tdd.
Исправь повторную обработку события, сначала покажи воспроизводящий падающий тест.
```

```text
Проведи независимые $code-review и $security-review этого изменения.
Сначала перечисли findings по критичности, ничего не исправляй.
```

Если инструмент не поддерживает нативное обнаружение skills, перед задачей укажи ему
прочитать `AGENTS.md`, нужный файл из `agents/` и нужный `SKILL.md`. Благодаря обычному
Markdown эта схема переносится между Codex, Claude Code, Cursor и другими агентами.

## Последовательность для типовых задач

### Новая возможность

`product-analyst` + `$requirements` → `architect` + `$plan-change` →
`test-designer` + `$tdd` → `implementer` + `$implement-incrementally` →
`reviewer` + `$code-review` → `documentation-writer` + `$documentation`.

Добавляй `$architecture-decision`, `$design-interface` и `$security-review` только при
соответствующем риске.

### Исправление дефекта

`implementer` + `$debug-systematically` → `$tdd` → `$code-review`.
Первый тест обязан воспроизвести исходный дефект.

### Commit/push и завершение EPIC

После готовой TASK автор реализации передаёт diff независимому `reviewer` с
`$code-review`. Автор не делает commit/push: их выполняет только reviewer после
отсутствия блокирующих findings, фиксации проверок и проверки синхронизации
канонических документов. Если findings исправлены, review повторяется на новом diff.
После завершения всех TASK главный агент назначает отдельное полное EPIC review;
reviewer фиксирует его в EPIC отдельным evidence-коммитом после проверенного commit. Без него EPIC не
считается завершённым и не передаётся как release-candidate.

### Явный контракт этапов

| Этап | Ответственная роль | Обязательный артефакт | Gate для перехода |
|---|---|---|---|
| Бизнес-требования | product-analyst | confirmed REQ | пользователь подтвердил критерии |
| Архитектура | architect | ADR либо отметка «не требуется» | выбран минимальный проверяемый вариант |
| Планирование | главный агент | EPIC и независимые TASK | каждый критерий REQ связан с TASK и проверкой |
| Реализация TASK | implementer | обновлённые TASK, отчёт done и документация | доказаны red/green и обязательные проверки |
| Review TASK | reviewer | результат review в отчёте TASK | нет P0/P1/P2; reviewer делает commit/push |
| Закрытие EPIC | reviewer | раздел «Полное EPIC review» в EPIC | все TASK terminal, документация синхронизирована; reviewer фиксирует hash проверенного коммита отдельным evidence-коммитом |

`make ai-validate` проверяет этот контракт в профиле reviewer и канонических правилах.

### Подготовка выпуска

После реализации можно независимо провести:

- `reviewer` + `$code-review`;
- `security-reviewer` + `$security-review`;
- `devops-reviewer` + `$prepare-release`;
- `documentation-writer` + `$documentation`.

Их результаты объединяет главный агент. Параллельная работа безопасна только для
независимых проверок; несколько агентов не должны одновременно менять одни файлы.

Перед итоговым решением `devops-reviewer` проверяет заполнение
`docs/operations/production-handoff.md` и запускает `make production-check`. Он не
развёртывает сервис и не угадывает его runtime-контракт. Заполненный документ передаётся
DevOps Operations Agent, который отвечает за серверную часть и запрашивает отдельное
одобрение на production-развёртывание.

## Проверка AI-слоя

Команда проверяет манифест, обязательные разделы ролей и skills, уникальность eval cases
и ссылки на существующие skills:

```text
make ai-validate
```

Она входит в `make check` и pre-commit. При добавлении skill сначала создай сценарий в
`evals/cases.json`, который фиксирует не только желаемое действие, но и запрещённое
поведение. Например, skill требований должен собирать критерии, но не начинать реализацию.

## Как расширять набор

Новая роль оправдана, когда появляется самостоятельная зона ответственности и отдельный
формат результата. Новый skill оправдан, когда процесс повторяется в разных проектах и
его пропуск уже приводил к ошибкам.

Перед добавлением:

1. убедись, что существующий skill нельзя уточнить без смешения обязанностей;
2. опиши триггеры и ситуации, когда skill не нужен;
3. зафиксируй обязательные шаги, red flags и проверку;
4. добавь eval case;
5. обнови эту карту и выполни `make ai-validate`.
