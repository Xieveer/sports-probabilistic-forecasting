# Артефакты работы Codex-агентов

Этот документ задаёт единый способ сохранять и передавать знания между ролями Codex.
Он применяется к новым возможностям, изменениям поведения и существенным дефектам. Старый
журнал Cursor в `docs/cursor/refactor/` остаётся историческим и не переносится автоматически.

## Канонические места

| Артефакт | Создаёт / обновляет | Место | Назначение |
|---|---|---|---|
| Требования | `product-analyst` | `docs/product/requirements/REQ-<id>-<slug>.md` | Подтверждённая бизнес-потребность и критерии приёмки |
| Архитектурное решение | `architect` | `docs/architecture/adr/ADR-<id>-<slug>.md` | Значимое решение, варианты и последствия |
| Эпик | главный агент | `docs/backlog/EPIC-<id>-<slug>.md` | Цель, декомпозиция и зависимости большой работы |
| Задача | главный агент | `docs/backlog/tasks/TASK-<epic-id>-<sequence>-<slug>.md` | Один проверяемый вертикальный срез для implementer |
| Отчёт о завершении | `implementer` | `docs/changes/done/TASK-<epic-id>-<sequence>-<slug>.md` | Доказательства реализации и проверок |

Идентификатор эпика выбирают один раз и не меняют. Идентификатор новой задачи состоит из
идентификатора эпика и порядкового номера: например, `EPIC-002` содержит `TASK-002-1`,
`TASK-002-2` и далее. Связи между артефактами оформляют относительными Markdown-ссылками.
Если отдельный файл не нужен для безопасной локальной правки, агент пишет
в итоговом сообщении, почему применён облегчённый процесс.

## Статусы и переходы

`REQ`: `draft` → `confirmed` → `superseded`.

`ADR`: `proposed` → `accepted` | `rejected` | `superseded`.

`EPIC` и `TASK`: `backlog` → `in_progress` → `done` | `blocked` | `cancelled`.

Только главный агент или пользователь меняет приоритет, владельца и scope эпика. Implementer
может перевести назначенную задачу в `in_progress`, `blocked` или `done`; изменение scope,
критериев либо архитектурного решения возвращает задачу на соответствующий предыдущий этап.

## Handoff

Следующий этап получает ссылку на предыдущий артефакт, а не пересказ без источника.

```text
REQ (confirmed)
  → ADR (если решение значимо) + EPIC/TASK
  → TASK (in_progress) + тестовый план
  → отчёт done + обновлённый TASK
  → review / security
  → финальная синхронизация документации и статусов
  → документация / commit
```

- Product analyst создаёт или обновляет `REQ` и передаёт только `confirmed` требования.
- Architect ссылается на `REQ`; после решения обновляет ADR и передаёт ссылку на него planner,
  test-designer и implementer.
- Planner связывает каждый критерий `REQ` с задачей и проверкой. В один момент времени у
  зависимой цепочки только одна задача имеет статус `in_progress`.
- Implementer до кода отмечает задачу `in_progress`; после зелёных проверок создаёт отчёт
  `done`, обновляет TASK и передаёт ссылки на diff и отчёт проверяющим.
- Reviewer, security-reviewer и documentation-writer добавляют результаты в раздел
  «Проверки и follow-up» отчёта или создают отдельную связанную задачу для finding. Они не
  переписывают доказательства implementer.
- После успешного review главный агент до коммита синхронизирует все затронутые
  канонические документы и статусы: REQ/ADR/EPIC/TASK, отчёт `done`, runbook,
  README и `.env.example`. Эпик становится `done` только когда его задачи имеют
  terminal status; отложенный scope должен быть явно `blocked` или `cancelled`.

## Доказательства

В отчёт `done` попадают только фактически выполненные команды, их краткий результат,
связанные тесты, изменённые границы и остаточные риски. Утверждение `red` допустимо только
с названием и результатом фактически запущенного падающего теста. Успешное выполнение review,
security или документации фиксируется ссылкой на отчёт соответствующей роли либо явно как
не выполненное.

## Старые артефакты

`docs/cursor/context/` остаётся каноническим контекстом предметной области, а
`docs/cursor/refactor/` — историей Cursor-разработки. Новые Codex-артефакты не создаются в
этих каталогах. При продолжении старого эпика новая задача может сослаться на существующий
`R*`-документ как на входной контекст.
