# Планирование изменения

## Процесс

1. Прочитать подтверждённые требования, AGENTS.md, существующий код, тесты и документацию.
2. Назвать неизвестные, которые блокируют корректный план; остальные оформить как предположения.
3. Выбрать минимальный вертикальный срез, дающий наблюдаемое поведение.
4. Разбить работу на шаги, каждый из которых:
   - имеет один результат;
   - указывает затрагиваемые области;
   - содержит проверку;
   - оставляет репозиторий в согласованном состоянии.
5. Для изменения поведения поставить тест перед production-кодом.
6. Упорядочить шаги по зависимостям и риску, ранние проверки поставить перед дорогой работой.
7. Отдельно отметить миграции, обратную совместимость, документацию и rollback.
8. Связать каждый критерий приёмки с шагом и доказательством.
9. Для большой работы создать `EPIC` и `TASK` по шаблонам из `docs/backlog/`; для одного среза
   создать только TASK. Внести ссылки на REQ и ADR либо явно указать, что ADR не требуется.

## Нельзя сокращать

- Не писать план как список фаз «backend → tests → docs».
- Не объединять независимые большие изменения в один шаг.
- Не добавлять «на будущее» компоненты без критерия приёмки.
- Не выдавать предположение за уже принятое решение.

## Red flags

- Шаг нельзя проверить отдельно.
- Тесты стоят после всей реализации.
- План требует одновременного изменения многих границ.
- Нет пути остановиться после частично выполненной работы.

## Результат

Вернуть ссылки на EPIC/TASK с целью, предположениями, упорядоченными шагами, проверками,
зависимостями, рисками и rollback. Для сложной работы получить одобрение плана до реализации.

## Проверка

- Все критерии приёмки покрыты.
- В каждом шаге указан ожидаемый артефакт и команда/наблюдение проверки.
- Одновременно in progress может быть только один зависимый шаг.
