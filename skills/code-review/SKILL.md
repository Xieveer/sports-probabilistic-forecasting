# Ревью кода

## Пять направлений

1. **Correctness:** требования, границы, ошибки, состояние, конкурентность.
2. **Simplicity:** имена, поток управления, дублирование, оправданность abstractions.
3. **Architecture:** владение, зависимости, контракты, соответствие ADR.
4. **Security:** недоверенный ввод, авторизация, секреты, supply chain.
5. **Operations:** логи, конфигурация, ресурсы, миграция, rollback.

## Процесс

1. Прочитать требования и diff целиком.
2. Проследить изменённые входы до побочных эффектов.
3. Проверить тесты: способны ли они обнаружить дефект и не закрепляют ли реализацию.
4. Для риска безопасности применить `$security-review`.
5. Проверить документацию и совместимость.
6. Вернуть findings до summary, по убыванию важности.

## Обязательный gate для TASK и EPIC

1. После реализации TASK автор запускает проверки, но **не выполняет commit или push**.
2. Главный агент передаёт полный diff независимому `reviewer` с `$code-review`.
3. При P0/P1/P2 finding автор исправляет его через TDD, после чего reviewer
   повторяет review изменённого diff.
4. До commit/push reviewer сверяет обновление TASK, отчёта `done`, REQ/ADR/EPIC и применимых
   README/runbook/`.env.example`. Он сначала коммитит проверенный diff, а затем отдельным
   documentation-only evidence-коммитом фиксирует в отчёте hash проверенного коммита; после
   этого одним push отправляет согласованную ветку с обоими коммитами.
5. Только reviewer, вернувший отсутствие блокирующих findings и зафиксировавший
   выполненные проверки, создаёт эти коммиты и выполняет push согласованной ветки.
6. После всех TASK EPIC главный агент инициирует отдельное полное EPIC review:
   проверяются требования/ADR, границы задач, документы, интеграционные риски,
   release evidence и незавершённый scope. Reviewer фиксирует итог и hash проверенного коммита
   в EPIC отдельным evidence-коммитом; до этого review EPIC не объявляется завершённым и не
   передаётся как release-candidate.

## Нельзя сокращать

- Не считать успешный CI доказательством корректности.
- Не выдавать style preference за блокирующий дефект.
- Не писать расплывчатое «добавить обработку ошибок» без сценария.
- Не исправлять код во время review, если пользователь просил только анализ.

## Формат находки

Указать приоритет, точное место, достижимый сценарий, последствие и минимальное направление
исправления. Если findings нет — назвать проверенные области и остаточные риски.

## Red flags

- Находка не привязана к строке или контракту.
- Предлагаемое исправление расширяет scope.
- Тест проходит даже при удалении проверяемого поведения.
- Summary скрывает блокирующие findings.
- Автор TASK сам делает commit/push до независимого reviewer gate.
- EPIC закрывается по статусам TASK без отдельного полного review.

## Проверка

- Рассмотрены все пять направлений либо объяснена неприменимость.
- Findings воспроизводимы и actionable.
- Не заявлена абсолютная безопасность или корректность.
