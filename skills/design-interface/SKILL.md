# Проектирование интерфейса

## Процесс

1. Определить потребителя, ответственность и границу доверия.
2. Описать входы, выходы, типы, инварианты и семантику ошибок.
3. Выбрать минимальную поверхность: не экспортировать то, что не нужно потребителю.
4. Задать поведение для пустых, повторных, неверных и частично доступных данных.
5. Для сети определить timeout, retry, idempotency, rate limit и отмену.
6. Для Python определить sync/async контракт и владение ресурсами.
7. Проверить совместимость и способ эволюции без молчаливого изменения смысла.
8. Сначала написать contract-тест или пример использования, затем реализацию через TDD.

## Нельзя сокращать

- Не возвращать `None` как универсальный ответ на разные ошибки.
- Не смешивать транспортную модель и модель предметной области без причины.
- Не создавать общий интерфейс ради единственной гипотетической реализации.
- Не логировать секретные входы для «удобства диагностики».

## Red flags

- Значение поля зависит от неописанного контекста.
- Исключения теряются или превращаются в пустой результат.
- Повтор операции может создать дубликаты.
- Потребитель обязан знать детали реализации.

## Результат

Вернуть контракт, примеры использования, ошибки, нефункциональные ограничения и план проверки.

## Проверка

- Контракт понятен без чтения реализации.
- Ошибочные и граничные сценарии определены.
- Изменение можно проверить на границе через тест.
