# Упрощение кода

## Процесс

1. Зафиксировать текущее поведение тестами и релевантными проверками.
2. Назвать конкретную сложность: ветвления, состояния, уровни, дублирование или неясный контракт.
3. Понять причину существующей конструкции и её потребителей.
4. Выбрать изменение, которое удаляет понятие, ветку или специальный случай, а не просто
   перемещает его.
5. Делать по одному структурному изменению с тестом после каждого.
6. Удалить мёртвый код, устаревшие comments и compatibility shims только после проверки
   потребителей.
7. Сравнить сложность до/после и обновить документацию при изменении внутренней архитектуры.

## Нельзя сокращать

- Не менять публичное поведение под видом refactor.
- Не заменять понятный код «умной» конструкцией ради количества строк.
- Не создавать generic abstraction до третьего подтверждённого случая.
- Не удалять странный guard, не выяснив его происхождение.

## Red flags

- Diff одновременно добавляет feature.
- Число концепций не уменьшилось.
- Новый helper только переименовал старую сложность.
- Тесты не покрывают удаляемую ветку.

## Результат

Вернуть, какая сложность удалена, почему поведение сохранено и какие проверки это доказывают.

## Проверка

- Тесты зелёные до и после.
- Публичный контракт не изменён.
- Код объективно имеет меньше состояний, ветвей или дублирования.
