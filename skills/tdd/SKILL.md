# Разработка через TDD

## Red

1. Выбрать один критерий приёмки и самый дешёвый надёжный уровень теста.
2. Написать тест поведения, а не внутреннего устройства.
3. Запустить только новый тест.
4. Подтвердить, что он падает по ожидаемой причине; зелёный с первого запуска требует проверки
   теста или наличия поведения.

## Green

1. Добавить минимальный production-код для выбранного сценария.
2. Запустить новый тест, затем близкий набор тестов.
3. Не расширять scope и не создавать абстракцию до подтверждённой повторяемости.

## Refactor

1. Упростить имена, структуру и дублирование без изменения контракта.
2. После каждого смыслового изменения повторить затронутые тесты.
3. Запустить полный релевантный suite и проверки типов/lint.
4. Обновить документацию, если изменился публичный контракт.

Для выбора теста прочитать `../../references/testing-checklist.md`.

## Нельзя сокращать

- «Добавлю тест потом» — это не TDD.
- Ручная проверка не заменяет воспроизводимый тест.
- Запрещено ослаблять assertion, skip или конфигурацию ради green.
- Не утверждать red/green без фактически выполненной команды.

## Red flags

- Исправление дефекта без reproduction test.
- Тест проверяет mock-вызовы вместо результата.
- Новый тест проходит до реализации.
- Один тест проверяет несколько независимых поведений.

## Результат

Сообщить доказанный red, минимальный green, выполненный refactor и точные команды проверки.

## Проверка

- Каждое новое поведение имеет тест.
- Дефект воспроизводился до исправления.
- Нет пропущенных или отключённых тестов.
- Coverage не снизился, полный релевантный suite зелёный.
